# IEC 61850 Architecture & Protocol Research Primer

## Executive Summary

IEC 61850 is a substation automation standard built around a structured information model and multiple communication services rather than a single network protocol. Its architecture connects engineering configuration, logical device models, supervisory communication, and time-critical process-bus messaging into a common substation information model.

The research therefore needs to treat IEC 61850 as an ecosystem:

```text
                         IEC 61850
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
         SCL               MMS            GOOSE / SV
          │                 │                 │
   Configuration       Client / Server    Publisher /
     & Schema           Communication     Subscriber
          │                 │                 │
          ▼                 ▼                 ▼
   Logical Model       Namespace         Process Bus
          │            Enumeration
          │                 │
          └─────────────────┼─────────────────┘
                            ▼
                     Physical Process
```

The central architectural model can be summarized as:

```text
SCL Configuration
        ↓
IED / Logical Model
        ↓
Data Objects / Data Attributes
        ↓
DataSets / Control Blocks
        ↓
Communication Services
        ↓
Process Interaction
```

Four components are particularly relevant to this research:

```text
SCL
 │
 └── Defines the configured substation model

MMS
 │
 └── Client/server access to the information model

GOOSE
 │
 └── Time-critical Layer-2 event/state distribution

SV
 │
 └── Time-critical Layer-2 sampled measurement streams
```

The security investigation follows these boundaries rather than treating IEC 61850 as a single protocol surface.

The research therefore examines:

```text
Engineering Configuration
        ↓
SCL Schema & Trust
        ↓
MMS Association & Namespace
        ↓
MMS Control / File Services
        ↓
GOOSE / SV Process-Bus Mechanics
        ↓
Injection & State Manipulation
        ↓
Security Extensions
```

This primer establishes only the architectural concepts required to understand those experiments. It is not intended to reproduce the complete IEC 61850 specification.

---

# 1. Multi-Tier Substation Ecosystem Architecture

IEC 61850 models substation automation across several functional levels rather than treating every device as an isolated endpoint.

A simplified architecture is:

```text
               +-------------------------------------------------------+
               |                  Station Level                        |
               |      Engineering Workstation / SCADA / HMI            |
               +---------------------------+---------------------------+
                                           |
                                    Station Bus
                                           |
                                      MMS / TCP
                                        Port 102
                                           |
        +----------------------------------+----------------------------------+
        |                                                                     |
+-------+-----------------------+                         +-------------------+-------------------+
|       Bay Level: IED 1        |                         |       Bay Level: IED 2                | 
|   Protection / Control        |                         |   Protection / Control                |
+-------+-----------------------+                         +-------------------+-------------------+
        |                                                                      |
        |                         Process Bus                                  |
        |                    GOOSE / Sampled Values                            |
        |                                                                      |
        +-------------------------------+-------------------------------------+
                                        |
                         +--------------+--------------+
                         |                             |
                  +------+-------+              +------+-------+
                  | Merging Unit |              | Switchgear / |
                  |     (MU)     |              | Sensors etc. |
                  +--------------+              +-------------+
```

The exact physical implementation varies between substations. The important distinction for the research is between **station-level client/server communication** and **bay/process-level time-critical communication**.

---

## 1.1 Station Level

The station level contains systems such as:

* SCADA/HMI systems
* Engineering workstations
* Historians
* Station controllers
* Configuration and maintenance systems

MMS is commonly used for client/server communication at this level.

The communication model is therefore approximately:

```text
SCADA / Engineering Client
            │
            │ MMS
            ▼
           IED
            │
            ▼
     Logical Information Model
```

This is the primary architectural context for the MMS research phases.

---

## 1.2 Bay Level

The bay level contains Intelligent Electronic Devices (IEDs), including protection relays and bay controllers.

These devices implement logical functions such as:

```text
Protection
Control
Measurement
Monitoring
Interlocking
```

An IED can expose these functions through the IEC 61850 logical-node model while simultaneously participating in GOOSE communication with other IEDs.

Consequently, an IED can participate in both communication models:

```text
                   IED
                  /   \
                 /     \
                ▼       ▼
             MMS       GOOSE
          Client/      Publisher/
           Server      Subscriber
```

This dual role is important when evaluating trust boundaries. A device may expose a rich application namespace over MMS while also accepting time-critical Layer-2 messages from peer devices.

---

## 1.3 Process Level

The process level interfaces with physical electrical equipment.

Examples include:

* Current transformers
* Voltage transformers
* Circuit breakers
* Disconnectors
* Sensors
* Merging units

Merging Units digitize analog measurements and publish sampled values to the process bus.

Conceptually:

```text
Physical Measurement
        ↓
CT / VT
        ↓
Merging Unit
        ↓
Sampled Values
        ↓
Protection / Measurement IED
```

GOOSE can similarly carry state information between bay-level and process-related devices.

---

# 2. IEC 61850 Communication Architecture

IEC 61850 does not define one universal packet format for every communication function. Instead, different services operate through different communication mechanisms.

The research-relevant profile is:

```text
+------------------------------------------------------+
|                 IEC 61850 Information Model          |
+------------------------------------------------------+
          │              │                 │
          ▼              ▼                 ▼
         MMS            GOOSE              SV
          │              │                 │
          ▼              ▼                 ▼
     ISO-on-TCP       Ethernet          Ethernet
       / TCP/102       Layer 2            Layer 2
```

The major traffic categories are:

| Component | Primary Role                                                    | Network Context  |
| --------- | --------------------------------------------------------------- | ---------------- |
| **SCL**   | Configuration and information-model description                 | Offline XML      |
| **MMS**   | Client/server monitoring, control, reporting, and file services | TCP/102          |
| **GOOSE** | Peer-to-peer event and state messaging                          | Ethernet Layer 2 |
| **SV**    | Continuous sampled measurement transmission                     | Ethernet Layer 2 |

# 3. SCL & Engineering Configuration Model

The **Substation Configuration Language (SCL)** provides the XML-based configuration model used to describe substation systems, IED capabilities, communication relationships, and the information model.

For this research, SCL should be viewed as the bridge between the intended engineering design and the runtime configuration of the devices.

```text
                 SCL
                  │
        ┌─────────┼─────────┐
        │         │         │
        ▼         ▼         ▼
       IED    Substation   Communication
       Model     Model       Bindings
        │         │         │
        └─────────┼─────────┘
                  ▼
          Configured IED
```

This makes SCL security-relevant even though it is primarily an engineering artifact rather than a network protocol.

---

## 3.1 Relevant SCL Documents

The IEC 61850 ecosystem defines several SCL document types.

The research primarily needs the conceptual distinction:

| Document | Research Relevance                                 |
| -------- | -------------------------------------------------- |
| **ICD**  | Describes an IED's capabilities                    |
| **CID**  | Describes a configured IED                         |
| **SCD**  | Describes the complete substation configuration    |
| **SSD**  | Describes the substation/system specification      |
| **IID**  | Represents IED-specific instantiated configuration |

The important relationship is:

```text
IED Capabilities
      ↓
Engineering Configuration
      ↓
SCD / CID
      ↓
Configured Device
```

Therefore, changing SCL content can potentially change more than metadata. It can alter the logical model, datasets, communication relationships, or other configuration consumed by an implementation. This is why SCL parsing and configuration validation form the first research phase.

# 4. IEC 61850 Object Model

The central IEC 61850 information model represents substation functions as structured objects rather than flat numerical addresses.

A simplified hierarchy is:

```text
IED
 │
 └── Server
      │
      └── Logical Device
           │
           ├── Logical Node
           │
           ├── Logical Node
           │
           └── ...
                │
                ▼
           Data Object
                │
                ▼
        Common Data Class
                │
                ▼
         Data Attribute
```

The additional Common Data Class layer becomes important when interpreting structured objects such as status, quality, timestamps, and measurements.

---

# 5. Servers, Logical Devices & Logical Nodes

An IED does not expose its entire information model as one undifferentiated namespace.

A simplified structure is:

```text
IED
 │
 └── Server
      │
      ├── Logical Device
      │    │
      │    ├── LLN0
      │    ├── LPHD
      │    ├── XCBR1
      │    ├── CSWI1
      │    └── MMXU1
      │
      └── ...
```

The **Server** provides the application context through which the client accesses the information model.

A **Logical Device (LD)** groups related logical functions.
A **Logical Node (LN)** represents a standardized functional component.

Two special logical nodes are particularly relevant:

```text
LLN0
 │
 └── Common logical-node functionality

LPHD
 │
 └── Physical-device / hardware-related information
```

Other logical nodes represent functional domains.

---

## 5.1 Logical Node Class Groups

Logical Node class names use standardized prefixes that indicate their functional domain.

Examples include:

| Prefix | Functional Domain       | Example        |
| ------ | ----------------------- | -------------- |
| **A**  | Automatic control       | `ATCC`         |
| **C**  | Supervisory control     | `CSWI`         |
| **G**  | Generic functions       | `GGIO`         |
| **M**  | Metering / measurement  | `MMXU`         |
| **P**  | Protection              | `PTOC`         |
| **R**  | Protection-related      | `RREC`         |
| **S**  | Sensors / monitoring    | `SIMG`         |
| **T**  | Instrument transformers | `TVTR`         |
| **X**  | Switchgear              | `XCBR`, `XSWI` |

The research does not require memorizing every Logical Node class. The important point is that the class name provides semantic context about the function represented by the node.

---

# 6. Data Objects, Common Data Classes & Data Attributes

A Logical Node contains Data Objects representing specific functional information.

For example:

```text
XCBR1
  │
  └── Pos
       │
       ├── stVal
       ├── q
       └── t
```

Here:

```text
XCBR1 → Logical Node
Pos   → Data Object
stVal → Status Value
q     → Quality
t     → Timestamp
```

The Data Object's structure is defined through a **Common Data Class (CDC)**.

Conceptually:

```text
Logical Node
      ↓
Data Object
      ↓
Common Data Class
      ↓
Data Attributes
```

This matters for security research because values are not isolated from their associated semantic information.

A status value can carry:

```text
Value
+
Quality
+
Timestamp
```

Consequently, manipulating a quality attribute may change how the receiving application interprets an otherwise valid process value.

---

# 7. Object Naming & References

IEC 61850 uses structured object references rather than flat numerical process addresses.

A simplified reference can be represented as:

```text
LD/LN.DO.DA
```

For example:

```text
SubstationA_Bay1/CTRL/XCBR1.Pos.stVal
```

Conceptually:

```text
SubstationA_Bay1/CTRL
        │
        ▼
    XCBR1
        │
        ▼
       Pos
        │
        ▼
      stVal
```

This hierarchy provides semantic information that is absent from a simple numerical address. It also creates an important reconnaissance surface. If a client can enumerate the server namespace, the discovered object names can reveal:

```text
Protection Functions
Control Functions
Measurements
Status Information
Configuration Objects
```

This relationship becomes central to the MMS enumeration phase.

---

# 8. Functional Constraints

IEC 61850 uses **Functional Constraints (FCs)** to describe the functional context in which Data Attributes are used.

Relevant examples include:

| FC     | Meaning                | Research Relevance           |
| ------ | ---------------------- | ---------------------------- |
| **ST** | Status information     | Process state                |
| **MX** | Measured values        | Analog measurements          |
| **CO** | Control                | Control operations           |
| **CF** | Configuration          | Configuration parameters     |
| **DC** | Description            | Metadata                     |
| **SP** | Setpoint               | Process control parameters   |
| **SG** | Setting group          | Setting-group information    |
| **SE** | Setting group editable | Setting modification         |
| **SV** | Substitution           | Substituted values           |
| **BL** | Blocking               | Blocking-related information |

Functional Constraint should not be treated as a simple access-control list.

Instead:

```text
Data Attribute
      │
      ▼
Functional Constraint
      │
      ▼
Service / Functional Context
```

Whether a particular attribute can be read, written, controlled, or otherwise manipulated depends on the object definition, service, and implementation behavior. This becomes important when testing MMS `Read`, `Write`, and control operations.

---

# 9. DataSets & Control Blocks

A **DataSet** groups multiple Data Attributes into a logical collection.

The relationship is:

```text
Logical Node / Logical Device
             │
             ▼
          DataSet
             │
      ┌──────┼──────┐
      ▼      ▼      ▼
     DA     DA      DA
```

DataSets are important because several IEC 61850 communication services operate around them.

The architectural relationship is:

```text
Data Model
     ↓
DataSet
     ↓
Control Block
     ↓
Communication Service
```

Control blocks provide configuration and operational parameters for services such as reporting, GOOSE, and Sampled Values.

Conceptually:

```text
                    DataSet
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Report         GOOSE          SV
       Control        Control       Control
       Block          Block         Block
          │            │             │
          ▼            ▼             ▼
        MMS          Ethernet      Ethernet
```

This relationship connects the information model established through SCL to the traffic observed on the network.

---

# 10. MMS Client/Server Architecture

MMS provides the principal client/server application mechanism used by IEC 61850 for station-level communication. Unlike GOOSE and SV, MMS operates through a connection-oriented stack.

A simplified protocol path is:

```text
MMS
 │
 ▼
ACSE
 │
 ▼
Presentation
 │
 ▼
Session
 │
 ▼
COTP
 │
 ▼
TPKT
 │
 ▼
TCP
 │
 ▼
Port 102
```

The exact protocol exchange contains several layers of connection establishment before MMS services can be exchanged.

The research therefore treats:

```text
TCP Connection
      ↓
COTP Connection
      ↓
Session / Presentation
      ↓
ACSE Association
      ↓
MMS
```

as distinct stages rather than treating TCP/102 as equivalent to an established MMS association.

---

# 11. MMS Namespace & Services

Once an MMS association exists, the client can interact with the server's information model through MMS services.

The research-relevant services include:

```text
GetNameList
      │
      ▼
Namespace Enumeration

Read / Write
      │
      ▼
Data Access

Reports
      │
      ▼
Event / Dataset Reporting

Control
      │
      ▼
Process Interaction

File Services
      │
      ▼
FileOpen / FileRead / FileWrite
```

`GetNameList` is particularly important during reconnaissance because it can expose the server's object namespace.

Conceptually:

```text
MMS Association
       │
       ▼
GetNameList
       │
       ▼
Logical Devices
       │
       ▼
Objects / Variables
       │
       ▼
Data Model
```

This creates a direct relationship between network-level enumeration and the semantic information model established earlier.

---

# 12. MMS Reporting

MMS communication is not limited to request/response operations. IEC 61850 can use reporting mechanisms to transmit changes associated with configured DataSets.

The architectural relationship is:

```text
DataSet
   │
   ▼
Report Control Block
   │
   ▼
MMS Reporting
   │
   ▼
SCADA / Client
```

This allows a client to receive relevant process changes without repeatedly polling every individual attribute.

For the research, this provides another example of the relationship between:

```text
Information Model
       ↓
DataSet
       ↓
Control Block
       ↓
Network Service
```

---

# 13. MMS Control Model

IEC 61850 provides control models for process-affecting operations.

A simplified control architecture is:

```text
Control Object
      │
      ├── Direct Operate
      │
      └── Select-Before-Operate
             │
             ├── Select
             │
             └── Operate
```

For example, a Logical Node representing a circuit breaker may expose control-related objects through the `CO` functional constraint. Select-Before-Operate can introduce an additional operational sequence, but it should not automatically be interpreted as an identity or authorization mechanism. The research therefore tests what the implementation actually enforces rather than assuming that the presence of an SBO-capable control model provides security by itself.

---

# 14. MMS File Services

MMS can also provide file services.

Relevant operations for the research include:

```text
FileOpen
FileRead
FileWrite
```

This creates an additional attack surface separate from process-object manipulation.

Conceptually:

```text
MMS Association
      │
      ├── Information Model
      │
      └── File Services
             │
             ├── Configuration
             ├── Records
             └── Other exposed files
```

Whether these services are enabled, restricted, or exposed depends on the implementation and deployment. The research therefore treats file access as an implementation behavior to be tested rather than assuming that every IEC 61850 device exposes a general filesystem.

---

# 15. GOOSE Process-Bus Architecture

**Generic Object Oriented Substation Event (GOOSE)** provides fast peer-to-peer event and state communication. Unlike MMS, GOOSE does not depend on TCP/IP.

A simplified path is:

```text
Data Model
     ↓
DataSet
     ↓
GOOSE Control Block
     ↓
Ethernet
     ↓
Multicast
     ↓
Subscriber IEDs
```

A simplified Ethernet structure is:

```text
+-------------+---------+---------+----------------+
| Ethernet    | 802.1Q  | GOOSE   | GOOSE Payload  |
| Header      | VLAN    | Header  |                |
+-------------+---------+---------+----------------+
```

GOOSE uses EtherType:

```text
0x88B8
```

The communication is normally multicast at Layer 2.

---

# 16. GOOSE Publisher / Subscriber Model

GOOSE follows a publisher/subscriber model rather than a TCP client/server model.

```text
                  Publisher IED
                       │
                       ▼
                    DataSet
                       │
                       ▼
                GOOSE Control Block
                       │
                       ▼
                 Ethernet Multicast
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
          IED A      IED B      IED C
        Subscriber Subscriber Subscriber
```

The subscriber does not need to establish a TCP connection to the publisher.

This creates a fundamentally different trust boundary:

```text
MMS
Client → TCP Connection → Server

GOOSE
Publisher → Layer-2 Multicast → Subscribers
```

This distinction becomes central when testing spoofed or injected GOOSE traffic.

---

# 17. GOOSE State & Sequence Mechanics

GOOSE carries state and sequence information that allows subscribers to distinguish a newly changed state from repeated retransmissions.

The principal values relevant to the research are:

```text
stNum
 │
 └── State Number

sqNum
 │
 └── Sequence Number

TAL
 │
 └── Time Allowed to Live
```

A simplified steady-state sequence can be represented as:

```text
stNum = 10
sqNum = 0
      │
      ▼
stNum = 10
sqNum = 1
      │
      ▼
stNum = 10
sqNum = 2
      │
      ▼
       ...
```

Following a state change:

```text
Previous State
stNum = 10
      │
      │ State Change
      ▼
New State
stNum = 11
sqNum = 0
      │
      ▼
Rapid Retransmission
sqNum = 1
      │
      ▼
sqNum = 2
      │
      ▼
...
```

The exact retransmission behavior is implementation- and configuration-dependent, but the security-relevant distinction is:

```text
stNum
→ identifies state progression

sqNum
→ identifies message progression within that state
```

This provides the baseline required for the later sequence-manipulation experiments.

---

# 18. Ethernet, VLAN & APPID Boundaries

Because GOOSE and SV operate directly over Ethernet, Layer-2 fields become part of the communication context.

A simplified GOOSE path is:

```text
Destination MAC
       ↓
Ethernet
       ↓
802.1Q VLAN / PCP
       ↓
EtherType 0x88B8
       ↓
APPID
       ↓
GOOSE Payload
```

SV follows the equivalent architecture:

```text
Destination MAC
       ↓
Ethernet
       ↓
802.1Q VLAN / PCP
       ↓
EtherType 0x88BA
       ↓
APPID
       ↓
SV Payload
```

The **APPID**, VLAN configuration, destination MAC, and other frame characteristics can therefore become part of the subscriber's filtering and processing context.

This produces an important research question: "What fields does a subscriber actually use when deciding whether a received Layer-2 frame belongs to an expected publisher or communication stream?" That question is important for the security research than simply identifying the EtherType.

# 19. Sampled Values Architecture

**Sampled Values (SV)** provide continuous transmission of digitized measurements, commonly originating from instrument transformers and Merging Units.

The conceptual path is:

```text
CT / VT
  │
  ▼
Merging Unit
  │
  ▼
Sampling
  │
  ▼
Sampled Value Stream
  │
  ▼
Ethernet Multicast
  │
  ▼
Protection / Measurement IED
```

SV uses EtherType:

```text
0x88BA
```

Like GOOSE, SV operates directly at Layer 2 rather than through TCP/IP.

However, the communication semantics are different:

```text
GOOSE
→ Event / state-oriented messaging

SV
→ Continuous sampled measurement stream
```

---

## 19.1 SV Sample Model

A sampled stream can contain measurements associated with multiple channels.

Conceptually:

```text
Sample
 │
 ├── Current A
 ├── Current B
 ├── Current C
 ├── Voltage A
 ├── Voltage B
 └── Voltage C
```

The receiving device interprets the samples according to the configured stream and expected data model. Consequently, modifying the contents of an SV stream can affect how a subscriber interprets the electrical process.

This provides the architectural foundation for later experiments involving:

* Sample sequence manipulation
* Measurement modification
* Invalid or unexpected values
* Phase relationships
* Frequency changes
* Quality or validity interpretation

# 20. GOOSE and SV Security Boundary

GOOSE and SV share several architectural properties:

```text
No TCP Connection
No IP Transport
Layer-2 Delivery
Multicast Communication
Time-Critical Processing
```

Their security boundary can therefore be represented as:

```text
Ethernet Segment
       │
       ├── Legitimate Publisher
       │
       ├── Legitimate Subscriber
       │
       └── Potentially Rogue Transmitter
```

This is fundamentally different from a conventional TCP service where the server can distinguish connection endpoints through the transport layer.

The security research therefore evaluates whether subscribers adequately distinguish:

```text
Expected Publisher
       vs.
Injected / Spoofed Traffic
```

# 21. Configuration-to-Wire Relationship

One of the most important architectural relationships for this research is that IEC 61850 configuration and runtime communication are not independent.

The complete chain can be represented as:

```text
                  SCL
                   │
                   ▼
            Information Model
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
     DataSet              Communication
        │                   Binding
        │                     │
        ▼                     ▼
 Control Block          Network Parameters
        │                     │
   ┌────┼─────┐               │
   ▼    ▼     ▼               ▼
 MMS  GOOSE   SV          Ethernet / TCP
```

This relationship explains why the research begins with SCL before moving into network traffic.

An incorrectly configured or maliciously modified engineering artifact can potentially influence:

```text
Logical Names
DataSets
Control Blocks
Communication Relationships
Network Bindings
```

The later packet-level behavior therefore cannot always be understood independently from the configuration that created it.

# 22. Security Architecture Baseline

Native IEC 61850 communication mechanisms establish communication semantics, information modeling, and process interaction. They should not automatically be interpreted as providing complete cryptographic security.

The research baseline is therefore:

```text
                  IEC 61850
                     │
        ┌────────────┼────────────┐
        │            │            │
       SCL          MMS        GOOSE / SV
        │            │            │
        ▼            ▼            ▼
 Configuration    TCP/IP       Layer 2
    Trust          Trust         Trust
        │            │            │
        └────────────┼────────────┘
                     ▼
             Security Mechanisms
```


The absence of a cryptographic control in a particular communication path should therefore be documented as an architectural property, while the actual impact must be established through implementation testing and deployment context.

# Security Characteristics

IEC 61850 is best understood as a **substation information and communication architecture**, not a single protocol.


The key architectural characteristics established for the research are:

* **SCL provides the engineering configuration model** from which IED capabilities, logical models, datasets, and communication relationships can be represented.
* **The IEC 61850 information model is hierarchical**, progressing from IED/server structures through Logical Devices, Logical Nodes, Data Objects, Common Data Classes, and Data Attributes.
* **Functional Constraints provide semantic context** for Data Attributes and should not be treated as a standalone authorization mechanism.
* **DataSets and Control Blocks connect the information model to communication services.**
* **MMS provides connection-oriented client/server access** to the information model, including namespace enumeration, data access, reporting, control, and file services.
* **GOOSE provides Layer-2 publisher/subscriber communication** for time-critical state and event distribution.
* **SV provides Layer-2 sampled measurement streams** between Merging Units and subscribers.
* **GOOSE and SV do not depend on TCP/IP**, creating a fundamentally different trust boundary from MMS.
* **GOOSE state and sequence fields**, including `stNum`, `sqNum`, and timing information, provide the baseline for evaluating subscriber state tracking.
* **Ethernet fields such as destination MAC, VLAN/PCP, EtherType, and APPID** form part of the process-bus communication context.
* **Configuration and runtime traffic are connected** through DataSets, Control Blocks, and communication bindings.



The subsequent research can therefore move from **what the substation is configured to be**, to **what its services expose**, and finally to **what its process-bus subscribers actually trust**.
