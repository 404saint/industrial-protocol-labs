# Phase 6: Secure Extension Contrast — IEC 62351 Profiles

## 1. Executive Summary

The first five phases of this research established the security characteristics of an unsecured IEC 61850 environment through direct protocol experimentation.

The research observed an SCL configuration trust boundary during engineering, unauthenticated MMS association and namespace enumeration over TCP/102, unauthorized control operations through the ACSI control model, and unauthenticated Layer 2 GOOSE/SV traffic that could be constructed and injected onto the process bus.

Phase 6 does not repeat those experiments. Instead, it maps the previously observed attack surfaces against the security mechanisms defined by the IEC 62351 family. The objective is to establish where cryptographic protection, access control, and authenticated process-bus communication change the baseline security model.

IEC 62351 is not a single security mechanism applied uniformly across IEC 61850. Different parts address different communication and authorization boundaries. IEC 62351-3 provides a profiled TLS security mechanism for TCP/IP-based communication, IEC 62351-6 addresses security for IEC 61850 protocols including MMS and the peer-to-peer GOOSE/SV profiles, while IEC 62351-8 establishes role-based access control for power-system management.

The result is a layered security model rather than a single control:

```text
                    IEC 61850 SECURITY MODEL
                              │
             ┌────────────────┼────────────────┐
             │                │                │
             ▼                ▼                ▼
       Engineering       Station Bus      Process Bus
             │                │                │
             │                │                │
          SCL / CID        MMS / TCP       GOOSE / SV
             │                │                │
             │             TLS /           Message
             │             Security        Security
             │                │                │
             └────────────┬───┴────────────────┘
                          │
                          ▼
                    Authorization
                         RBAC
                          │
                          ▼
                  Operational Policy
```

The important conclusion is that IEC 62351 does not replace the architectural security boundaries identified earlier. It adds security controls to those boundaries.

# 2. Baseline: What the Earlier Phases Demonstrated

Before examining the security extensions, it is useful to establish the baseline they are intended to change.

| Phase       | Baseline Observation                                                                          | Security Property Missing                              |
| ----------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **Phase 1** | SCL parser processed attacker-controlled XML and resolved external entities                   | Secure configuration ingest                            |
| **Phase 2** | MMS association accepted without client authentication                                        | Communication authentication                           |
| **Phase 2** | `GetNameList` exposed 304 MMS variables                                                       | Authorization / least privilege                        |
| **Phase 3** | ACSI control operations were accepted without authenticated operator identity                 | Command authorization                                  |
| **Phase 3** | File service was disabled on the tested profile                                               | Attack surface reduction through service configuration |
| **Phase 4** | GOOSE/SV operated directly over Ethernet                                                      | Network-layer security boundary absent                 |
| **Phase 5** | Forged GOOSE/SV frames could be constructed with arbitrary source identity and protocol state | Message origin authentication and integrity            |

This produces three security questions:

```text
Can the device communicate?
        │
        ▼
Is the communication authentic?
        │
        ▼
Is the authenticated subject authorized
to perform the requested operation?
```

Encryption alone cannot answer the final question. Likewise, authorization cannot establish that an Ethernet frame actually originated from the expected publisher. The IEC 62351 family addresses these concerns at different layers.

# 3. IEC 62351-3: Protecting TCP/IP Communication

## 3.1 Security Boundary

Phase 2 established the native MMS communication path:

```text
MMS
 │
ISO Presentation
 │
ISO Session
 │
COTP / TPKT
 │
TCP
 │
IPv4
```

The captured traffic was readable at the application layer because the TCP connection provided transport but not cryptographic protection.

IEC 62351-3 addresses TCP/IP-based power-system communication by defining a TLS profile intended to provide security between communicating endpoints. The current 2023 edition is self-contained in its definition of the TLS profile, rather than requiring a separate document to define the TLS parameters.

The resulting model becomes:

```text
MMS
 │
ISO Presentation / Session
 │
COTP / TPKT
 │
TLS
 │
TCP
 │
IP
```

The important change is the introduction of a cryptographic boundary between the communicating endpoints.

---

## 3.2 Confidentiality

In Phase 2, MMS requests and responses were available for direct inspection.

A `GetNameList` request therefore exposed the target's internal namespace to anyone capable of establishing the connection.

With TLS protection, the MMS payload is carried inside the protected TLS session rather than being exposed directly on the network. This addresses passive observation of MMS traffic.

An observer positioned between the control center and IED can still identify that a TCP/TLS connection exists, but cannot simply decode the MMS service requests and responses from the captured transport stream.

---

## 3.3 Integrity

Phase 2 also established that the MMS session operated without a cryptographic integrity boundary.

TLS adds authenticated cryptographic protection to the communication channel. Consequently, an intermediary cannot simply modify an MMS request in transit and have that modification accepted as an authentic message from the communicating endpoint.

This directly changes the threat model surrounding operations such as:

```text
GetNameList
Read
Write
Control
File services
```

The protection is applied to the communication channel rather than to the IEC 61850 object itself.

---

## 3.4 Endpoint Authentication

Confidentiality alone does not establish who is communicating. The TLS profile therefore has an important role in endpoint authentication and certificate validation. This matters directly to the Phase 2 finding.

The original observation was:

```text
Unauthenticated client
        │
        ▼
TCP/102
        │
        ▼
MMS Association
        │
        ▼
Namespace Enumeration
```

The secured model introduces cryptographic identity verification before protected application communication is trusted.

The security question therefore is:

> "Can this endpoint establish a valid authenticated security relationship with the IED?"

This is a substantially stronger boundary than relying on network reachability alone.

# 4. IEC 62351-6: Security for IEC 61850 Communication

IEC 62351-6 is specifically concerned with securing protocols based on or derived from IEC 61850. Its scope includes IEC 61850 mappings to MMS and Ethernet-based profiles including Sampled Values, making it particularly relevant to the station-bus and process-bus findings from this research. This makes Phase 5 especially important.

The process bus cannot simply be protected by putting GOOSE and SV inside TLS because those protocols do not use TCP as their transport. The security mechanism therefore has to operate at the communication profile itself.

---

## 4.1 GOOSE Security

Phase 5 demonstrated that a GOOSE frame could be constructed with:

```text
Source MAC: de:ad:be:ef:ff:ff
EtherType: 0x88B8
stNum:      9999
sqNum:      0
```

The Ethernet frame therefore carried an application-level state transition without providing a cryptographic proof that the message originated from the legitimate publisher.

IEC 62351-6 addresses security for IEC 61850 peer-to-peer profiles, including GOOSE. The security mechanisms are designed to provide cryptographic protection for these messages rather than relying exclusively on Ethernet addressing or network segmentation.

This changes the trust relationship to:


```text
Correct protocol structure
        +
Valid security parameters
        +
Cryptographic verification
        =
Authenticated message
```

The critical improvement is that protocol fields such as state and sequence information are no longer trusted solely because they arrived in a structurally valid Ethernet frame.

---

## 4.2 Sampled Values Security

The same architectural problem exists for Sampled Values.

Phase 5 demonstrated the ability to inject an SV frame using:

```text
EtherType: 0x88BA
Source MAC: de:ad:be:ef:ff:ff
Dataset: MU01_Voltage
```

Because SV operates directly over Ethernet, traditional TCP security mechanisms do not apply. IEC 62351-6 therefore provides the relevant security framework for IEC 61850 peer-to-peer profiles, including Sampled Values.

This is important because SV is not simply carrying ordinary telemetry. A compromised or spoofed publisher can influence the measurements from which protection and monitoring functions derive electrical state. The security objective is therefore not merely confidentiality. For process-bus traffic, **authenticity and integrity are central properties**.

---

# 5. IEC 62351-8: Authorization and Least Privilege

The Phase 3 findings reveal a problem that transport encryption cannot solve.

The laboratory demonstrated that an unauthenticated client could reach the ACSI control interface and successfully invoke control operations:

```text
simpleIOGenericIO/GGIO1.SPCSO1
        │
        ├── True  → Accepted
        └── False → Accepted
```

Even if MMS communication is protected with TLS, the following question remains:

> What is the authenticated subject actually allowed to do?

IEC 62351-8 addresses this problem through role-based access control.

The standard defines RBAC (Role Based Access Controls) around subjects, roles, and rights, with the objective of restricting access to only the resources required by a subject's assigned role. It explicitly applies to human users as well as automated systems and software applications.

Conceptually:

```text
Subject
   │
   ▼
Assigned Role
   │
   ▼
Permissions / Rights
   │
   ▼
IEC 61850 Object or Operation
```

This changes the authorization model from:

```text
Can connect?
     │
     └── Yes → Can attempt operation
```

to:

```text
Can connect?
     │
     ▼
Who are you?
     │
     ▼
What role do you have?
     │
     ▼
Does that role permit this operation?
     │
     ├── Yes → Execute
     └── No  → Reject
```

This directly addresses the authorization problem exposed during Phase 3.

---

# 6. RBAC and the IEC 61850 Object Model

The relationship between RBAC and the IEC 61850 object model is particularly relevant to this research because Phase 2 mapped the internal hierarchy of the IED:

```text
Logical Device
    │
    └── Logical Node
          │
          └── Data Object
                │
                └── Data Attribute
```

Access control can then be considered in terms of the resources and operations associated with those objects.

For example, a monitoring role might require:

```text
Read:
  GGIO1$ST
  GGIO1$MX
```

while a protection-control role might additionally require specific control operations.

The goal is not to make every authenticated subject a super-user. IEC 62351-8 explicitly frames RBAC around least privilege and restricting subjects to resources required for their roles.

There is also a current IEC 61850-specific development worth noting: **IEC PAS 61850-90-19:2026** applies the RBAC requirements to IEC 61850 and defines how permissions can be associated with IEC 61850 objects through SCL-based identification. It was published on August 20, 2026.

That development is particularly relevant to Phase 1 because it connects authorization policy back to the IEC 61850 engineering and object model rather than treating access control as an entirely separate network mechanism.

# 7. Attack Surface → Security Control Mapping

The complete research can now be summarized as a security-control mapping:

| Research Finding                  | Baseline Weakness                                         | Relevant Security Mechanism                        | Security Property                                |
| --------------------------------- | --------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| **Phase 1: SCL XXE**              | Unsafe XML/configuration processing                       | Secure implementation and configuration management | Parser / engineering security                    |
| **Phase 2: MMS enumeration**      | Unauthenticated namespace discovery                       | IEC 62351-3 + authorization controls               | Confidentiality / authentication / authorization |
| **Phase 3: Control injection**    | Unrestricted control access                               | IEC 62351-8 RBAC + authenticated communication     | Authorization / least privilege                  |
| **Phase 3: File services**        | Exposed service functionality                             | Service minimization + access control              | Attack-surface reduction                         |
| **Phase 5: GOOSE spoofing**       | No cryptographic publisher authentication                 | IEC 62351-6                                        | Message authenticity / integrity                 |
| **Phase 5: `stNum` manipulation** | Protocol state trusted without cryptographic origin proof | IEC 62351-6                                        | Message integrity / authenticity                 |
| **Phase 5: SV injection**         | Unauthenticated Layer 2 measurement source                | IEC 62351-6                                        | Message authenticity / integrity                 |

The table also exposes an important limitation: **No single IEC 62351 part addresses the entire IEC 61850 attack surface.**

The security model is distributed across communication protection, peer-to-peer message security, authorization, key management, logging, and operational controls. The IEC itself describes the 62351 family as covering multiple security technologies and notes that the individual communication standards may reference different security parts according to their requirements.

# 8. What IEC 62351 Does Not Automatically Solve

The security extensions should not be interpreted as a complete elimination of the attack surface identified during this research.

### 8.1 SCL Parser Vulnerabilities

TLS does not protect an `.scd` or `.cid` file from a vulnerable XML parser. The Phase 1 XXE finding occurs during configuration processing, before the protected operational communication channel becomes relevant. A vulnerable parser remains vulnerable unless the implementation itself is hardened.

### 8.2 Compromised Endpoints

Cryptographic authentication establishes trust in keys and credentials. It does not prove that the endpoint itself is free of compromise. A legitimate IED holding valid credentials can still become a security problem if its host environment or engineering process is compromised.

### 8.3 Malicious Configuration

Security mechanisms cannot compensate for an engineering team deliberately or accidentally loading an incorrect SCL configuration. Configuration integrity, change control, validation, and engineering workstation security therefore remain important.

### 8.4 Availability

Encryption and authentication do not prevent every denial-of-service condition. A process-bus attacker may still be able to consume bandwidth, overload switches, interfere with traffic delivery, or otherwise affect availability even when forged messages fail cryptographic verification.

This is particularly important for GOOSE and SV because their operational value depends heavily on deterministic and timely delivery.

### 8.5 Key and Certificate Management

Cryptographic protection introduces another operational dependency: keys, certificates, trust anchors, and their lifecycle must be managed correctly. IEC 62351-9 addresses key-management techniques for selected IEC 62351 security mechanisms, including the group-security context used for GOOSE and SV.

A security architecture that specifies cryptography without maintaining its credentials securely simply moves the trust problem elsewhere.

# 9. The Resulting IEC 61850 Security Model

The research began with an architecture where several critical decisions depended primarily on network location and protocol structure:

```text
Network Access
      │
      ▼
Protocol Association
      │
      ▼
Object Discovery
      │
      ▼
Control / Process Data
```

The security extensions introduce additional trust decisions:

```text
Network Access
      │
      ▼
Cryptographic Authentication
      │
      ▼
Protected Communication
      │
      ▼
Authorization / Role Evaluation
      │
      ▼
Object or Service Access
      │
      ▼
Process Operation
```

For GOOSE and SV, the path is different because the traffic does not traverse TCP:

```text
Ethernet Frame
      │
      ▼
Protocol Validation
      │
      ▼
Cryptographic Security Validation
      │
      ▼
Publisher / Message Trust
      │
      ▼
Process-Bus Application
```

This is the fundamental architectural change introduced by the security extensions. The receiver is no longer expected to trust a message merely because it arrived on the expected network and conforms to the expected protocol structure.

---

# 10. Final Findings

The IEC 61850 research began with an unsecured communication model and progressively examined its trust boundaries.

The laboratory demonstrated that:

1. SCL can become a high-value engineering trust boundary when configuration input is processed unsafely.
2. MMS can expose the internal IEC 61850 object namespace when application associations are not protected by authentication and authorization.
3. ACSI control operations can become high-impact attack paths when authorization is absent.
4. GOOSE and SV operate outside the TCP/IP security mechanisms used for MMS and therefore require security mechanisms appropriate to their Layer 2 communication model.
5. Protocol fields such as GOOSE state and sequence values should not be treated as cryptographic proof of message origin.

IEC 62351 provides security mechanisms that address different portions of this architecture.

**IEC 62351-3** introduces a profiled TLS security mechanism for TCP/IP-based communication, providing the cryptographic channel required to protect communication between endpoints.

**IEC 62351-6** addresses security for IEC 61850 communication profiles, including the MMS and peer-to-peer GOOSE/SV environments examined during this research.

**IEC 62351-8** introduces role-based authorization based on subjects, roles, and rights, providing the least-privilege model required to answer a question that encryption alone cannot answer: **what is an authenticated subject allowed to do?**

The security model therefore becomes layered rather than dependent on a single control.

```text
                    IEC 61850
                       │
        ┌──────────────┼──────────────┐
        │              │              │
     SCL /          MMS /          GOOSE /
  Engineering     TCP/IP             SV
        │              │              │
        │         62351-3         62351-6
        │              │              │
        └──────────────┼──────────────┘
                       │
                    62351-8
                  Authorization
                       │
                       ▼
                Least Privilege
```

The most important conclusion from the complete research is therefore not that IEC 61850 is inherently insecure, nor that IEC 62351 simply "fixes" the protocol. The more accurate conclusion is that **IEC 61850's operational architecture creates multiple security boundaries, and those boundaries require different security controls**. The unsecured laboratory established what happens when those boundaries rely primarily on protocol structure, network reachability, and device configuration.

The IEC 62351 family provides the mechanisms for introducing cryptographic authentication, communication integrity, confidentiality, peer-to-peer message security, and role-based authorization into those boundaries. The remaining security posture depends on how correctly those mechanisms are implemented, configured, and operated.

---

## Phase 6 Methodology Note

Unlike Phases 1–5, this phase was intentionally conducted as a specification-driven analysis rather than another exploitation exercise.

The laboratory work had already established the unsecured baseline empirically. Repeating those attacks against a partially implemented security profile would primarily demonstrate the behavior of one particular library or configuration rather than establish the requirements of the IEC security architecture.

The purpose of this phase was therefore to take the observed findings and ask a narrower question:

> **Which security mechanisms are intended to protect each trust boundary identified during the research?**

That keeps the empirical and specification-driven portions of the research separate while allowing the final security assessment to connect them.
