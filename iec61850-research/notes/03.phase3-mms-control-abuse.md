# Phase 3: MMS Unauthenticated Control & File Transfer Abuse

* **Target IED:** `192.168.1.10:102`
* **Implementation:** `libiec61850` soft-IED
* **Protocol Layer:** MMS / ACSI over ISO-on-TCP
* **Objective:** Examine whether an unauthenticated MMS association can access writable process objects, invoke ACSI control operations, alter process state, and reach the MMS file-service subsystem.

---

## Executive Summary

Phase 3 examined the transition from **namespace visibility** into actual process interaction.

Following the unauthenticated MMS association and object enumeration established in Phase 2, the client tested two different paths to process control. The first used direct MMS variable writes against exposed control attributes. These operations were refused by the target, demonstrating that the server's native data-typing and object-access constraints still applied at the bare MMS variable-write layer.

The second path used the `ControlObjectClient` ACSI interface against the same control objects. These operations were accepted without an authentication or authorization exchange, demonstrating a significantly different security boundary between **raw MMS variable access** and **properly modeled IEC 61850 control services**.

The resulting state verification confirmed that the control operations reached the target process model and affected the corresponding status points.

MMS file-service testing produced a different result. The target refused a `fileDirectory` request for the root path with MMS error `99`. Investigation of the `libiec61850` deployment showed that MMS file services are not automatically enabled with the IED data model and require explicit server-side file-service configuration. Consequently, this phase did **not** demonstrate remote file-system access or file exfiltration against the tested profile.

The primary security finding is therefore not that every MMS operation is universally unrestricted. Rather, it is that **an unauthenticated client can reach an exposed ACSI control interface and invoke modeled control operations despite the refusal of equivalent raw MMS writes**.

---

# 1. Control-Access Architecture

IEC 61850 separates the conceptual control model from the underlying MMS transport.

The relevant path in this phase can be represented as:

```text
                    TCP/102
                       │
                       ▼
              ISO-on-TCP / COTP
                       │
                       ▼
                    MMS
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
      Variable Access        ACSI Services
       Read / Write       ControlObjectClient
             │                   │
             │                   ▼
             │              Control Object
             │                   │
             └─────────────► Process Model
```



The same control object may be visible through the MMS namespace while the server applies different validation behavior depending on whether the client accesses the underlying variable directly or invokes the IEC 61850 control service through the ACSI abstraction.

The research therefore treated these as separate attack paths rather than assuming that successful namespace enumeration automatically implies arbitrary MMS writes.

---

# 2. Direct MMS Variable Write Testing

The first test attempted to manipulate control attributes through direct MMS variable access.

The target objects included:

```text
GGIO1$CO$SPCSO1$Oper$ctlVal
GGIO1$CO$SPCSO2$Oper$ctlVal
```

A measured-value attribute was also used as a negative control:

```text
GGIO1$MX$AnIn1$mag$f
```

The test matrix was:

| MMS Variable Path             | Test                        | Result      |
| ----------------------------- | --------------------------- | ----------- |
| `GGIO1$CO$SPCSO1$Oper$ctlVal` | Write `True`                | **REFUSED** |
| `GGIO1$CO$SPCSO1$Oper$ctlVal` | Write `False`               | **REFUSED** |
| `GGIO1$CO$SPCSO2$Oper$ctlVal` | Write `True`                | **REFUSED** |
| `GGIO1$MX$AnIn1$mag$f`        | Write read-only measurement | **REFUSED** |

The control-variable attempts returned:

```text
Code: 3
MMS Error: 83
```

while the read-only measurement test returned:

```text
Code: 7
MMS Error: 33
```

No post-operation state change was observed through this direct MMS path.

This provides an important negative finding:

> **An exposed MMS namespace does not necessarily provide unrestricted raw variable manipulation.**

The target implementation retained constraints around direct variable access even though the client had established an unauthenticated MMS association.

---

# 3. ACSI Control Object Injection

The second test used the IEC 61850 control abstraction rather than attempting to write the underlying MMS variable directly.

The client invoked:

```text
ControlObjectClient_operate
```

against:

```text
simpleIOGenericIO/GGIO1.SPCSO1
simpleIOGenericIO/GGIO1.SPCSO2
```

The observed results were:

| Control Object                   | Command | Operate Result |
| -------------------------------- | ------- | -------------- |
| `simpleIOGenericIO/GGIO1.SPCSO1` | `True`  | **SUCCESS**    |
| `simpleIOGenericIO/GGIO1.SPCSO1` | `False` | **SUCCESS**    |
| `simpleIOGenericIO/GGIO1.SPCSO2` | `True`  | **SUCCESS**    |

The target accepted the control operations through the ACSI interface.

The resulting interaction can be represented as:

```text
Unauthenticated Client
          │
          ▼
       TCP/102
          │
          ▼
      MMS Session
          │
          ▼
    ACSI Control Service
          │
          ▼
      GGIO1.SPCSO1
          │
          ▼
     Process Model
```

No authentication or authorization exchange was observed between the established MMS association and the accepted control operation. This is the principal security finding of Phase 3.

---

# 4. Why the Two Write Paths Behaved Differently

The different results between Sections 2 and 3 are important.

The direct MMS operation attempted to modify:

```text
GGIO1$CO$SPCSO1$Oper$ctlVal
```

as a normal MMS variable.

The ACSI operation instead addressed the modeled control object:

```text
simpleIOGenericIO/GGIO1.SPCSO1
```

through the control-service abstraction.

Conceptually:

```text
Direct MMS Write
      │
      ▼
Underlying Variable
      │
      ▼
Server Access Validation
      │
      └── REFUSED


ACSI Operate
      │
      ▼
Control Object Service
      │
      ▼
Control Logic
      │
      ▼
Process State
      │
      └── ACCEPTED
```

This demonstrates that **MMS object-level access controls and IEC 61850 control-service enforcement are not necessarily equivalent security boundaries**.

For defensive analysis, this is significant because a security assessment that tests only generic MMS `Write` operations could incorrectly conclude that control objects are protected simply because direct writes are rejected.

---

# 5. Process-State Verification

Following the accepted ACSI operations, the client queried the corresponding status attributes using:

```text
IedConnection_readObject
```

with the `ST` functional constraint.

The resulting audit reported:

| Control Object                   | Action      | Injection Status | Observed `stVal` |
| -------------------------------- | ----------- | ---------------- | ---------------- |
| `simpleIOGenericIO/GGIO1.SPCSO1` | Set `True`  | **ACCEPTED**     | `True`           |
| `simpleIOGenericIO/GGIO1.SPCSO1` | Set `False` | **ACCEPTED**     | `True`           |
| `simpleIOGenericIO/GGIO1.SPCSO2` | Set `True`  | **ACCEPTED**     | `True`           |

The important point is that the control requests reached the modeled process-control layer and produced observable state associated with the target control objects.

However, the returned values should be interpreted carefully.

The observed:

```text
Set False → stVal = True
```

does **not** by itself prove that the requested `False` operation failed. The relationship between a control command and a status attribute depends on the particular object model, control semantics, and simulator implementation.

Therefore, the finding can be concluded as:

> **Unauthenticated ACSI control operations were accepted and resulted in observable process-model state changes, while the exact relationship between command value and returned `stVal` remained implementation-specific.**

---

# 6. Select-Before-Operate & Control-State Considerations

IEC 61850 control objects can support different control models, including direct control and Select-Before-Operate (SBO).

The relevant distinction is:

```text
Direct Control

Client
  │
  └── Operate ───────────────► Control Object


Select-Before-Operate

Client
  │
  ├── Select ────────────────► Control Object
  │
  └── Operate ───────────────► Control Object
```

The Phase 3 control test exercised the ACSI `Operate` path directly. This is important because the presence of an SBO-capable object should not automatically be interpreted as an authentication or authorization mechanism. SBO primarily establishes **control sequencing and object-selection semantics**.

It does not inherently provide:

```text
Cryptographic Identity
        +
Authorization
        +
Role Enforcement
```

Consequently, subsequent testing should distinguish between:

* Whether an object requires Select before Operate.
* Whether selection state is bound to a specific association.
* Whether selection expires.
* Whether another client can interfere with an existing selection.
* Whether authorization exists independently of the control model.

# 7. MMS File-Service Attack Surface

The final portion of Phase 3 examined whether the same unauthenticated MMS association could reach the target's file-service subsystem.

The client issued a directory request equivalent to:

```text
fileDirectory("/")
```

The target responded:

```text
REFUSED
MMS Error: 99
```

No remote directory contents were returned and no file-read operation was performed.

The observed boundary was:

```text
Unauthenticated MMS Association
             │
             ▼
       File Directory
             │
             ▼
          REFUSED
```

This result initially appeared inconsistent with the phase objective, but inspection of the target implementation provided an important explanation.

---

# 8. Virtual File-System Binding

In `libiec61850`, MMS file services are not automatically enabled simply because an MMS server and IEC 61850 data model are running.

The file-service subsystem requires explicit server-side configuration, including mechanisms such as:

```text
MmsServer_setFileBasepath()
```

or a server profile specifically configured for MMS file services.

The tested soft-IED profile primarily exposed:

```text
MMS Data Model
        +
ACSI Control Objects
```

while the corresponding MMS virtual file-system interface was not mounted.

Therefore:

```text
TCP/102
   │
   ▼
MMS Association
   │
   ├── Object Model ───────► Available
   │
   ├── ACSI Control ───────► Available
   │
   └── File Service ───────► Not Mounted
```

The refusal of the directory request should therefore be interpreted as an **implementation/deployment configuration boundary**, not evidence that IEC 61850 file services universally reject unauthenticated access.

---

# 9. Attack-Surface Interpretation

The combined results reveal a more useful attack-surface model than simply labeling the MMS endpoint "unauthenticated."

```text
                         TCP/102
                            │
                            ▼
                     MMS Association
                            │
             ┌──────────────┼──────────────┐
             │              │              │
             ▼              ▼              ▼
       Namespace        Variable        File Service
       Enumeration        Write
             │              │              │
          OPEN          RESTRICTED       DISABLED
             │              │              │
             ▼              ▼              ▼
        Reconnaissance   MMS Error       MMS Error
                            │
                            │
                            ▼
                    ACSI Control Path
                            │
                            ▼
                       ACCEPTED
```

The important observation is that **security boundaries existed at different layers**. The server rejected arbitrary direct variable manipulation while still accepting properly structured ACSI control operations from an unauthenticated client. Likewise, the file-service subsystem was unavailable because it was not configured in the tested deployment.

This reinforces a broader principle for IEC 61850 assessments:

> **Security testing must follow the actual service architecture rather than assuming that all MMS-exposed functionality shares the same access-control behavior.**

# 10. Security Assessment

## 10.1 Unauthenticated Control-Service Access

The strongest finding is the successful invocation of ACSI control operations without an observed authentication or authorization exchange.

The tested path was:

```text
Unauthenticated Client
        │
        ▼
MMS Association
        │
        ▼
ACSI Operate
        │
        ▼
GGIO1.SPCSO1 / SPCSO2
        │
        ▼
Process Model
```

This creates a potentially high-impact attack surface where network access to TCP/102 can become sufficient to reach control functionality exposed by the IED.

The practical severity depends on:

* Network segmentation.
* Object control model.
* IED configuration.
* Authorization mechanisms.
* Whether the object represents an actual process actuator.
* Whether IEC 62351 security mechanisms are deployed.

---

## 10.2 Direct MMS Write Restrictions

The refusal of raw MMS writes demonstrates that the tested implementation does enforce some object-level constraints.

This is a useful defensive observation:

```text
Namespace Enumeration
       ≠
Arbitrary Memory / Variable Write
```

The finding should therefore not be generalized into "MMS allows unrestricted writes." Instead, the research demonstrates that **different MMS/ACSI access paths may expose materially different security properties**.

---

## 10.3 File-Service Exposure Depends on Deployment

The file-service test did not demonstrate file-system access.

The tested server returned: `MMS Error 99` when asked to enumerate the root directory.

Because the file-service subsystem was not mounted in this server profile, no `.icd` files, fault records, or other filesystem objects were exposed.

The correct security conclusion is therefore:

> **MMS file transfer represents an additional attack surface when explicitly enabled, but it was not exposed by the tested `libiec61850` deployment profile.**

This is important when translating lab results into real-world assessments.

---

# Security Characteristics

Phase 3 demonstrated that the IEC 61850 attack surface cannot be characterized solely by whether TCP/102 is reachable or whether an MMS association can be established.

The tested implementation exhibited three distinct behaviors:

```text
                         Unauthenticated MMS
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
       Namespace Access    Raw Variable      File Service
                              Write
              │                 │                 │
           Allowed           Refused          Disabled
                                │
                                ▼
                         ACSI Control Path
                                │
                                ▼
                             Allowed
```

The principal findings were:

* Direct MMS writes to tested control and measurement variables were refused.
* Properly modeled ACSI `Operate` requests were accepted without an observed authentication or authorization exchange.
* Subsequent status reads confirmed observable interaction with the target process model.
* SBO semantics should be treated as control sequencing rather than an authentication mechanism.
* MMS file-directory access was refused because the tested `libiec61850` server profile did not expose its virtual file-system service.
* The file-service result is therefore a **deployment-specific boundary**, not evidence of universal IEC 61850 file-service behavior.
