# Phase 5: GOOSE/SV Injection & Edge-Case Anomalies

* **Target:** `br-processbus` / `ns-ied1` / `ns-sub1`
* **Implementation:** `libiec61850`
* **Protocols:** IEC 61850 GOOSE (`0x88B8`) and Sampled Values (`0x88BA`)
* **Objective:** Examine the process bus response surface against forged Layer 2 multicasts, sequence-state manipulation, quality-flag changes, and malformed or anomalous sampled-value payloads.

---

## Executive Summary

Phase 5 moved the research from observing legitimate process-bus traffic to actively constructing anomalous GOOSE and Sampled Values frames.

The process bus operates directly over Ethernet, allowing a test client attached to the `br-processbus` bridge to construct frames without establishing an IP, TCP, or application-layer session. The test harness generated three classes of anomalies:

```text
GOOSE
 │
 ├── stNum / sqNum manipulation
 │
 └── Quality flag manipulation
        │
        ▼
     Subscriber
        │
        └── State / validity evaluation

SV
 │
 └── Sample / frequency anomaly
        │
        ▼
     Subscriber
        │
        └── Measurement processing
```

The first test generated GOOSE frames using a rogue source MAC address and a large `stNum` value. The second modified the encoded quality field. The third generated an SV frame carrying an anomalous sample/frequency representation. The harness successfully transmitted and intercepted all three classes of frames on the process-bus bridge.

The most important architectural observation is that **process-bus traffic can be injected at Layer 2 without first interacting with the MMS session established in earlier phases**. Consequently, controls protecting TCP/102 do not automatically protect GOOSE or SV traffic.

The Phase 5 captures establish the **injection and wire-visibility attack surface**. Where subscriber acceptance or process-state changes are not directly observed, those outcomes are retained as hypotheses for further implementation-specific testing rather than presented as confirmed effects.

# 1. Process Bus Attack Surface

GOOSE and SV use Ethernet directly rather than relying on the TCP/IP stack used by MMS.

The simplified communication path is:

```text
                  Station Bus
                       │
                       │ MMS / TCP
                       ▼
                    IED
                       │
                       │
              ┌────────┴────────┐
              │   Process Bus   │
              └────────┬────────┘
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         ▼
      GOOSE 0x88B8              SV 0x88BA
          │                         │
          ▼                         ▼
   Protection / Control       Measurement /
       Subscribers             Protection
```

An attacker positioned on the relevant Layer 2 segment can therefore interact with process-bus traffic without performing the MMS association and namespace enumeration demonstrated in Phase 2.

The security boundary is consequently different:

```text
MMS Attack Surface
TCP
 │
 ▼
COTP / Session / ACSE
 │
 ▼
MMS
 │
 ▼
IEC 61850 Object Model


Process Bus Attack Surface
Ethernet
 │
 ├── GOOSE
 │
 └── SV
```

This makes process-bus segmentation and Layer 2 traffic controls important components of the overall IEC 61850 security architecture.

# 2. GOOSE Frame Structure

The Phase 5 GOOSE tests targeted EtherType:

```text
0x88B8
```

The process-bus Ethernet frame can be represented conceptually as:

```text
+---------------------------+
| Ethernet Header           |
|                           |
| Destination MAC           |
| Source MAC                |
| Optional 802.1Q VLAN      |
| EtherType = 0x88B8       |
+---------------------------+
| GOOSE Header / PDU        |
+---------------------------+
| Dataset Values            |
+---------------------------+
```

The GOOSE payload uses ASN.1 BER encoding for its protocol fields and dataset representation.

Relevant state fields include:

```text
gocbRef
timeAllowedToLive
datSet
goID
t
stNum
sqNum
test
confRev
ndsCom
numDatSetEntries
```

The Phase 5 harness focused specifically on:

```text
stNum
sqNum
q
```

These fields are important because they influence how a subscriber interprets publisher state and the validity of the associated process information.

# 3. GOOSE State Numbers & Sequence Numbers

GOOSE uses two sequence-related values:

```text
stNum → State Number
sqNum → Sequence Number
```

A simplified publisher cycle can be represented as:

```text
Normal State
    │
    ├── stNum = 1
    │
    ├── sqNum = 0
    │
    ├── sqNum = 1
    │
    ├── sqNum = 2
    │
    └── ...
             │
             │ Event
             ▼
       New State Number
             │
        stNum = 2
             │
        sqNum = 0
             │
             ├── 1
             ├── 2
             └── ...
```

The state number identifies a publisher state change, while the sequence number advances within that state.

This provides subscribers with information that can be used to determine whether an incoming frame represents:

* A new publisher state
* Another transmission of the current state
* An older state
* An unexpected sequence transition

The protocol fields therefore provide state information, but the Phase 5 research specifically examines what happens when those values are supplied by an **unauthorized Ethernet sender**.

# 4. Test 5.1: `stNum` Poisoning

The first injection generated a GOOSE frame with:

```text
EtherType:
    0x88B8

Source MAC:
    de:ad:be:ef:ff:ff

Destination MAC:
    01:0c:cd:01:00:01

stNum:
    9999

sqNum:
    9999
```

The relevant encoded payload began:

```text
61 81 00 80
02 27 0f
84 02 27 0f
85 01 00
...
```

The `02 27 0f` sequence represents the encoded value `9999`.

The harness transmitted the frame repeatedly and observed it on the process-bus interface:

```text
[!] Injecting stNum Poisoning (Massive sequence jump)

EtherType              0x88B8
Source MAC             de:ad:be:ef:ff:ff
Destination MAC        01:0c:cd:01:00:01
Status                 Anomaly Injected / Monitored
```

The source MAC deliberately identifies the sender as a rogue endpoint rather than the legitimate publisher used by the lab.

### Security Question

The test is designed to determine whether a subscriber treats the incoming state as valid based primarily on protocol fields:

```text
Incoming GOOSE
      │
      ├── Valid BER structure
      ├── Expected destination
      ├── Large stNum
      └── Unauthorized source
             │
             ▼
       Subscriber decision
```

A robust deployment should ensure that protocol-valid traffic originating from an unauthorized process-bus endpoint cannot influence protection or control logic.

The Phase 5 capture establishes that the forged state information can be placed directly onto the Layer 2 communication path. Whether a particular subscriber accepts or acts upon that state remains implementation-dependent and must be verified from subscriber telemetry or process-state changes.

# 5. Test 5.2: Quality Flag Manipulation

The second GOOSE injection modified the encoded quality field.

The harness transmitted:

```text
EtherType:
    0x88B8

Source MAC:
    de:ad:be:ef:ff:ff

Destination MAC:
    01:0c:cd:01:00:01
```

The relevant payload began:

```text
61 81 00 80
02 00 02
87 01 03
...
```

The test targeted quality information represented in the GOOSE dataset.

Quality information can communicate conditions such as:

```text
Good
Invalid
Questionable
Test
```

The security relevance comes from the fact that an IED may use quality information when deciding whether a received process value should participate in protection, control, alarming, or fallback logic.

The conceptual processing path is:

```text
GOOSE Dataset
      │
      ▼
Process Value + Quality
      │
      ▼
Subscriber Logic
      │
      ├── Accept
      ├── Ignore
      ├── Alarm
      └── Enter fallback behavior
```

A forged quality state can therefore become operationally significant even when the underlying value itself has not been changed. As with the `stNum` test, the capture demonstrates successful construction and transmission of the manipulated frame. It does not independently demonstrate that the subscriber altered its internal process state in response.

# 6. Test 5.3: Sampled Values Anomaly

The third test targeted Sampled Values using:

```text
EtherType:
    0x88BA

Source MAC:
    de:ad:be:ef:ff:ff

Destination MAC:
    01:0c:cd:01:00:01
```

The injected payload began:

```text
60 81 10 80
08 4d 55 30 31 5f 56 6f 6c 74 61 67 65
82 02 05 dc
...
```

The test harness identified the payload as an SV frequency/sample anomaly targeting:

```text
MU01_Voltage
```

Sampled Values are fundamentally different from GOOSE in their operational purpose.

GOOSE communicates event-driven state:

```text
Breaker Trip
Interlock
Protection State
Binary Status
```

SV continuously transports sampled measurement data:

```text
Current
Voltage
Phase Information
Sample Counters
```

A simplified SV path is:

```text
Merging Unit
     │
     │ sampled electrical quantities
     ▼
SV Ethernet Stream
     │
     ▼
Protection / Measurement IED
     │
     ▼
Measurement Processing
     │
     ├── RMS
     ├── Frequency
     ├── Phase
     └── Protection Algorithms
```

Consequently, malformed or manipulated samples can potentially affect calculations downstream of the network parser. The Phase 5 test provides the wire-level injection mechanism. Actual impact depends on how the receiving implementation validates sample counters, sample rates, dataset lengths, and measurement ranges.

# 7. Rogue Source MAC Address

All Phase 5 injections used:

```text
Source:
    de:ad:be:ef:ff:ff
```

while targeting the GOOSE multicast destination:

```text
01:0c:cd:01:00:01
```

This deliberately separates **Ethernet-level sender identity** from the protocol payload.

The resulting packet structure is conceptually:

```text
Ethernet
 ├── Source = Rogue MAC
 ├── Destination = GOOSE multicast
 └── EtherType = 0x88B8
             │
             ▼
          GOOSE PDU
             │
             ├── stNum
             ├── sqNum
             ├── Quality
             └── Dataset
```

This is useful for detection engineering because a defender does not necessarily need to decode every dataset value to identify suspicious traffic.

A process-bus monitoring system can correlate:

```text
Source MAC
     +
EtherType
     +
Destination MAC
     +
GOOSE control block
     +
stNum / sqNum behavior
```

to identify traffic that does not match the expected publisher profile.

# 8. State-Sequence Monitoring

The sequence fields provide an additional detection opportunity.

A subscriber or network sensor can establish a baseline:

```text
Expected Publisher
        │
        ▼
stNum progression
        │
        ├── State changes
        │
        └── sqNum progression
```

Anomalies may include:

```text
Unexpected stNum jump
Unexpected source MAC
Repeated state number
Unexpected sequence reset
Abnormally high transmission rate
Unexpected dataset identity
```

A simplified monitoring model is:

```text
Observed GOOSE
       │
       ▼
Identify Publisher
       │
       ▼
Validate Expected Control Block
       │
       ▼
Track stNum / sqNum
       │
       ├── Expected → Continue
       │
       └── Anomalous → Alert
```

This approach does not replace cryptographic protection. It provides a detection layer for environments where process-bus availability and legacy compatibility make additional controls necessary.

# 9. Injection Results

The Phase 5 harness produced three reproducible anomaly classes.

| Test    | Protocol | Mutation                       | Source    | Result                      |
| ------- | -------- | ------------------------------ | --------- | --------------------------- |
| **5.1** | GOOSE    | `stNum` / `sqNum` manipulation | Rogue MAC | Frame injected and observed |
| **5.2** | GOOSE    | Quality-field manipulation     | Rogue MAC | Frame injected and observed |
| **5.3** | SV       | Sample / frequency anomaly     | Rogue MAC | Frame injected and observed |

The captured traffic confirms that the process-bus test environment permits a Layer 2 endpoint to construct and transmit protocol-shaped GOOSE and SV traffic without first establishing an MMS session. This is the principal result of the phase.

Subscriber-side acceptance requires a separate measurement of the receiving implementation. In particular, a complete validation would correlate the injected frame with:

```text
Injected Frame
      │
      ▼
Subscriber Reception
      │
      ▼
Internal Dataset Update
      │
      ▼
Process State / Protection Logic
```

That correlation is deliberately kept separate from the packet-injection result.

# 10. Security Assessment

## 10.1 Layer 2 Reachability Matters

MMS access controls do not automatically constrain GOOSE or SV.

An architecture may therefore have:

```text
Protected MMS
     │
     ▼
TCP/102
```

while still exposing:

```text
Process Bus
     │
     ├── GOOSE
     └── SV
```

to unauthorized Layer 2 traffic.

Process-bus security must therefore be evaluated independently from station-bus security.

---

## 10.2 Protocol Validity Is Not Publisher Identity

A forged frame can contain syntactically valid protocol fields while originating from an unauthorized Ethernet sender.

The security problem can therefore be expressed as:

```text
Valid GOOSE/SV Encoding
          ≠
Authorized Publisher
```

Likewise:

```text
Valid stNum / sqNum
          ≠
Trusted State Transition
```

and:

```text
Valid Measurement Encoding
          ≠
Trusted Measurement Source
```

The receiving implementation must therefore be evaluated for both protocol parsing and source/trust enforcement.

---

## 10.3 Process-Bus Segmentation

Because GOOSE and SV operate directly at Layer 2, network architecture becomes an important security control.

Relevant controls include:

* Dedicated process-bus VLANs
* Strict switch port assignment
* MAC-level filtering where supported
* Port security
* Controlled access to process-bus bridges
* Monitoring of unexpected GOOSE/SV publishers
* Isolation of engineering and maintenance hosts from protection networks

The goal is to reduce the number of systems capable of physically or virtually placing arbitrary Ethernet frames onto the process bus.

# Security Characteristics

Phase 5 demonstrated the Layer 2 injection surface surrounding IEC 61850 process-bus traffic.

The test environment successfully generated:

```text
GOOSE
 │
 ├── stNum / sqNum manipulation
 └── Quality-field manipulation

SV
 │
 └── Sample / frequency anomaly
```

using a rogue Ethernet source:

```text
de:ad:be:ef:ff:ff
```

The key architectural observation is that these frames can be placed directly onto the process bus without traversing the MMS association established during Phase 2.

The phase therefore establishes three important security characteristics:

1. **GOOSE and SV require independent security analysis from MMS.**
2. **Layer 2 access to the process bus creates an injection opportunity independent of TCP/102 authentication.**
3. **Protocol-valid frames should not automatically be treated as trusted publisher traffic.**

The current captures establish successful frame construction, transmission, and interception. Subscriber acceptance, internal state modification, or protection-operation consequences require direct observation from the receiving IED and should be treated as implementation-specific findings when demonstrated.

The resulting attack surface can be summarized as:

```text
                 IEC 61850 Process Bus
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
        GOOSE 0x88B8               SV 0x88BA
             │                         │
             ▼                         ▼
      State / Control             Measurements
             │                         │
             └────────────┬────────────┘
                          │
                    Layer 2 Trust
                          │
             ┌────────────┴────────────┐
             │                         │
        Authorized                  Rogue
        Publisher                   Sender
             │                         │
             ▼                         ▼
       Expected State             Anomalous
                                  State / Data
```

Phase 6 examinines the IEC 62351 security profiles and comparing their protection mechanisms against the attack surfaces identified throughout Phases 1–5.
