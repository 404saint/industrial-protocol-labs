# Phase 2: Plaintext MMS Session State & Substation Namespace Enumeration

* **Target IED:** `192.168.1.10:102`
* **Network Context:** `ns-sub1` → `ns-ied1`
* **Protocol Stack:** TPKT / COTP → ISO Session / Presentation → ACSE → MMS
* **Objective:** Examine MMS application-association behavior, session establishment, namespace discovery, and the amount of information exposed before authentication or authorization is encountered.
* **Lab Action:** Established an MMS association using a custom Python wrapper around `libiec61850`, issued `GetNameList` requests across VMD and Domain scopes, and mapped the resulting Logical Device namespace.

---

# Executive Summary

Phase 2 moves from the engineering configuration boundary established in Phase 1 into the **runtime application layer** of IEC 61850. The objective was to determine what an unauthenticated client could discover after reaching the target IED's MMS endpoint on TCP/102.

A custom Python wrapper extending `libiec61850` successfully established an MMS application association with the target:

```text
192.168.1.10:102
```

The association traversed the expected ISO-on-TCP stack:

```text
TCP
 │
 ▼
TPKT
 │
 ▼
COTP
 │
 ▼
ISO Session / Presentation
 │
 ▼
ACSE
 │
 ▼
MMS
```

No credential exchange or cryptographic challenge was required during the observed association. Once the MMS association was established, the client issued `GetNameList` requests to enumerate the server's exposed namespace. The target returned a Logical Device domain named: `simpleIOGenericIO`.  The enumeration produced **304 distinct MMS variables**, including Logical Node objects, Functional Constraint containers, Data Objects, and Data Attributes.

The resulting namespace exposed information such as:

```text

GGIO1$CF$SPCSO1
GGIO1$CF$SPCSO1$ctlModel

GGIO1$CF$SPCSO2$ctlModel
```

This is significant because the attacker does not need to guess the IEC 61850 object model from packet captures alone. The MMS directory services provide a structured view of the runtime information model.

The resulting research chain is:

```text
SCL Configuration
       ↓
Configured Information Model
       ↓
MMS Association
       ↓
GetNameList
       ↓
Logical Device / Object Namespace
       ↓
Potential Control Targets
```

Phase 2 therefore establishes the reconnaissance baseline required for the following control-abuse phase.

# 1. MMS as the Runtime Application Layer

IEC 61850 uses **Manufacturing Message Specification (MMS)** as the primary client/server application protocol for station-level communication. In the laboratory environment, MMS was exposed through TCP port `102`.

The communication stack observed in the capture was:

```text
+-------------------------------------------------------------+
| Layer 7: MMS (ISO 9506)                                     |
|              ASN.1 BER Encoded PDUs                         |
+-------------------------------------------------------------+
| Layer 6: ISO Presentation                                   |
|              ISO 8823 / X.209                               |
+-------------------------------------------------------------+
| Layer 5: ISO Session                                        |
|              ISO 8327                                       |
+-------------------------------------------------------------+
| Layer 4: COTP / ISO Transport                               |
|              ISO 8073 / RFC 1006 TPKT                       |
+-------------------------------------------------------------+
| Layer 3: IPv4                                               |
+-------------------------------------------------------------+
| Layer 2: Ethernet II                                        |
+-------------------------------------------------------------+
```

This is an important architectural distinction from the process-bus protocols examined later.

MMS is:

```text
Client / Server
      │
      ▼
TCP Connection
      │
      ▼
Application Association
      │
      ▼
MMS Services
```

while GOOSE and Sampled Values operate directly over Ethernet at Layer 2. The result is that MMS has a substantially different session and security model from the process-bus traffic examined in Phases 4 and 5.

---

# 2. TCP/102 Transport & ISO-on-TCP

The first runtime boundary is the TCP connection to port `102`.

The target was reachable at: `192.168.1.10:102`. The TCP connection provides the underlying byte stream, but MMS does not communicate directly as raw TCP payload. IEC 61850's MMS stack uses the ISO-on-TCP mechanism to carry the upper ISO layers over TCP.

The simplified relationship is:

```text
TCP/102
   │
   ▼
TPKT
   │
   ▼
COTP
   │
   ▼
ISO Session
   │
   ▼
ISO Presentation
   │
   ▼
ACSE
   │
   ▼
MMS
```

This layered construction is important during packet analysis because an MMS request cannot be reliably identified by inspecting TCP payload bytes alone. Each layer contributes its own framing or session semantics.

---

## 2.1 TPKT & COTP

The captured connection included TPKT and COTP transport framing. The test environment observed COTP Connection Request and Connection Confirm exchanges establishing the transport parameters before the upper-layer association was attempted.

The observed COTP negotiation included:

```text
TPDU Size: 1024 bytes
TSAP parameters: 0x0001
```
Reaching TCP/102 establishes only the first boundary. The client must still traverse the ISO stack and establish an MMS application association before issuing normal MMS services.

---

# 3. Application Association

After the transport connection was established, the client initiated the upper-layer application association. The relevant protocol element is the **Association Control Service Element (ACSE)**.

The association begins with an `AARQ`:

```text
Client
  │
  │ AARQ
  ▼
IED
  │
  │ AARE
  ▼
Client
```

The laboratory target returned an accepted association:

```text
AARE
result = accepted (0)
```

The resulting state can be represented as:

```text
TCP Connected
      │
      ▼
COTP Established
      │
      ▼
ISO Session / Presentation
      │
      ▼
ACSE AARQ
      │
      ▼
ACSE AARE
      │
      ▼
MMS Association Established
```

The test harness reported:

```text
[+] Status: MMS Session & Application Association Established!
```

At this point, the client was able to begin issuing MMS service requests.

---

# 4. Association Security Boundary

The observed association did not require a credential exchange or cryptographic challenge before the target accepted the application association.

The practical sequence was therefore:

```text
TCP Connect
     ↓
COTP Setup
     ↓
ACSE AARQ
     ↓
ACSE AARE
     ↓
MMS Available
```

No authentication barrier was encountered between network reachability and MMS service availability in the tested configuration. This is an important difference from saying that MMS itself can never implement authentication or security controls.

The finding is specific to the **native plaintext laboratory deployment**:

```text
Observed:
Unauthenticated client
        ↓
Accepted MMS association
```

Additional security mechanisms can change this behavior, which will be examined in Phase 6.

# 5. ASN.1 BER Encoding

MMS service requests and responses are represented using ASN.1 structures encoded using **Basic Encoding Rules (BER)**.

At the wire level, the application payload therefore follows a Tag-Length-Value structure:

```text
+---------+---------+----------------------+
|  Tag    | Length  | Value                |
+---------+---------+----------------------+
```

A simplified MMS request can therefore be viewed as:

```text
MMS PDU
 │
 ├── Request Identifier
 │
 ├── Service Type
 │
 └── Service Parameters
```

The exact structure depends on the MMS service being invoked. This matters for later research because the protocol is not simply transmitting strings such as:

```text
Read GGIO1
```

Instead, the requested object and service semantics are encoded into nested ASN.1 structures. The Phase 2 harness therefore operates above raw packet parsing while the corresponding PCAP provides the wire-level representation required to correlate application operations with their BER-encoded form.

# 10. Namespace Enumeration as Reconnaissance

The security significance of `GetNameList` is that the attacker does not have to begin with an unknown address space. The target itself can provide the directory structure.

The resulting reconnaissance workflow becomes:

```text
TCP/102
   │
   ▼
MMS Association
   │
   ▼
GetNameList
   │
   ▼
Logical Device Discovery
   │
   ▼
Logical Node Discovery
   │
   ▼
Data Object / Attribute Discovery
   │
   ▼

```

In the laboratory environment, this process exposed **304 variables**. That information can significantly reduce the search space for subsequent testing. Instead of blindly attempting arbitrary object references, a researcher can construct requests against objects already confirmed to exist. This is particularly important in IEC 61850 because the object model can contain operationally meaningful names rather than anonymous numerical point identifiers.

# 11. Session Lifecycle & Resilience

Phase 2 also examined how the target behaved during session termination. A normal MMS session can be closed using the MMS `Conclude` mechanism.

The observed lifecycle was:

```text
MMS Association
       │
       ▼
MMS Services
       │
       ▼
Conclude-Request
       │
       ▼
Association Released
```

The `libiec61850` client was able to close the association cleanly using the library's connection-close path. The target released the corresponding server-side communication state without instability.

---

## 11.1 Unclean Disconnect

The test also considered the behavior of an unclean TCP termination.

A TCP reset can leave the underlying socket in a temporary kernel-managed state such as:

```text
TCP RST
  │
  ▼
Socket Cleanup
  │
  ▼
TIME_WAIT / Connection Recycling
```

In the observed environment, the server event loop remained stable and the target did not crash following the unclean disconnect. This is relevant because a protocol implementation that survives malformed or abruptly terminated sessions is materially different from one where a single broken association can terminate the service. The Phase 2 target demonstrated resilience under the tested disconnect condition.

# 12. Security Assessment

## 12.1 Unauthenticated Application Association

The most important Phase 2 observation is that the target accepted an MMS application association without an authentication exchange in the tested plaintext configuration.

The resulting boundary was:

```text
Network Reachability
        ↓
TCP/102
        ↓
MMS Association
        ↓
MMS Services
```

No authentication barrier was encountered between the reachable TCP endpoint and the MMS namespace. This does not mean that every IEC 61850 deployment behaves identically. The observation applies to the tested native plaintext configuration.

---

## 12.2 Namespace Exposure

The target exposed its Logical Device and MMS variable namespace through `GetNameList`.

The enumeration returned:

```text
Logical Device: simpleIOGenericIO
Variables: 304
```

This transforms reconnaissance from a guessing problem into a directory-discovery problem.

An attacker can potentially learn:

```text
Logical Devices
Logical Nodes
Data Objects
Data Attributes
Functional Constraints
Control Metadata
```

before attempting any process manipulation.

---

## 12.3 Information Leakage

The namespace itself is operational information.

Names such as:

```text
GGIO1
SPCSO1
SPCSO2
ctlModel
```

can provide insight into the structure and purpose of the IED's exposed objects. The security issue is therefore not merely that the device responds to a directory query. It is that the response can reveal **how the device represents operational state and control functions**.

---

## 12.4 Session Resilience

The target remained stable during the tested normal and abnormal disconnect paths.

Observed behavior:

```text
Normal Conclude
      ↓
Clean session release

TCP RST
      ↓
Socket cleanup
      ↓
Server remains operational
```

No crash or event-loop failure was observed during the tested disconnect scenario. This is a positive resilience characteristic even though it does not mitigate the namespace exposure itself.

---

# 13. Hardening Considerations

The first control is to restrict who can reach TCP/102.

Recommended network controls include:

* OT firewall ACLs
* Strict source and destination filtering
* Station-bus segmentation
* Controlled routing between SCADA and IED networks
* Monitoring unexpected TCP/102 connections

The goal should be:

```text
Untrusted Network
       │
       X
     TCP/102
       │
       ▼
Authorized SCADA / Engineering Hosts
```

Network isolation is particularly important where the native MMS deployment does not provide sufficient application-layer authentication.

---

## 13.1 Protect the MMS Session

Where supported, IEC 61850 deployments should use appropriate IEC 62351 security mechanisms rather than relying exclusively on network isolation.

The security objective is to introduce controls between:

```text
TCP Connectivity
       ↓
MMS Association
```

and unrestricted MMS service access. Phase 6 will examine this contrast directly.

---

## 13.2 Reduce Unnecessary Namespace Exposure

An IED should expose only the objects and services required for its operational role.

Where implementation capabilities allow it, administrators should review:

```text
GetNameList
Read
Write
Control
File Services
```

and determine which operations are actually required by the legitimate client population. Namespace visibility should be treated as information disclosure even when the exposed objects cannot subsequently be modified.

---

# Security Characteristics

Phase 2 establishes the **runtime discovery boundary** between the configured IEC 61850 information model and the MMS application layer.

### The key findings are:

* The tested IED accepted an MMS application association without an authentication exchange.
* The association traversed the expected ISO-on-TCP stack successfully.
* MMS traffic was represented using ASN.1 BER structures.
* `GetNameList` exposed the Logical Device namespace.
* The target exposed **304 MMS variables** in the tested configuration.
* The returned namespace revealed Logical Node, Functional Constraint, Data Object, Data Attribute, and control-model information.
* Normal MMS termination worked correctly.
* The tested TCP-reset condition did not crash the target event loop.

Phase 1 established that the SCL configuration defines the information model upstream. Phase 2 demonstrates that the resulting model can become **directly observable through the MMS runtime interface**. Phase 3 therefore moves from **namespace discovery** into **MMS control and file-service abuse**.
