# Phase 4: Process Bus Mechanics (Layer 2 GOOSE & Sampled Values)

* **Target Interface:** `br-processbus`
* **Protocol Layer:** IEC 61850 Process Bus / Ethernet Layer 2
* **Protocols:** GOOSE (`0x88B8`) and Sampled Values (`0x88BA`)
* **Objective:** Examine the wire-level mechanics of IEC 61850 process-bus traffic, focusing on Layer 2 multicast delivery, ASN.1 BER encoding, application identifiers, state/sequence fields, and the relationship between process data and their encoded dataset structures.

---

## Executive Summary

Phase 4 moved the investigation below the IP layer and into the **IEC 61850 process bus**.

Unlike the MMS communication examined in Phases 2 and 3, GOOSE and Sampled Values do not depend on TCP sessions or an application association over TCP/102. Process-bus traffic is carried directly inside Ethernet frames, allowing time-critical protection and automation data to move between IEDs and process-level devices without the TCP/IP transport path used by MMS.

The initial process-bus test focused on GOOSE. A custom test harness transmitted a Layer 2 GOOSE frame using EtherType `0x88B8` and the IEC 61850 multicast destination `01:0c:cd:01:00:01`. The frame was successfully constructed with an application identifier, state number, sequence number, and Time Allowed to Live value, and the payload was encoded using ASN.1 BER.

The captured test frame represented an event-triggered state:

```text
stNum = 2
sqNum = 42
TAL   = 1500 ms
```

This provides the baseline for the next phase, where these state variables become security-relevant. In particular, the process bus does not rely on a TCP connection or MMS association to establish communication context. Instead, subscribers derive publisher state directly from the Ethernet frames they receive.

The phase therefore establishes the following architectural difference:

```text
MMS
 │
 ├── TCP
 ├── ISO-on-TCP
 ├── MMS Association
 └── Client / Server
```

versus:

```text
GOOSE / SV
 │
 ├── Ethernet
 ├── Multicast
 └── Publisher / Subscriber
```

This difference becomes critical when analyzing spoofing, replay, sequence manipulation, and process-state poisoning in Phase 5.

---

# 1. Process Bus Architecture

IEC 61850 divides communication responsibilities across different buses.

The station bus provides higher-level supervisory communication:

```text
Station Level
      │
      │ TCP/IP
      ▼
     MMS
      │
      ▼
     IED
```

The process bus provides time-critical communication between protection, control, and process-level devices:

```text
IED / Protection Relay
          │
          │
          ▼
    Process Bus
          │
     ┌────┴────┐
     │         │
    GOOSE      SV
     │         │
     ▼         ▼
  IEDs /     Merging
  Controllers Units
```

The important difference is that GOOSE and SV are **Ethernet-native protocols**.

They do not require:

```text
IP
 ↓
TCP
 ↓
Application Session
```

before process data can be transmitted.

Instead:

```text
Ethernet
   │
   ├── GOOSE  0x88B8
   │
   └── SV     0x88BA
```

This allows process-bus messages to avoid the connection-oriented behavior associated with MMS.

---

# 2. GOOSE Wire Architecture

GOOSE, or **Generic Object Oriented Substation Event**, is designed for high-speed peer-to-peer communication between substation devices.

A simplified Ethernet representation is:

```text
+------------------- Ethernet --------------------+
| Destination MAC | Source MAC | EtherType 0x88B8 |
+--------------------------------------------------+
| 802.1Q VLAN / Priority (where configured)       |
+--------------------------------------------------+
| GOOSE Header / Application Fields                |
| APPID / Length / Reserved                       |
+--------------------------------------------------+
| ASN.1 BER GOOSE Payload                          |
| gocbRef / timeAllowedToLive / stNum / sqNum ... |
+--------------------------------------------------+
```

The protocol is therefore fundamentally different from the MMS traffic examined earlier.

The communication path is:

```text
GOOSE Publisher
      │
      ▼
Ethernet Frame
      │
      ▼
Multicast MAC
      │
      ▼
GOOSE Subscribers
```

There is no TCP handshake establishing the relationship between publisher and subscriber.

---

# 3. Layer 2 Multicast Delivery

The Phase 4 harness generated the following destination:

```text
Destination MAC:
01:0c:cd:01:00:01
```

and used:

```text
EtherType:
0x88B8
```

The resulting frame was therefore identifiable at the Ethernet layer as GOOSE traffic.

The observed frame metadata was:

| Field           | Observed Value      |
| --------------- | ------------------- |
| Protocol        | GOOSE               |
| OSI Layer       | Layer 2             |
| EtherType       | `0x88B8`            |
| Source MAC      | `26:42:53:af:9c:91` |
| Destination MAC | `01:0c:cd:01:00:01` |

The communication model can be represented as:

```text
                 GOOSE Publisher
                 26:42:53:af:9c:91
                         │
                         │ Ethernet
                         │ 0x88B8
                         ▼
              01:0c:cd:01:00:01
                  Multicast Group
                         │
               ┌─────────┼─────────┐
               │         │         │
               ▼         ▼         ▼
             IED 1     IED 2     IED 3
```

The significance is that a subscriber does not need to establish a session with the publisher before receiving process events. The Ethernet frame itself carries the information required for the subscriber to interpret the GOOSE message.

# 4. ASN.1 BER Payload Encoding

Although GOOSE operates directly over Ethernet, its application payload uses **ASN.1 Basic Encoding Rules (BER)**.

The test harness reported the beginning of the encoded payload as:

```text
61 81 00 80 02 00 01 84 01 02 85 01 2a ...
```

This demonstrates the nested TLV structure used to represent GOOSE application fields.

Conceptually:

```text
ASN.1 BER
   │
   ├── Tag
   ├── Length
   └── Value
```

This is important for packet analysis because the process bus is not simply a collection of fixed-position binary integers.

A useful analytical model is:

```text
Ethernet
   │
   ▼
GOOSE Application Header
   │
   ▼
BER Encoded Fields
   │
   ├── Publisher / Control Reference
   ├── Dataset Reference
   ├── TAL
   ├── stNum
   ├── sqNum
   └── Dataset Values
```

Consequently, custom process-bus tooling must understand both **Ethernet framing** and **BER field structure**.

---

# 5. Application Identifier & Subscriber Filtering

GOOSE frames contain an **APPID** used to identify the application stream.

This creates another layer of filtering beyond the Ethernet multicast address:

```text
Ethernet Destination MAC
          │
          ▼
    Multicast Group
          │
          ▼
        APPID
          │
          ▼
   GOOSE Application
          │
          ▼
       Dataset
```

The resulting filtering model allows an IED to distinguish between different GOOSE streams sharing the same physical process-bus infrastructure. This is operationally useful, but it should not automatically be interpreted as an authentication mechanism. An identifier tells a subscriber **which application stream a frame claims to belong to**.

It does not inherently prove: `Who generated the frame?` That becomes central to the injection testing in Phase 5.

---

# 6. GOOSE State & Sequence Model

GOOSE uses two particularly important state variables:

```text
stNum
sqNum
```

They provide subscribers with information about publisher state and message progression.

The simplified model is:

```text
                 Publisher State
                       │
                       ▼
                    stNum
                       │
              Event / State Change
                       │
                       ▼
                stNum increments
                       │
                       ▼
                sqNum progression
```

The Phase 4 test frame contained:

```text
stNum = 2
sqNum = 42
```

The harness classified the frame as:

```text
Event Triggered
```

This provides a concrete example of the difference between publisher state and individual message sequencing.

A useful conceptual model is:

```text
stNum
  │
  └── Identifies publisher state / event generation

sqNum
  │
  └── Identifies progression of retransmissions
      within that state
```

This relationship is particularly important because subscribers can use these values to determine whether an incoming frame represents:

```text
Expected progression
        │
        ├── New publisher state
        │
        └── Retransmission of current state
```

The exact subscriber behavior is implementation-dependent and becomes an explicit test target in Phase 5.

---

# 7. Time Allowed to Live

The test frame contained:

```text
TAL = 1500 ms
```

The **Time Allowed to Live (TAL)** communicates the expected validity interval associated with the GOOSE transmission.

This field contributes to subscriber supervision:

```text
GOOSE Frame
     │
     ▼
TAL = 1500 ms
     │
     ▼
Subscriber expects continued publication
     │
     ├── Valid continuation
     │
     └── Publication timeout
```

GOOSE publishers can retransmit messages according to their configured timing behavior, particularly following state changes. Therefore, TAL should be considered alongside `stNum` and `sqNum`, rather than treated as an isolated timestamp or sequence field.

---

# 8. Event State vs. Steady-State Traffic

GOOSE communication distinguishes between a change in publisher state and continued publication of the current state.

Conceptually:

```text
Normal State
    │
    ├── Periodic / repeated publication
    │
    └── stNum remains associated with current state
              │
              ▼
        sqNum progresses


Process Event
    │
    ▼
stNum changes
    │
    ▼
New event state
    │
    ▼
GOOSE retransmission sequence
```

The Phase 4 harness deliberately generated:

```text
stNum = 2
sqNum = 42
```

to represent an event-triggered frame. This provides the baseline required for Phase 5, where deliberately altered state and sequence values can be introduced and subscriber reactions observed. Importantly, the current Phase 4 execution demonstrates the structure of an event-triggered frame. It does not by itself establish a complete empirical timing curve for steady-state retransmission behavior.

# 9. Sampled Values Architecture

Sampled Values provide a different process-bus communication model.

Where GOOSE primarily communicates **events, states, and control-related dataset values**, SV provides a continuous stream of digitized measurements from process-level instrumentation.

The architectural relationship is:

```text
             Analog Process
                  │
             CT / PT Signals
                  │
                  ▼
           Merging Unit
                  │
          A/D Conversion
                  │
                  ▼
         Sampled Values
                  │
                  ▼
          Ethernet 0x88BA
                  │
          ┌───────┴───────┐
          ▼               ▼
      Protection        Metering
         IED              IED
```

The corresponding wire path is:

```text
Ethernet
    │
    ▼
EtherType 0x88BA
    │
    ▼
SV Application Payload
    │
    ▼
Encoded Sample Dataset
    │
    ▼
Current / Voltage Samples
```

Unlike a conventional SCADA measurement read, the subscriber does not request each sample individually. The Merging Unit continuously publishes the sample stream.

---

# 10. GOOSE vs. Sampled Values

The two process-bus protocols can therefore be separated conceptually:

| Characteristic   | GOOSE                               | Sampled Values                  |
| ---------------- | ----------------------------------- | ------------------------------- |
| EtherType        | `0x88B8`                            | `0x88BA`                        |
| Communication    | Multicast                           | Multicast                       |
| Primary role     | Events / status / control signaling | Digitized process measurements  |
| Publisher        | IED / protection device             | Merging Unit                    |
| Subscriber       | IEDs / controllers                  | Protection / measurement IEDs   |
| Timing model     | Event-driven + retransmission       | Continuous stream               |
| Key state fields | `stNum`, `sqNum`, TAL               | Sample / synchronization fields |
| Transport        | Ethernet Layer 2                    | Ethernet Layer 2                |

That is important because the attack surfaces are different.

GOOSE analysis focuses heavily on:

```text
State
Sequence
Timing
Dataset semantics
```

while SV analysis additionally requires attention to:

```text
Sample ordering
Sampling rate
Channel mapping
Signal plausibility
Synchronization
```

---

# 11. Process-Bus Trust Boundary

The architecture established by Phase 4 creates a very different trust boundary from the MMS environment.

MMS:

```text
Client
  │
  ▼
TCP/102
  │
  ▼
Application Association
  │
  ▼
Service Request
```

GOOSE:

```text
Ethernet
  │
  ▼
Multicast Frame
  │
  ▼
Subscriber
```

SV:

```text
Ethernet
  │
  ▼
Multicast Sample Stream
  │
  ▼
Subscriber
```

The process-bus subscriber therefore has to make security-relevant decisions based directly on received Ethernet traffic.

For GOOSE, those decisions include:

```text
Is this the expected multicast stream?
        │
Is the APPID expected?
        │
Is the publisher state plausible?
        │
Is the sequence progression plausible?
        │
Is the timing within expectations?
        │
Are the dataset values valid?
```

This makes process-bus state validation an important security control even before cryptographic extensions are considered.

# Security Characteristics

Phase 4 establishes the wire-level baseline for the IEC 61850 process bus.

The tested GOOSE frame demonstrated:

```text
Ethernet
    │
    ▼
EtherType 0x88B8
    │
    ▼
Multicast Destination
01:0c:cd:01:00:01
    │
    ▼
GOOSE Payload
    │
    ├── ASN.1 BER
    ├── APPID
    ├── TAL = 1500 ms
    ├── stNum = 2
    └── sqNum = 42
```

The major architectural characteristics are:

* GOOSE and SV operate directly over Ethernet rather than TCP/IP.
* GOOSE uses Layer 2 multicast delivery and EtherType `0x88B8`.
* SV uses Layer 2 multicast delivery and EtherType `0x88BA`.
* GOOSE application data is encoded using ASN.1 BER.
* `stNum`, `sqNum`, and TAL provide subscriber-visible state and timing context.
* APPID and multicast addressing identify the intended traffic stream but do not inherently establish cryptographic identity.
* GOOSE and SV therefore expose a fundamentally different trust boundary from MMS.
* The Phase 4 harness empirically demonstrated GOOSE frame construction and transmission; detailed SV waveform behavior and long-term GOOSE retransmission timing require corresponding live captures before being presented as measured findings.

The resulting process-bus model is:

```text
                  IEC 61850 Process Bus
                           │
              ┌────────────┴────────────┐
              │                         │
           GOOSE                         SV
              │                         │
       Event / Control             Measurement Stream
              │                         │
       Ethernet 0x88B8             Ethernet 0x88BA
              │                         │
              ▼                         ▼
      State / Sequence              Samples
       / Timing Model             / Synchronization
              │                         │
              └────────────┬────────────┘
                           ▼
                  Subscriber Logic
                           │
                           ▼
                    Physical Process
```

This baseline is what makes Phase 5 possible. Once the subscriber's expectations for **multicast identity, application identity, state number, sequence number, timing, and process values** are understood, those same fields can be deliberately manipulated to determine which parts of the process-bus trust model are actually enforced.
