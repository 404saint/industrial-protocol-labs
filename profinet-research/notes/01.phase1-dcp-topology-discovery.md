# Phase 1: Layer 2 Discovery & Network Topology Mapping

## 1. Executive Summary

PROFINET IO networks use a Layer 2 discovery and configuration path that operates independently of ordinary IP connectivity. This allows engineering stations, controllers, and diagnostic tools to identify devices, inspect network parameters, and map physical topology before normal IP-based communication and Application Relationship establishment are complete.

This phase evaluated the Layer 2 attack surface of a PROFINET IO-Device based on the `p-net` sample stack. The target operated inside an isolated Linux network namespace, while a separate unauthenticated namespace performed discovery, passive traffic capture, and a controlled station-name modification attempt.

The assessment covered two complementary protocols:

* **PROFINET Discovery and basic Configuration Protocol (DCP)** for active device enumeration and configuration operations.
* **Link Layer Discovery Protocol (LLDP)** for passive topology and device-information disclosure.

The tests demonstrated that an unauthenticated Layer 2 participant could enumerate the target device's station name, vendor/device identifiers, and configured IP parameters through DCP. Passive LLDP capture also exposed chassis information, port identification, system name, and advertised information lifetime.

A subsequent unauthenticated DCP Set Request targeting the station name did not change the configured value. The target continued to report `rt-labs-dev` after the modification attempt. This demonstrates that unauthenticated reachability and successful state modification are separate conditions. In the tested implementation, runtime write protection prevented the attempted station-name change.

### Key Findings

* **Active DCP Enumeration:** An unauthenticated Layer 2 DCP Identify request successfully enumerated the target IO-Device's station name, vendor/device identifiers, and configured IP parameters without requiring prior IP connectivity.
* **Passive LLDP Disclosure:** Periodic LLDP Layer 2 multicast advertisements exposed implementation-specific chassis information, the device's port identifier, system name, and advertised information lifetime without requiring an active probe.
* **DCP State Modification Attempt:** An unauthenticated DCP Set Request targeting the station name did not change the configured value. A subsequent Identify response continued to report `rt-labs-dev`.
* **Implementation-Level Protection:** The tested `p-net` implementation demonstrated runtime protection against the attempted station-name update. The experiment did not establish that all PROFINET implementations provide equivalent protection.
* **Security Boundary:** The protocol exposed discovery information to an unauthenticated Layer 2 participant, while the tested implementation separately enforced restrictions on runtime configuration changes.

## 3. Protocol Scope

### 3.1 PROFINET DCP

PROFINET DCP operates directly over Ethernet using EtherType `0x8892`. It provides discovery and basic configuration functions such as:

* Identifying local PROFINET devices.
* Reading device identification information.
* Reading configured IP parameters.
* Assigning station names.
* Assigning IP parameters.
* Performing supported reset or factory-related operations.

DCP does not require ordinary IP connectivity for its Layer 2 discovery and configuration functions. DCP messages contain a protocol header followed by option and suboption blocks. The operation is represented through the DCP Service ID and Service Type fields. The payload is structured into typed blocks containing lengths and values.

The relevant DCP operations in this phase were:

* **Identify:** Enumerate available PROFINET devices and retrieve identification/configuration information.
* **Set:** Attempt to modify a device parameter, specifically the station name.

The Ethernet EtherType identifies the PROFINET DCP carrier protocol. It should not be confused with the DCP operation itself.

### 3.2 LLDP

LLDP uses Ethernet EtherType `0x88CC` and the standard Layer 2 multicast destination:

```text
01:80:c2:00:00:0e
```

PROFINET devices use LLDP information to support topology discovery and neighbor identification. LLDP advertisements may expose:

* Chassis identification.
* Port identification.
* System name.
* System description.
* Time To Live.
* Additional organization-specific information.

The Time To Live value indicates how long the advertised information should remain valid without a refresh. It is not necessarily identical to the device's transmission interval.

## 4. DCP Frame and Attribute Model

DCP is carried directly inside Ethernet frames:

```text
Ethernet
 ├── Destination MAC
 ├── Source MAC
 ├── EtherType: 0x8892
 └── DCP Message
      ├── Service ID
      ├── Service Type
      ├── Transaction ID
      ├── Response Delay
      ├── Data Length
      └── Option/Suboption Blocks
```

The option and suboption structure allows DCP responses to carry different categories of information. The values observed during enumeration included device identification and IP parameter blocks.

### Captured DCP Attributes

| Block Option | Suboption | Description           | Extracted Value                                                     |
| :----------- | :-------- | :-------------------- | :------------------------------------------------------------------ |
| `0x02`       | `0x02`    | Name of Station       | `rt-labs-dev`                                                       |
| `0x02`       | `0x03`    | Vendor ID / Device ID | Vendor: `0x0493`, Device: `0x0002`                                  |
| `0x01`       | `0x02`    | IP Parameter Block    | IP: `192.168.1.20`, Subnet: `255.255.255.0`, Gateway: `192.168.1.1` |

The DCP option and suboption values above were extracted from the captured response and interpreted according to the DCP block structure used by the target implementation.

### 5.3 Test 3: DCP Station-Name Modification Attempt

The audit script transmitted a DCP Set Request targeting the station name of the device at:

```text
02:00:00:00:00:02
```

The attempted replacement value was:

```text
tesla-pnet-node
```

The request was transmitted using:

```bash
sudo ip netns exec ns-controller python3 scripts/01_dcp_audit.py --set-name tesla-pnet-node
```

The target's station name was then verified through a subsequent DCP Identify request.

#### Verification Output

```text
[*] Transmitting DCP Identify Request on veth-controller (02:00:00:00:00:01)...
[+] Captured DCP Identify Response from 02:00:00:00:00:02
...
│ Name of Station    │ rt-labs-dev       │
...
```

#### Result

The station name remained:

```text
rt-labs-dev
```

The attempted update to `tesla-pnet-node` did not take effect.

The observed behavior is consistent with runtime write protection in the tested `p-net` implementation. The target's station name remained unchanged when verified through a new DCP Identify response. This test established that the target was reachable for unauthenticated DCP discovery but did not permit the attempted runtime station-name modification.

## 6. Security Analysis

### 6.1 Reconnaissance Exposure

The DCP Identify response exposed several attributes that can assist an attacker in identifying and profiling a PROFINET device:

* MAC address.
* Station name.
* Vendor ID.
* Device ID.
* IP address.
* Subnet mask.
* Default gateway.

This information was available through Layer 2 communication without requiring ordinary IP connectivity. The exposed station name is particularly relevant because PROFINET controller configuration commonly associates a device with its configured station name. The vendor/device identifiers can also assist with device classification and engineering-system matching.

### 6.2 Passive Topology Disclosure

LLDP provided topology-related information without requiring an active request.

The captured information exposed:

* The existence of a neighboring PROFINET device.
* The device's chassis identifier.
* The device's port identifier.
* The system name.
* The advertised information lifetime.

In a larger network, comparable LLDP observations could be correlated across multiple devices to build a Layer 2 topology map. This can help identify device adjacency, port relationships, and potential paths toward control assets.

### 6.3 DCP Configuration and Authentication Boundary

Classic DCP discovery and configuration traffic does not provide cryptographic message authentication. Consequently, the ability to transmit a DCP request is primarily governed by network reachability and the receiving implementation's validation and authorization behavior.

This creates two distinct security questions:

1. Can an unauthenticated Layer 2 participant discover the device?
2. Can that participant successfully modify device state?

The first condition was demonstrated in this phase. The second was not achieved against the tested `p-net` implementation.

The result is important because protocol-level unauthenticated reachability does not automatically imply successful configuration modification. Device-side write restrictions, commissioning state, persistence rules, and implementation-specific authorization logic can affect the outcome.

### 6.4 Implementation-Specific Runtime Protection

The `p-net` sample stack did not apply the attempted station-name change during runtime. The subsequent DCP Identify response continued to report the original value.

The available implementation behavior indicates that runtime configuration updates are restricted unless the relevant write permissions or initialization conditions are satisfied. This should be treated as an implementation-specific control rather than a property guaranteed by classic DCP itself.

The finding therefore applies precisely to the tested stack:

> The tested `p-net` implementation exposed unauthenticated discovery information but prevented the attempted runtime station-name modification.

It should not be generalized to all PROFINET devices without separate testing.

## 7. Defense and Remediation Recommendations

### 7.1 Restrict Layer 2 Access

Use network segmentation and switch access controls to prevent unauthorized systems from joining the PROFINET segment.

Potential controls include:

* Dedicated automation VLANs.
* Port security.
* Strict switch-port assignment.
* IEEE 802.1X where supported and operationally appropriate.
* Removal of unnecessary access paths between enterprise and control networks.
* Monitoring for unauthorized MAC addresses.

Layer 2 access should be treated as a meaningful trust boundary because DCP and RT traffic do not depend on ordinary IP authentication.

### 7.2 Protect DCP Configuration Operations

Where supported by the device and engineering workflow:

* Restrict runtime DCP configuration changes.
* Apply commissioning-state controls.
* Enforce device-side write permissions.
* Disable or limit remote configuration operations after commissioning.
* Require a controlled maintenance procedure for station-name and IP changes.
* Verify whether reset and factory-related DCP operations are exposed.

The tested `p-net` behavior demonstrates the value of implementation-level protection, but this behavior must be verified independently for each device family and firmware version.

### 7.3 Control LLDP Disclosure

Where supported and compatible with PROFINET topology functions:

* Limit LLDP exposure to trusted automation segments.
* Review system-name and chassis-description fields.
* Avoid unnecessary descriptive information in device identifiers.
* Monitor LLDP advertisements for unexpected devices or topology changes.
* Ensure that disabling LLDP does not interfere with required topology discovery or commissioning functions.

LLDP should not be treated as an authentication mechanism. It is an information-disclosure and topology-discovery protocol.

### 7.4 Monitor DCP Activity

Network monitoring should identify unexpected DCP activity, particularly:

* DCP Identify bursts.
* DCP Set Requests.
* Station-name changes.
* IP parameter changes.
* Reset-related operations.
* DCP traffic originating from unauthorized ports or MAC addresses.

A baseline of normal commissioning and operational DCP activity can help distinguish expected engineering operations from suspicious Layer 2 reconnaissance or configuration attempts.

## 9. Key Takeaways

* PROFINET DCP provides powerful discovery and basic configuration capabilities directly over Ethernet.
* An unauthenticated Layer 2 participant can enumerate meaningful device and network information without first obtaining IP connectivity.
* LLDP provides passive topology information that can be collected without active probing.
* Classic DCP does not provide cryptographic message authentication, so network access and implementation-level controls remain important security boundaries.
* The tested `p-net` stack rejected or ignored the attempted runtime station-name update, demonstrating implementation-level protection against the specific modification tested.
* Discovery exposure and configuration modification are separate security properties and should be evaluated independently.
* A practical PROFINET security assessment should combine active DCP testing, passive LLDP analysis, implementation-aware mutation, and Layer 2 access-control review.
