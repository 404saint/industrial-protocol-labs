# Phase 4: Netload, Stress & Resiliency Audit

## Executive Summary

Phase 4 examined the behavior of a PROFINET network environment under controlled Layer 2 stress, discovery-oriented traffic, and malformed frame injection. Unlike Phase 3, which used a dedicated packet-generation harness because the `pn_dev` environment did not produce usable cyclic RT traffic, this phase retained the p-net `pn_dev` stack as the device-side implementation while an independent Scapy-based harness generated adversarial inputs.

Three experiments were performed. The first generated a high-rate EtherType `0x8892` burst as a Class III-oriented netload simulation. The second transmitted crafted DCP-like traffic attempting to associate the station name `rt-labs-dev` with a rogue source MAC. The third transmitted malformed EtherType `0x8892` frames containing a crafted Frame ID of `0x00FF` and a truncated payload.

The resulting PCAP contained 508 Ethernet frames. The capture directly establishes what traffic was transmitted and observed: 500 high-rate burst frames, three DCP-like station-name frames, and five malformed frames. It does not independently establish how `pn_dev` processed those inputs. No endpoint response, diagnostic, alarm, or recovery traffic was captured after the DCP-like or malformed-frame injections.

The primary security finding is therefore architectural rather than an assertion of successful or failed endpoint exploitation. PROFINET Layer 2 mechanisms expose meaningful attack surface to a host capable of transmitting Ethernet frames on the relevant network segment. The experiments demonstrate that an external host can generate traffic resembling protocol activity, but endpoint-side acceptance, filtering, and state changes require additional instrumentation or observable protocol responses to establish conclusively.

---

## 1. Experimental Boundary

Phase 4 used the p-net `pn_dev` stack as the device-side PROFINET implementation. The controller and device remained separated into Linux network namespaces, with the adversarial traffic generated independently using Scapy. This is important when interpreting the results.

The Scapy harness controls the packets transmitted onto the Layer 2 segment. The PCAP provides direct evidence of those packets and their timing. The harness itself can label an operation as completed, rejected, or handled, but those labels are generated by the test program unless they are supported by independent endpoint evidence.

Because the `pn_dev` environment did not expose corresponding runtime logs for these experiments, endpoint-side acceptance, rejection, parser behavior, and internal state transitions are not inferred from the absence of a crash or from the harness status messages.

Accordingly, the observations in this phase are divided into three categories:

* **Directly observed:** packet structure, source/destination addresses, EtherType, timing, payload contents, and packet counts.
* **Test-harness observations:** operations successfully transmitted by the Scapy generator.
* **Endpoint behavior:** reported only where independently observable through protocol responses, diagnostics, logs, or subsequent network behavior.

No endpoint-side behavior is attributed to `pn_dev` beyond what the capture can support.

## 3. Stage 1: PI Netload Stress Testing

## Objective

The first experiment evaluated the network environment under a short, high-rate burst of EtherType `0x8892` traffic.

The original target rate was approximately 15,000 packets per second, with a 500-frame burst. The actual transmitted rate was substantially lower, making this experiment better classified as a **Class III-oriented netload simulation** rather than a reproduction of a specific PROFINET Netload Class III limit.

## Test Procedure

The harness generated 500 Ethernet frames with:

* EtherType: `0x8892`
* Destination: `01:0e:cf:00:00:00`
* Source: `00:11:22:33:44:55`
* Ethernet payload: 60 zero bytes
* Captured frame length: 74 bytes

The resulting PCAP contains all 500 burst frames.

The first two bytes after the EtherType were `00 00` in every burst frame. Therefore, these packets should not be described as valid PROFINET RT frames merely because they use EtherType `0x8892`. They were generated as Layer 2 netload traffic for the stress experiment.

## Capture Measurements

The 500-frame burst occurred over approximately:

```text
Start:    2026-09-11 12:47:01.914612 +02:00
End:      2026-09-11 12:47:02.023148 +02:00
Duration: 108.536 ms
```

Measured timing:

| Metric                       |                Result |
| ---------------------------- | --------------------: |
| Frames                       |                   500 |
| Burst duration               |            108.536 ms |
| Minimum inter-frame interval |            159.979 µs |
| Maximum inter-frame interval |           1.708031 ms |
| Mean inter-frame interval    |            217.507 µs |
| Median inter-frame interval  |            205.040 µs |
| Measured TX rate             | ~4,014.46 packets/sec |

The capture reported: `0 packets dropped by kernel`. This establishes that the capture path did not report kernel-level packet drops during the observation. It does **not** establish that `pn_dev` processed every packet, nor does it demonstrate absence of application-level packet loss or degradation.

## Observation

The traffic generator successfully transmitted and the capture system successfully recorded all 500 generated frames. No endpoint-level performance metric was available from `pn_dev`. Consequently, the experiment establishes successful high-rate packet generation and capture, but not a quantitative measure of PROFINET stack resilience.

## 4. Stage 2: DCP-Like Station Name Spoofing

## Objective

The second experiment examined whether an external host could place crafted station-name information onto the Layer 2 segment using a rogue source MAC address.

The target station name was:

```text
rt-labs-dev
```

The traffic was generated from:

```text
aa:bb:cc:dd:ee:ff
```

## Captured Traffic

Three identical Ethernet frames were captured.

| Property    | Value               |
| ----------- | ------------------- |
| Frame count | 3                   |
| Length      | 37 bytes            |
| Destination | `ff:ff:ff:ff:ff:ff` |
| Source      | `aa:bb:cc:dd:ee:ff` |
| EtherType   | `0x8892`            |

The relevant payload began:

```text
03 01 00 01 00 01 00 08 02 02 00 0b
72 74 2d 6c 61 62 73 2d 64 65 76
```

The structure contains:

* Service ID: `0x03`
* Service Type: `0x01`
* XID: `0x00010001`
* Response delay field: `0x0008`
* Data length: `0x000b`
* Option: `0x02`
* Suboption: `0x02`
* Station name: `rt-labs-dev`

These packets are best described as **crafted DCP-like frames** in this experiment. The conventional DCP Ethernet framing includes the DCP Frame ID `0xFEFD`; these captured packets do not contain that value before the DCP header. The PCAP therefore supports analysis of the crafted DCP header and station-name data, but does not by itself establish successful processing as a conformant DCP transaction.

## Timing

The first DCP-like frame appeared approximately 20.410 ms after the end of the netload burst.

The three frames were transmitted within approximately 586 µs:

```text
Frame 501
     ↓ 287 µs
Frame 502
     ↓ 299 µs
Frame 503
```

No subsequent DCP response was captured.

## Observation

The experiment demonstrates that an external Layer 2 host was able to transmit station-name-bearing DCP-like traffic using a different source MAC address.

The capture does **not** establish that the legitimate device accepted the station name, changed its configuration, rejected the traffic, or activated a security filter. The harness status message describing the operation as handled by a controller security filter is therefore treated as a test-harness label rather than independent endpoint evidence. No subsequent protocol exchange was captured that would demonstrate a station-name takeover or successful state transition.

## 5. Stage 3: Protocol Anomaly and Malformed Frame Injection

## Objective

The third experiment generated deliberately malformed EtherType `0x8892` frames to examine the network's observable behavior when presented with an unexpected Frame ID and truncated payload.

## Crafted Frame

The injected frames contained:

```text
EtherType: 0x8892
Frame ID:  0x00FF
Payload:   10 bytes
```

Five identical frames were captured.

| Property                      | Value               |
| ----------------------------- | ------------------- |
| Frames                        | 5                   |
| Ethernet length               | 26 bytes            |
| Destination                   | `01:0e:cf:00:00:00` |
| Source                        | `00:11:22:33:44:55` |
| EtherType                     | `0x8892`            |
| Crafted Frame ID              | `0x00FF`            |
| Payload length after Frame ID | 10 bytes            |

The five frames were transmitted within approximately 926 µs.

```text
Frame 504  1789123622.073421
Frame 505  1789123622.073707
Frame 506  1789123622.073919
Frame 507  1789123622.074163
Frame 508  1789123622.074347
```

## Observation

The capture proves that malformed frames were placed onto the Layer 2 segment. It does not prove that `pn_dev` parsed and rejected the frames.

The harness described these packets as being rejected gracefully and logged as protocol warnings. Since no corresponding `pn_dev` log or response packet was available, that status is retained as the harness's own classification rather than an endpoint security result.

No crash, diagnostic response, alarm, or recovery exchange was visible in the captured traffic. However, because the capture ended immediately after the malformed-frame burst, the absence of subsequent traffic should not be interpreted as proof of continued service availability.

## 8. Endpoint Evidence Limitations

The most important methodological limitation of this phase is the lack of device-side runtime telemetry. The test environment included the real `pn_dev` implementation, but packet capture alone cannot reveal every internal processing decision.

For example:

| Claim                                                  | Evidence status    |
| ------------------------------------------------------ | ------------------ |
| 500 high-rate frames were transmitted                  | Directly supported |
| Capture path reported zero kernel drops                | Directly supported |
| 3 station-name-bearing crafted frames were transmitted | Directly supported |
| Rogue source MAC was used                              | Directly supported |
| 5 malformed `0x00FF` frames were transmitted           | Directly supported |
| `pn_dev` received every generated packet               | Not established    |
| `pn_dev` accepted the station name                     | Not established    |
| `pn_dev` rejected the station-name traffic             | Not established    |
| `pn_dev` parsed and rejected malformed frames          | Not established    |
| `pn_dev` generated a protocol warning                  | Not established    |
| Controller/device state changed                        | Not established    |
| No service degradation occurred                        | Not established    |

This prevents the test harness from becoming its own evidence source.

A stronger endpoint validation experiment would require one or more of the following:

* device-side `pn_dev` logging,
* controller-side application logs,
* packet capture on the receiving interface,
* observable device configuration changes,
* PROFINET diagnostic or alarm traffic,
* process-image changes,
* controlled service availability measurements before and after injection.

## 9. Security Analysis

## 9.1 Layer 2 Injection Surface

The experiments demonstrate that a host with access to the relevant Ethernet segment can construct and transmit EtherType `0x8892` traffic without requiring IP-layer connectivity. This matters because several PROFINET mechanisms operate directly at Ethernet Layer 2. Network segmentation therefore becomes an important security boundary. The ability to transmit a frame does not imply that a device will accept it, but it establishes that the network path itself can be used to deliver crafted inputs to a PROFINET-capable environment.

## 9.2 Netload and Resource Consumption

The 500-frame burst demonstrates that a short high-rate Layer 2 workload can be generated against the interface. The measured rate was approximately 4,014 packets/sec rather than the intended ~15,000 packets/sec. The experiment therefore should not be interpreted as a validated reproduction of a specific Netload Class III limit.

The capture path recorded no kernel-level drops. This is useful as an observation about the Linux capture environment, but it does not establish the processing capacity of the PROFINET stack or controller. A production assessment would require endpoint CPU utilization, queue depth, packet loss, cycle-time deviation, application response time, and device/controller state telemetry.

## 9.3 Discovery and Identity Spoofing

The DCP-like experiment demonstrates that station-name-bearing Ethernet traffic can be crafted with an arbitrary source MAC address. The security significance is that discovery and commissioning mechanisms exist at a network layer where traditional IP-layer authentication controls may not apply.

However, the experiment did not establish successful station-name modification or device takeover. The appropriate security conclusion is therefore that **DCP traffic represents an identity and configuration attack surface that should be constrained by network access controls and commissioning procedures**, rather than that the tested stack was successfully hijacked.

## 9.4 Malformed Input Handling

The malformed-frame experiment demonstrates the ability to deliver short, structurally abnormal EtherType `0x8892` packets. This is relevant to parser robustness because protocol implementations must validate lengths, identifiers, and state before interpreting payload data. The present capture does not prove how `pn_dev` handled these frames internally. Consequently, the experiment establishes malformed-input exposure but not a verified parser vulnerability or verified rejection behavior.

## 10. Architectural Security Implications

Several broader conclusions emerge from the experiment.

### Layer 2 is a meaningful trust boundary

PROFINET traffic can exist below the IP layer. A security architecture that focuses exclusively on IP addresses, TCP/UDP ports, or application-layer authentication can therefore miss relevant attack paths.

### Network placement directly affects attack surface

An attacker does not necessarily need access to the device's IP address to generate Ethernet traffic toward a PROFINET environment. Access to the relevant Layer 2 segment can itself become a significant capability.

### Traffic generation is different from protocol acceptance

A crafted packet that resembles a legitimate PROFINET structure is not equivalent to a successful protocol transaction. Endpoint state, parser behavior, validation rules, and application logic determine whether the input has an effect. This is especially important for security testing because packet construction alone can demonstrate exposure without demonstrating exploitation.

### Capture absence is not endpoint validation

The lack of a response, alarm, or diagnostic packet provides useful evidence about the observed wire exchange. It cannot, by itself, prove that the endpoint discarded the packet internally or remained unaffected.

## 11. Defense and Remediation

## Network Segmentation

Place PROFINET devices and controllers inside dedicated industrial network segments. Restrict Layer 2 adjacency to systems that require PROFINET communication.

## Switch-Level Controls

Where supported by the industrial switching infrastructure, apply controls that limit unauthorized access to the PROFINET segment and reduce the ability of unmanaged hosts to inject Ethernet traffic.

## DCP Protection

Restrict commissioning and discovery operations to authorized engineering infrastructure. Monitor for unexpected DCP traffic, especially station-name or configuration activity originating from unknown MAC addresses.

## Traffic Monitoring

Baseline normal EtherType `0x8892` behavior and monitor for:

* unexpected source MAC addresses,
* abnormal packet rates,
* unexpected Frame IDs,
* malformed or unusually short frames,
* unexpected DCP activity,
* deviations from established cyclic traffic patterns.

## Endpoint Telemetry

Where possible, expose device-side diagnostics and logging during security validation. Wire capture should be combined with application and device telemetry so that packet delivery can be correlated with endpoint behavior.

## Safety Separation

Where process safety is involved, safety communication mechanisms such as PROFIsafe should be evaluated separately. This experiment did not assess PROFIsafe authentication or safety-layer integrity mechanisms.

## 14. Key Takeaways

1. **Phase 4 used the real p-net `pn_dev` environment**, unlike Phase 3's dedicated RT traffic generator.
2. **500 high-rate EtherType `0x8892` frames were captured**, with an observed transmission rate of approximately 4,014 packets/sec.

3. **The netload burst was a Class III-oriented simulation**, not a validated reproduction of a 15,000 pps PROFINET Netload Class III condition.

4. **Three crafted DCP-like station-name frames were transmitted** from a rogue MAC address, but no successful station-name takeover was demonstrated.

5. **Five malformed `0x00FF` frames were transmitted**, but the capture does not independently prove that `pn_dev` rejected or safely parsed them.

6. **No endpoint diagnostic, alarm, recovery, or response traffic was captured** after the DCP-like or malformed-frame experiments.

7. **The strongest security finding is the Layer 2 attack surface itself:** a host with access to the relevant industrial Ethernet segment can generate controlled PROFINET-related traffic without relying on IP-layer connectivity.

8. **Endpoint acceptance remains the missing evidence layer.** Future testing should correlate packet capture with device logs, controller telemetry, process-image changes, diagnostic traffic, and measurable service behavior.
