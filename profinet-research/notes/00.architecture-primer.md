# PROFINET Architecture & Protocol Research Primer

## Executive Summary

PROFINET is an Industrial Ethernet communication system designed to exchange operational data between controllers and field devices while supporting both conventional Ethernet communication and deterministic real-time behavior.

It is not a single transport mechanism. A PROFINET installation can use standard TCP/IP communication for non-real-time functions, Layer-2 Real Time (RT) communication for cyclic I/O, and Isochronous Real Time (IRT) for applications requiring tighter timing and synchronization. PROFINET also defines mechanisms for device identification, configuration, diagnostics, engineering, and topology discovery.

For this research, the important architectural distinction is between the different communication paths and the roles they perform:

```text
                         PROFINET
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
   Engineering          Device / I/O        Network /
   Configuration          Runtime           Topology
        │                   │                   │
        ▼                   ▼                   ▼
      GSDML          DCE/RPC / RT          DCP / LLDP
                            │
                  ┌─────────┴─────────┐
                  ▼                   ▼
             Acyclic Data         Cyclic I/O
                  │                   │
                  ▼                   ▼
               UDP/IP             Ethernet L2
```

The central runtime relationship is:

```text
Engineering Configuration
          │
          ▼
       GSDML
          │
          ▼
   Configured I/O Model
          │
    ┌─────┴─────┐
    ▼           ▼
IO-Controller  IO-Device
    │           │
    └─────┬─────┘
          ▼
Application Relationship
          │
     ┌────┴────┐
     ▼         ▼
DCE/RPC       RT
Acyclic      Cyclic
Services       I/O
```

The security investigation follows these boundaries rather than treating PROFINET as one undifferentiated protocol surface.

The research therefore moves from:

```text
Engineering Configuration
        ↓
Device Identification
        ↓
DCP Discovery / Parameterization
        ↓
IO-Controller / IO-Device Relationship
        ↓
DCE/RPC Configuration
        ↓
Cyclic RT I/O
        ↓
Topology / Network Behavior
        ↓
Security Enforcement
```

This primer establishes only the architectural concepts required to understand those experiments. It is not intended to reproduce the complete PROFINET specification.

# 1. PROFINET Communication Architecture

PROFINET uses standard Ethernet as its underlying network technology while adding communication mechanisms appropriate for industrial automation.

The architecture can be viewed as several communication channels sharing the same physical Ethernet infrastructure:

```text
+------------------------------------------------------+
|                  Industrial Ethernet                 |
+------------------------------------------------------+
        │                 │                  │
        ▼                 ▼                  ▼
    TCP/IP              PROFINET RT        PROFINET IRT
        │                 │                  │
        ▼                 ▼                  ▼
 Non-real-time        Cyclic I/O         Scheduled /
 functions            exchange           synchronized I/O
```

Standard TCP/IP communication remains available for functions that do not require deterministic cyclic behavior. PROFINET RT bypasses the TCP/IP layers for cyclic automation data and operates directly at Layer 2 using EtherType `0x8892`. IRT extends the real-time architecture with scheduled communication and precise synchronization for demanding applications such as motion control. This is fundamental to the research.

A packet observed during PROFINET device configuration may belong to an IP-based communication path, while the cyclic I/O traffic that follows may have no IP or TCP/UDP headers at all.

Conceptually:

```text
                 PROFINET System
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
      TCP/IP          DCE/RPC        RT / IRT
        │              │              │
        ▼              ▼              ▼
 Non-real-time      Startup /       Cyclic
 services           configuration   process data
```

The later research phases therefore need to identify the communication context of each frame before interpreting its payload.

# 2. PROFINET Roles

PROFINET IO primarily revolves around three logical roles:

```text
IO-Controller
      │
      │ controls / consumes / provides
      ▼
IO-Device

IO-Supervisor
      │
      └── engineering / diagnostics / commissioning
```

⟶ An **IO-Controller** is typically a PLC, DCS, PAC, or similar automation controller running the control program.

⟶ An **IO-Device** is a distributed field device such as an I/O station, sensor, actuator, drive, vision system, RFID reader, or other automation component.

⟶ An **IO-Supervisor** is typically an engineering workstation, programming device, or diagnostic system used for commissioning and maintenance.

The controller/device relationship is not simply equivalent to a conventional client/server relationship.

PROFINET uses a **provider/consumer model** for cyclic I/O:

```text
                 IO-Controller
                /             \
          Provider             Consumer
         Output Data          Input Data
              │                  ▲
              │                  │
              ▼                  │
             IO-Device
```

The controller provides output data consumed by the device, while the device provides input data consumed by the controller. Both sides can therefore have provider and consumer responsibilities depending on the direction of the process data.

This provider/consumer relationship becomes important in Phase 3 because a valid frame is not defined only by its Ethernet structure. The receiving side must also interpret its data according to the configured communication relationship.

# 3. PROFINET Device Model

A PROFINET IO-Device is represented as a hierarchical structure rather than a flat collection of bytes.

The simplified model is:

```text
IO-Device
    │
    ├── Device
    │
    ├── Module
    │      │
    │      ├── Submodule
    │      ├── Submodule
    │      └── ...
    │
    └── Module
           │
           └── Submodule
```

The exact structure depends on the device.

The important research concept is that the engineering system does not simply configure "a device." It configures a device together with its expected modules, submodules, process data, parameters, and diagnostics. PI describes the PROFINET device model in terms of Device, Module, and Channel structures, with cyclic input and output data exchanged according to the configured update cycle.

This gives the later research a vocabulary for interpreting configuration records:

```text
Device
  ↓
Module
  ↓
Submodule
  ↓
Process Data
```

The same hierarchy also becomes relevant during Application Relationship establishment because the controller and device must agree on the expected configuration.

# 4. GSDML & Engineering Configuration

The **General Station Description Markup Language (GSDML)** provides the XML-based device description used by PROFINET engineering systems.

A GSDML file describes characteristics including:

```text
Device Identification
       │
       ├── Vendor ID
       ├── Device ID
       │
       ▼
Device Structure
       │
       ├── Modules
       ├── Submodules
       ├── Process Data
       ├── Parameters
       ├── Diagnostics
       └── Alarms
```

The current GSDML specification describes GSDML as the mechanism for describing PROFINET device identification, structure, communication features, process data, parameters, and diagnostics.

The relationship can therefore be represented as:

```text
Manufacturer
     │
     ▼
   GSDML
     │
     ▼
Engineering Tool
     │
     ▼
Configured PROFINET Project
     │
     ▼
IO-Controller
     │
     ▼
Expected IO-Device Structure
```

GSDML is consequently more significant than a simple device metadata file. It provides the engineering system with the information required to understand what the device is capable of exposing and how its modules and process data are structured.

The research does not need to reproduce the complete GSDML schema. The relevant question is:

> How does the engineering description become the runtime configuration that the controller expects to find on the network?

That question connects GSDML to the later DCE/RPC and RT phases.

---

# 5. Device Identification

PROFINET devices have manufacturer-associated identification values.

The identification model includes:

```text
Vendor ID
    +
Device ID
    ↓
Device Identity
```

The Vendor ID is assigned to a company, while the Device ID is defined by the manufacturer for a particular device. These identifiers are also represented in the GSDML ecosystem.

This is separate from the **station name** used for operational device addressing and commissioning. That becomes important in Phase 1 because DCP can expose both identification and configuration information, but the values serve different purposes.

---

# 6. Station Names & IP Parameters

PROFINET uses a configured **station name** as an important device identity within the PROFINET IO system. The station name is distinct from the IP address.

Conceptually:

```text
PROFINET Identity
       │
       ├── Station Name
       │
       └── IP Parameters
             │
             ├── IP Address
             ├── Subnet Mask
             └── Gateway
```

During commissioning, a controller or engineering system can use PROFINET DCP to discover devices and assign parameters such as the station name and IP configuration. DCP is specifically used for identification and parameterization, including device searches during controller startup.

This creates an important architectural difference:

```text
DCP
 │
 ├── PROFINET identity / discovery
 │
 └── IP parameterization

DCE/RPC
 │
 └── Runtime configuration / AR establishment
```

The device can therefore participate in PROFINET commissioning before the complete IP-based runtime relationship has been established.

---

# 7. DCP & Layer-2 Discovery

The **Discovery and Configuration Protocol (DCP)** provides PROFINET device identification and parameterization functions at Layer 2.

DCP operates directly over Ethernet using PROFINET EtherType: `0x8892`. This is the same EtherType used for PROFINET RT traffic, meaning the PROFINET frame context must be examined before the payload is interpreted as DCP or RT. DCP can be used to search for devices and obtain information such as device identity and station name. It can also be used for parameterization operations.

A simplified startup sequence is:

```text
Controller / Engineering Tool
             │
             │ DCP discovery
             ▼
       PROFINET Devices
             │
             │ identification
             ▼
       Device information
             │
             │ parameterization
             ▼
       Station Name / IP
             │
             ▼
       Runtime startup
```

DCP discovery is therefore not equivalent to ordinary IP scanning. The relevant network boundary is the local Ethernet segment or Layer-2 domain where the DCP traffic is visible.

---

# 8. DCP Operations Relevant to the Research

The research only requires a small subset of the DCP model.

Conceptually:

```text
DCP
 │
 ├── Identify
 │
 ├── Get
 │
 ├── Set
 │
 └── Reset / related management operations
```


DCP requests are particularly important during startup and commissioning. PI's commissioning guidance notes that DCP multicasts are used to search for planned PROFINET devices and that excessive multicast activity can itself become a network-load concern.



The research should identify DCP operations from the DCP service fields and frame structure rather than treating `0xFEFE` as an Identify opcode. This matters because the research is intended to produce packet-level observations that can later be reproduced accurately.

---

# 9. LLDP & Physical Topology

PROFINET installations can also use **Link Layer Discovery Protocol (LLDP)** for network topology information. LLDP operates directly at Ethernet Layer 2 using EtherType: `0x88CC`.

The conceptual relationship is:

```text
Switch / Device
      │
      │ LLDP
      ▼
Neighbor Information
      │
      ├── Chassis ID
      ├── Port ID
      ├── System information
      └── Port relationships
```

LLDP therefore provides a different type of information from DCP.

```text
DCP
 │
 └── PROFINET device identity / configuration

LLDP
 │
 └── Ethernet neighbor / topology information
```

The combination is useful for network mapping:

```text
DCP
  ↓
"What PROFINET devices exist?"

LLDP
  ↓
"How are Ethernet nodes connected?"
```

This becomes the basis for the topology component of Phase 1.

---

# 10. Application Relationships

Once device discovery and addressing are complete, the controller must establish the runtime relationship through which it communicates with the IO-Device.

PROFINET represents this relationship using an **Application Relationship (AR)**.

A simplified model is:

```text
IO-Controller
      │
      │
      ▼
Application Relationship
      │
      ├── IO Communication
      ├── Alarm Communication
      └── Record / Acyclic Communication
      │
      ▼
IO-Device
```

The AR provides the context within which the controller and device establish their communication relationships.

---

# 11. Communication Relationships

Within an Application Relationship, PROFINET establishes different communication relationships for different classes of traffic.

The exact structures are more detailed than required for this primer, but the research needs to recognize three broad categories:

```text
Application Relationship
        │
        ├── IO-CR
        │     └── Cyclic IO data
        │
        ├── Alarm-CR
        │     └── Alarm communication
        │
        └── Record-CR
              └── Acyclic record access
```

This gives the later DCE/RPC research a useful abstraction:

```text
DCE/RPC
   │
   ▼
AR establishment
   │
   ├── IO communication context
   ├── Alarm communication context
   └── Record communication context
```

The exact negotiation fields, UUIDs, connection parameters, and record operations belong in Phase 2 rather than in this architecture primer. The important point here is simply that PROFINET does not jump directly from DCP discovery into cyclic process data. A communication relationship must first be established.

---

# 12. DCE/RPC & Acyclic Communication

PROFINET uses DCE/RPC for important acyclic communication and connection-establishment operations. In the conventional PROFINET architecture, the relevant IP transport is UDP with port `UDP/34964`

The communication path can therefore be represented as:

```text
PROFINET Application
        │
        ▼
      DCE/RPC
        │
        ▼
       UDP
        │
        ▼
     IP / Ethernet
```

This is fundamentally different from PROFINET RT:

```text
DCE/RPC
   ↓
UDP/IP
   ↓
Ethernet

PROFINET RT
   ↓
Ethernet Layer 2
```

The DCE/RPC phase is responsible for communication activities that cannot be represented simply as cyclic process-data frames. This includes connection establishment and access to acyclic records. The exact state transitions and RPC structures will be established experimentally in Phase 2.

---

# 13. Parameterization & Record Access

A PROFINET IO-Device contains more information than its cyclic process data. Acyclic record services can be used to exchange configuration, diagnostic, identification, and parameter information.

Conceptually:

```text
IO-Device
    │
    ├── Cyclic Process Data
    │
    └── Acyclic Records
            │
            ├── Parameters
            ├── Diagnostics
            ├── Identification / Maintenance
            └── Other defined records
```

This is important because the same device can expose two very different classes of communication:

```text
Cyclic
  ↓
Fast, periodic process data

Acyclic
  ↓
On-demand configuration / diagnostic / parameter data
```

The research therefore does not treat "PROFINET traffic" as one homogeneous stream.

---

# 14. Cyclic Real-Time I/O

Once the Application Relationship and relevant communication relationships are established, cyclic I/O data can flow between the controller and device.

The simplified model is:

```text
IO-Controller
      │
      │ cyclic output data
      ▼
 IO-Device
      │
      │ cyclic input data
      ▼
IO-Controller
```

The exchange occurs according to a configured update cycle.

PROFINET RT performs this cyclic exchange directly at Ethernet Layer 2 rather than through TCP/IP. PI describes the cyclic exchange as real-time communication using EtherType `0x8892`.

The architecture is therefore:

```text
+------------------ Ethernet ------------------+
| MAC | VLAN | PROFINET RT | IO Data | Status |
+----------------------------------------------+
```

The exact frame structure will be dissected during Phase 3.

---

# 15. Provider / Consumer State

Cyclic data is accompanied by information that allows the receiving side to evaluate whether the data is usable.

A simplified model is:

```text
Provider
   │
   │ Data
   │ Status
   │ Cycle Information
   ▼
Consumer
   │
   ├── Data received?
   ├── Data current?
   ├── Data valid?
   └── Communication healthy?
```

PROFINET's system description identifies provider and consumer status information, data status, transfer status, and cycle information as part of the cyclic communication model. The receiving side can use these fields to determine whether the cyclic data is valid and whether the communication relationship remains healthy. This provides the conceptual foundation for Phase 3.

The research question is:

> Which fields does the consumer use to decide whether the received cyclic data belongs to the expected communication relationship and whether that data is valid?

That will become important when testing manipulated payloads, sequence values, and timing behavior.

---

# 16. Cycle Timing & Watchdog Behavior

Cyclic communication depends on timing.

A simplified model is:

```text
Cycle N
   │
   ▼
Expected update
   │
   ▼
Cycle N+1
   │
   ▼
Expected update
   │
   ▼
Cycle N+2
```

The consumer monitors whether expected data continues to arrive within the configured monitoring interval. If the expected data stops arriving for long enough, the communication relationship can be considered failed and the application can transition into an error or fallback state.

PI's system description explicitly describes time monitoring derived from the configured update time and states that failure of cyclic data to arrive within the monitoring time is monitored by the respective consumer. This is the baseline for the watchdog and resiliency experiments in Phase 4.

The exact timeout calculation should be established from the implementation and configuration under test rather than assumed to be identical across every PROFINET device.

---

# 17. Real-Time and Isochronous Real-Time

PROFINET provides more than one real-time performance model.

The research primarily concerns ordinary **PROFINET RT**, but the architectural difference from **IRT** is important.

```text
Standard TCP/IP
      │
      └── Non-deterministic functions

PROFINET RT
      │
      └── Real-time cyclic I/O

PROFINET IRT
      │
      └── Precisely scheduled / synchronized traffic
```

PROFINET RT is designed for typical real-time I/O applications, while IRT introduces scheduled communication and tighter synchronization for applications such as motion control. PI describes RT operation in the millisecond range and IRT as supporting sub-millisecond cycles with very low jitter when appropriate hardware support is used.

The research therefore avoids treating every `0x8892` frame as equivalent. The communication timing model depends on the configured PROFINET service and device capabilities.

# 18. Ethernet, VLAN & Priority Context

Because PROFINET is based on Ethernet, Layer-2 fields become part of the communication environment.

A simplified RT frame can be viewed as:

```text
Destination MAC
       │
       ▼
Source MAC
       │
       ▼
802.1Q VLAN / PCP
       │
       ▼
EtherType 0x8892
       │
       ▼
PROFINET Frame
       │
       ▼
IO Data / Status
```

VLAN tagging is not mandatory in every deployment, but when present, the VLAN ID and Priority Code Point (PCP) become relevant to traffic separation and prioritization. This matters for the research because a frame's meaning cannot always be determined from its application payload alone.

The surrounding Ethernet context may include:

```text
MAC addresses
VLAN ID
PCP
EtherType
Frame ID
Cycle information
Status information
```

Phase 3 will therefore begin with the Ethernet boundary before descending into the cyclic payload.

# 19. Configuration-to-Wire Relationship

The most important architectural relationship for this research is the connection between engineering configuration and runtime traffic.

The complete chain can be represented as:

```text
                 GSDML
                   │
                   ▼
          Engineering Project
                   │
                   ▼
            IO-Controller
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
      Expected           Network
      Device Model       Parameters
          │                 │
          └────────┬────────┘
                   ▼
          DCP Commissioning
                   │
                   ▼
        Application Relationship
                   │
             ┌─────┴─────┐
             ▼           ▼
          DCE/RPC        RT
          Acyclic      Cyclic
             │           │
             └─────┬─────┘
                   ▼
             Physical I/O
```

This means the packet capture is only the final representation of a much larger configuration process. A cyclic RT frame cannot be interpreted correctly without understanding the communication relationship that caused the frame to exist. Likewise, a DCP station name cannot be treated as arbitrary metadata because it participates in the identification and commissioning process. The research therefore moves from configuration to network behavior rather than beginning with packet bytes in isolation.

# 20. DCP, DCE/RPC and RT as One Startup Sequence

The architecture can now be reduced to a simplified operational sequence:

```text
             Engineering / Controller
                       │
                       ▼
                DCP Discovery
                       │
                       ▼
              Identify Device
                       │
                       ▼
           Assign / Verify Parameters
                       │
                       ▼
                IP Connectivity
                       │
                       ▼
              DCE/RPC Connect
                       │
                       ▼
          Establish Application Relationship
                       │
                       ▼
            Configure Communication
                       │
                       ▼
                 Application Ready
                       │
                       ▼
              Cyclic RT Exchange
                       │
                       ▼
              Process Interaction
```

This sequence is the backbone of the research.

Phase 1 begins before the controller has established its runtime relationship. Phase 2 examines the transition into that relationship. Phase 3 examines the cyclic communication that exists after the relationship is active. Phase 4 asks what happens when the network or communication conditions become abnormal. Phase 5 examines the security mechanisms applied across these boundaries.

# 21. Security Boundary Baseline

PROFINET security should not be reduced to one cryptographic mechanism.

The security architecture has evolved from a defense-in-depth model toward additional protocol-level protections, including cryptographic mechanisms and certificate-based device and operator authentication in newer security profiles. PI currently describes PROFINET security as combining plant/network protections with protocol-level security features, while its current specification material includes dedicated PROFINET security profiles.

For this research, the useful concept is:

```text
                    PROFINET
                       │
        ┌──────────────┼──────────────┐
        │              │              │
       GSDML          DCP          Runtime
        │              │              │
        ▼              ▼              ▼
 Configuration      Device        AR / RT
    Trust           Identity     Communication
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                Security Controls
```

# 22. Security Classes and Evolving PROFINET Security

Earlier PROFINET security documentation described a three-class model:

```text
Security Class 1
      ↓
Robustness

Security Class 2
      ↓
Integrity + Authenticity

Security Class 3
      ↓
Confidentiality
```

The earlier security-class proposal described Class 1 in terms including read-only DCP operation and protection of GSD files against unauthorized modification, while Classes 2 and 3 added cryptographic protection and stronger confidentiality properties.

However, this research does not freeze those descriptions into the architecture as though every PROFINET device implements them identically.

PI's current material shows that PROFINET security is evolving. Current PROFINET V2.5 material introduces newer security mechanisms and changes the treatment of security classes, while the current security documentation continues to describe Security Class 1/2/3 as part of the broader PROFINET security concept.

# 23. Security Characteristics

PROFINET is best understood as an **Industrial Ethernet communication architecture for controller-to-device automation**, rather than a single packet format or transport protocol.

The key architectural characteristics established for the research are:

* **PROFINET uses standard Ethernet as its underlying communication technology**, while adding communication mechanisms designed for industrial automation.
* **PROFINET supports multiple communication paths**, including standard TCP/IP, PROFINET RT, and PROFINET IRT.
* **IO-Controllers and IO-Devices communicate through a provider/consumer model**, rather than relying exclusively on a conventional client/server model.
* **The PROFINET device model is hierarchical**, with Device, Module, and Submodule structures defining the configured I/O system.
* **GSDML provides the XML-based engineering description** of device identification, structure, communication capabilities, process data, parameters, diagnostics, and related device information.
* **Vendor ID and Device ID identify the device type**, while the station name participates in PROFINET device identification and commissioning.
* **DCP operates at Layer 2** and is used for PROFINET device discovery and parameterization, including station-name and IP-parameter assignment.
* **DCP and PROFINET RT use EtherType `0x8892`**, so the protocol context must be determined from the frame contents rather than EtherType alone.
* **LLDP provides Layer-2 neighbor and topology information**, complementing DCP's device-oriented discovery.
* **DCE/RPC provides an IP-based communication path for important acyclic and connection-establishment operations**, including Application Relationship establishment.
* **An Application Relationship connects the controller and device into a runtime communication context**, containing communication relationships for cyclic I/O and other services.
* **PROFINET RT carries cyclic I/O directly over Ethernet Layer 2**, without TCP/IP in the cyclic data path.
* **Cyclic communication includes status and timing information** that allows consumers to evaluate data validity and communication health.
* **Timing and watchdog behavior are part of the communication model**, meaning loss or delay of cyclic data can cause the communication relationship to transition into an error state.
* **PROFINET IRT extends the real-time model with scheduled and synchronized communication** for applications requiring tighter timing characteristics.
* **Engineering configuration and runtime network behavior are directly connected**. GSDML defines the device capabilities and structure that the engineering system uses to construct the expected runtime configuration.
* **PROFINET security is an evolving architecture**, combining defense-in-depth with protocol-level security mechanisms and newer security profiles. Security behavior must therefore be verified against the specification version and implementation under test rather than inferred from historical security-class descriptions.

The subsequent research can therefore move from **what the PROFINET system is configured to be**, to **what a local Ethernet participant can discover and modify**, to **how an Application Relationship is established**, and finally to **what the cyclic I/O path actually trusts**.
