# Phase 3: Real-Time Cyclic I/O & State Machine Analysis

## Executive Summary

Phase 3 examines PROFINET Real-Time (RT) Class 1 traffic at the Ethernet Layer 2 boundary, with emphasis on cyclic frame structure, process-data placement, status fields, transmission timing, and controlled frame generation.

Unlike Phases 1 and 2, this phase was not conducted against the p-net `pn_dev` application as a functioning PROFINET IO-Device. The same p-net configuration used during the earlier phases did not produce usable cyclic RT traffic in the laboratory environment. Rather than infer behavior from the absence of traffic, a dedicated Python traffic-generation harness was introduced to provide a controlled source of RT frames.

This is fundamental to the interpretation of the results. `pn_rt_traffic_generator.py` constructs and transmits Ethernet frames containing the observed PROFINET RT structure. It is not a PROFINET IO-Device implementation and does not establish an Application Relationship (AR), negotiate IOCR parameters, maintain a process-data relationship, or demonstrate receiver-side acceptance.

The resulting capture therefore provides evidence about **the structure and behavior of the controlled RT traffic generated during the experiment**. It does not establish how a production PROFINET controller or IO-Device would interpret, accept, reject, or react to the crafted frames.

The analysis identified a consistent RT frame structure with Frame ID `0x8000`, a 40-byte IO/application-data region, an actual PROFINET Cycle Counter of `0x0000`, DataStatus `0x35`, and TransferStatus `0x00`. The sequential values initially interpreted as cycle counters were located inside the application-data region and are therefore treated as application-level values.

The capture contained 515 RT frames over 16.055062 seconds. No 144 ms silence interval, PN-IO diagnostic/alarm traffic, or DataStatus/TransferStatus transition was observed.

## 1. Experimental Boundary

Phases 1 and 2 used the p-net sample application as the protocol endpoint:

```text
sudo ip netns exec ns-device ./p-net/build/pn_dev \
    -i veth-device \
    -s rt-labs-dev \
    -v
```

Phase 1 exercised Layer 2 discovery behavior through DCP and LLDP. Phase 2 exercised the DCE/RPC connection path and observed the associated PROFINET Application Relationship establishment behavior.

For Phase 3, monitoring the same `pn_dev` configuration produced:

```text
! No PROFINET RT frames captured.
Phase 3 aborted: no usable RT traffic.
```

No assumption was made that the missing RT traffic represented a protocol-level failure. Instead, a separate controlled traffic source was introduced:

```text
sudo ip netns exec ns-device \
    python3 scripts/pn_rt_traffic_generator.py veth-device
```

The generator was designed specifically to provide deterministic RT frames for packet-level analysis.

### 1.1 What the Generator Is

`pn_rt_traffic_generator.py` is a Layer 2 packet-generation harness.

It constructs Ethernet frames containing:

* PROFINET RT EtherType `0x8892`
* Frame ID `0x8000`
* 40 bytes of controlled IO/application data
* a PROFINET RT cyclic trailer
* controlled transmission timing

The harness also provides controlled application-data values for injection experiments.

### 1.2 What the Generator Is Not

The generator is not a complete PROFINET IO-Device stack.

It does not:

* establish a PROFINET Application Relationship
* negotiate an IOCR
* perform DCE/RPC connection establishment
* maintain controller/device state
* expose a process image through a PROFINET stack
* demonstrate controller-side process-data acceptance
* generate evidence of real IO-Device state transitions
* reproduce the behavior of a production PROFINET endpoint

Consequently, Phase 3 findings are limited to what was observable at the Ethernet frame boundary and what was directly produced by the controlled harness.

## 3. PROFINET RT Frame Structure

The captured 60-byte Ethernet frames consistently followed this layout:

```text
Ethernet:
  0–5     Destination MAC
  6–11    Source MAC
  12–13   EtherType = 0x8892

PROFINET RT:
  14–15   Frame ID = 0x8000
  16–55   40 bytes IO/application data
  56–57   Cycle Counter = 0x0000
  58      DataStatus = 0x35
  59      TransferStatus = 0x00
```

Relative to the start of the PROFINET RT payload:

```text
+00–01  Frame ID
+02–41  IO/application data
+42–43  Cycle Counter
+44     DataStatus
+45     TransferStatus
```

This layout was established directly from the captured frames.

A critical correction from the initial analysis is that the sequential values found near the beginning of the 40-byte data region are **not the PROFINET Cycle Counter**. The actual Cycle Counter is located at offsets 56–57 of the Ethernet frame and remained `0x0000` throughout the capture.

## 5. Application-Level Sequencing

The first two bytes of the 40-byte IO/application region contained a sequential value.

Examples from the capture include:

```text
Frame 1:    00 01
Frame 2:    00 02
...
Frame 254:  00 FE
Frame 255:  00 FF
Frame 256:  01 00
...
Frame 345:  01 59
```

This value continued to increase through the capture. Because the actual PROFINET Cycle Counter at offsets 56–57 remained `0x0000`, these sequential values are classified as **application-level data generated by the harness**, rather than protocol-level cycle counters. That is important when discussing freshness.

The observed application sequence demonstrates deterministic sequencing within the generated process-data region. It does not establish that the value is used by a PROFINET controller as a protocol freshness mechanism.

---

## 6. DataStatus Analysis

Every captured frame contained:

```text
DataStatus = 0x35
```

Binary representation:

```text
0x35 = 00110101
       ||||||||
       |||||||+-- Primary
       ||||||+--- Redundancy
       |||||+---- DataValid
       |||+------ Reserved
       ||+------- ProviderState
       |+-------- StationProblemIndicator
       +--------- Ignore
```

Using the PROFINET RT DataStatus interpretation:

| Bit | Value | Interpretation                |
| --- | ----: | ----------------------------- |
| 7   |     0 | Evaluate                      |
| 6   |     0 | Reserved                      |
| 5   |     1 | Station Problem Indicator: OK |
| 4   |     1 | Provider State: Run           |
| 3   |     0 | Reserved                      |
| 2   |     1 | Data Valid                    |
| 1   |     0 | One primary AR present        |
| 0   |     1 | Primary                       |

The important observation is that these values remained constant across all 515 captured frames. No DataStatus transition was observed during the injection experiment.

Because the frames were generated by a controlled harness rather than a complete PROFINET IO-Device relationship, the constant `0x35` value should be interpreted as a property of the generated traffic, not as evidence of a real device remaining in RUN state.

---

## 7. TransferStatus Analysis

All 515 frames contained:

```text
TransferStatus = 0x00
```

No non-zero TransferStatus value was observed. The capture therefore provides no example of a generated frame carrying a TransferStatus condition that instructs the receiver to ignore the frame.

## 8. Stage 2: Controlled Process-Data Injection

The second stage modified values inside the 40-byte IO/application region while preserving the surrounding RT frame structure generated by the harness.

The injected application-data pattern was: `FF 00 AA 55` . The complete beginning of the application-data region therefore appeared as: `00 01 FF 00 AA 55` , where: `00 01` is the harness-generated application sequence and: `FF 00 AA 55` is the controlled payload pattern.

The actual PROFINET RT trailer remained:

```text
00 00 35 00
```

corresponding to:

```text
Cycle Counter:  0x0000
DataStatus:     0x35
TransferStatus: 0x00
```

The capture contains ten frames carrying the primary injected pattern:

```text
Frame 346  00 01 FF 00 AA 55
Frame 348  00 02 FF 00 AA 55
Frame 350  00 03 FF 00 AA 55
...
Frame 364  00 0A FF 00 AA 55
```

These values were therefore placed inside the application-data region and did not modify the PROFINET RT trailer.

### 8.1 Secondary Injection Sequence

A second generated sequence followed the primary pattern:

```text
Frame 366  00 0B 00 00 00 00
Frame 368  00 0C 00 00 00 00
Frame 370  00 0D 00 00 00 00
Frame 372  00 0E 00 00 00 00
Frame 374  00 0F 00 00 00 00
```

Again, these values were located inside the application-data region.

## 9. Injection Timing and Traffic Interleaving

The capture shows the injection frames appearing between frames produced by the baseline traffic generator.

For example:

```text
Frame 345  normal
Frame 346  injected
Frame 347  normal
Frame 348  injected
Frame 349  normal
Frame 350  injected
...
```

This observation must be interpreted specifically as **harness behavior**. The generator continued producing its baseline frames while the injection routine emitted additional crafted frames. The resulting capture therefore contains traffic from both generation paths.

This does not demonstrate how a PROFINET controller or IO-Device would arbitrate between competing RT frames. It also does not demonstrate that the injected frames replaced, displaced, or were accepted instead of legitimate process data by a PROFINET endpoint.

The normal application sequence in the baseline generated traffic continued through the injection interval, for example:

```text
Frame 345  0x0159
Frame 347  0x015A
Frame 349  0x015B
...
Frame 365  0x0163
Frame 367  0x0164
Frame 369  0x0165
...
```

This demonstrates continuity of the **generator's own baseline sequence**, not continuity of a real PROFINET IO relationship.

# 10. Timing Analysis

The baseline generator operated with an approximately 32 ms transmission interval.

Observed timing around the injection sequence included:

```text
Frame 344 → 345    ~32.191 ms
Frame 345 → 346    ~15.121 ms
Frame 346 → 347    ~17.035 ms
Frame 347 → 348    ~15.162 ms
Frame 348 → 349    ~17.004 ms
```

The injection therefore occupied time within the baseline transmission schedule rather than producing a long period of silence.

The largest packet-to-packet gap observed across the capture was approximately:

```text
33.972 ms
```

No 144 ms silence interval was observed.

## 11. Stage 3: Watchdog Timing Model

A watchdog model was included to evaluate the relationship between the configured 32 ms cycle interval and a hypothetical retention factor of three cycles:

```text
Cycle Time:       32 ms
Retention Factor: 3
Watchdog Model:   96 ms
```

A 144 ms interval was retained as a reference value for testing a silence condition:

```text
Reference Silence: 144 ms
```

The experiment did not suppress the traffic generator for 144 ms. Consequently, the capture cannot be used as evidence of a real PROFINET watchdog timeout.

The actual capture showed:

```text
Maximum observed packet gap: ~33.972 ms
144 ms silence:              Not observed
PN-IO alarm traffic:         Not observed
```

The 96 ms value is therefore a **laboratory timing model**, not a claim that 96 ms represents a universal PROFINET watchdog threshold.

# 12. Diagnostic and Alarm Traffic

The capture contained only:

```text
EtherType: 0x8892
Frame ID:  0x8000
```

across all 515 packets. No separate PN-IO diagnostic or alarm traffic was identified. Therefore, the experiment does not demonstrate a PN-IO diagnostic/alarm response to the generated traffic. Any claim about a real controller entering a fault state or generating an alarm would require a separate experiment involving a functioning PROFINET endpoint and capture of the resulting diagnostic traffic.

## 13. Security Analysis

### 13.1 Layer 2 Injection Surface

The experiment demonstrates that a Linux host with appropriate Layer 2 access can construct and transmit Ethernet frames carrying the observed PROFINET RT structure using a raw socket.

The controlled harness successfully emitted frames with:

```text
EtherType:       0x8892
Frame ID:        0x8000
Application data: controlled values
Cycle Counter:   0x0000
DataStatus:      0x35
TransferStatus:  0x00
```

This establishes a packet-generation capability at the Ethernet boundary. It does not establish successful impersonation of a real IO-Device.

### 13.2 Protocol State Is Not Cryptographic Authentication

The observed RT trailer contains fields representing protocol state and data handling information, including:

* Cycle Counter
* DataStatus
* TransferStatus

These fields provide protocol semantics and freshness/state-related information, they should not be treated as cryptographic authentication credentials. Matching a frame's visible structural fields does not, by itself, demonstrate that a receiver will trust the source or accept the associated process data.

### 13.3 Receiver Acceptance Remains Untested

No functioning PROFINET controller was used in Phase 3 to verify whether the generated frames modified a real process image or affected an established IO relationship.

Therefore, the following remain outside the evidence produced by this experiment:

* controller-side acceptance
* process-image modification
* IO-Device impersonation
* AR hijacking
* state transition caused by crafted traffic
* real watchdog expiration
* PN-IO diagnostic generation
* safety impact

These would require receiver-side experimentation.

---

## 14. Architectural Security Implications

The experiment establishes a useful boundary-level observation:

> **PROFINET RT Class 1 traffic can be constructed and transmitted directly at Ethernet Layer 2 without reproducing the complete PROFINET connection-management stack.**

That makes Layer 2 access an important security boundary for PROFINET environments.

However, the security significance of a crafted frame depends on the behavior of the receiving endpoint. A packet that is structurally similar to observed RT traffic is not automatically equivalent to legitimate process data. The Phase 3 harness therefore demonstrates the **ability to generate candidate RT traffic**, while leaving endpoint acceptance as a separate research question. This separation is important when assessing real-world attack paths.

---

## 15. Defense and Remediation Considerations

### Network Segmentation

PROFINET RT traffic should remain within appropriately controlled industrial network segments. Limiting unnecessary Layer 2 access reduces the number of systems capable of transmitting candidate RT traffic.

### Layer 2 Access Control

Switch-level controls and network architecture should restrict unauthorized hosts from gaining direct access to PROFINET segments.

### Passive Monitoring

Monitoring can identify unexpected sources, Frame IDs, timing patterns, and changes in process-data characteristics. Because RT traffic is highly timing-sensitive, deviations from an established baseline can provide useful detection signals.

### Endpoint Validation

Security testing should verify how individual PROFINET controllers and IO-Devices validate:

* source relationships
* Application Relationships
* IOCR context
* sequence behavior
* DataStatus
* timing
* watchdog conditions

These behaviors are implementation-specific and should not be inferred solely from packet construction.

### Safety Separation

Where safety functions are involved, the security properties of standard PROFINET RT should not be conflated with PROFIsafe guarantees. PROFIsafe was outside the scope of this phase.

## 17. Key Takeaways

1. Phases 1 and 2 used the p-net `pn_dev` implementation as the PROFINET protocol endpoint.
2. Phase 3 used a separate controlled Python traffic generator because the tested `pn_dev` configuration did not produce usable cyclic RT traffic.

3. `pn_rt_traffic_generator.py` is a packet-generation harness, not a complete PROFINET IO-Device.

4. The Phase 3 PCAP therefore represents controlled Layer 2 RT traffic generation rather than a complete controller-to-device cyclic I/O relationship.

5. The observed Ethernet frames used EtherType `0x8892` and Frame ID `0x8000`.

6. The 40-byte IO/application region was located between the Frame ID and cyclic trailer.

7. The actual PROFINET Cycle Counter was `0x0000` in every captured frame.

8. The sequential values initially interpreted as cycle counters were actually located inside the application-data region.

9. DataStatus remained `0x35` and TransferStatus remained `0x00` across the entire capture.

10. The `FF 00 AA 55` pattern was transmitted as controlled application data, not as a PROFINET status or cycle field.

11. Additional generated frames were interleaved with baseline generated traffic. This demonstrates behavior of the harness, not arbitration or acceptance behavior of a PROFINET endpoint.

12. The maximum observed packet gap was approximately 33.972 ms. No 144 ms silence condition occurred.

13. No PN-IO diagnostic or alarm traffic was observed.

14. The experiment demonstrates the ability to construct and transmit candidate PROFINET RT frames at Layer 2, but does not demonstrate receiver-side acceptance or process-image manipulation.

15. Protocol state and freshness-related fields should not be treated as equivalent to cryptographic source authentication.

16. A meaningful next step for endpoint-security research would require a functioning PROFINET controller/IO-Device pair capable of receiving the generated frames and exposing observable acceptance, rejection, watchdog, or process-image behavior.
