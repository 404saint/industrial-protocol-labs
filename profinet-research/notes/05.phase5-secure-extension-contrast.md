# Phase 5: Secure Extension Contrast

## Executive Summary

The first four phases of this research examined PROFINET from the wire outward. Phase 1 established the Layer 2 discovery surface through DCP and LLDP. Phase 2 examined acyclic application-relation establishment through DCE/RPC. Phase 3 analyzed cyclic PROFINET RT framing and established the actual position of the Cycle Counter, DataStatus, and TransferStatus fields. Phase 4 then examined the ability of an external Layer 2 host to generate high-rate, discovery-oriented, and malformed traffic against a real `pn_dev` environment.

Phase 5 takes a different approach.

Rather than introducing another laboratory experiment without a security-capable implementation, this phase compares those empirical observations against the security architecture defined by PROFIBUS & PROFINET International (PI). The analysis covers the historical Security Class 1/2/3 model, the later security extensions, and the current PROFINET V2.50 architecture.

This comparison reveals an important evolution. Earlier PI security material described three security classes: Security Class 1 for robustness, Security Class 2 for integrity and authenticity, and Security Class 3 for confidentiality. Security Class 1 focused on measures such as signed GSD files, hardened SNMP behavior, and read-only DCP configuration. Security Classes 2 and 3 extended the model toward cryptographic protection of communication and confidentiality.

The current PROFINET V2.50 specification moves beyond that original class model. PI describes a dedicated Security Profile, secure-capable successors to protocols such as CLRPC and RSI, SXP over Layer 3 and Layer 2, secure provisioning using IDevID and certificates, and Secure SXP over TCP. GSDML V2.50 introduces the `SecureAccess` and `SecureRealtime` application classes and removes Security Classes 2 and 3 from the GSDML security model.

The result is not a claim that the laboratory implementation used during Phases 1–4 provides these protections. It does not. Instead, Phase 5 identifies where the observed protocol behavior sits relative to the security mechanisms defined by PI and where a security-capable implementation would change the trust model.

---

## 1. Research Boundary

Phase 5 is a specification-driven analysis.

No new cryptographic implementation was introduced into the laboratory. No certificates were provisioned into `pn_dev`. No attempt was made to simulate Security Classes 1–3 using a packet generator. No encrypted cyclic stream was fabricated and presented as a genuine PROFINET security implementation.

The reason is methodological.

A packet generator can reproduce the shape of an Ethernet frame, but it cannot establish that a genuine PROFINET security mechanism has been implemented. Cryptographic authentication, certificate validation, secure provisioning, key lifecycle management, secure application relations, and protected real-time communication all depend on implementation behavior that cannot be inferred from manually constructed packets.

The laboratory evidence from Phases 1–4 is therefore retained as empirical evidence, while the security mechanisms discussed in this phase are treated as specification-defined capabilities.

The analysis asks four questions:

1. What security mechanisms does PI define?
2. Which protocol boundaries from Phases 1–4 do those mechanisms address?
3. What would change in the trust model if those mechanisms were implemented?
4. Which security properties remain outside the evidence collected by this laboratory?

## 2. Source and Specification Basis

The primary source is the official PROFINET specification material published by PROFIBUS & PROFINET International.

PI's current specification repository identifies PROFINET V2.5 as a major security revision. The V2.5 specification introduces a dedicated Security Profile and describes security-related structural changes across the Service, Protocol, Profile, and Security Profile documents. PI also identifies SXP over Layer 3 and Layer 2, secure provisioning using IDevID and certificates, and Secure SXP over TCP as part of the newer architecture.

The analysis also uses PI's published security material covering the evolution toward the security-class model and the current security guidance. PI's 2019 Security Extensions white paper describes the security objectives and the proposed three-class architecture, while the Security Class 1 guideline documents the initial robustness-oriented mechanisms.

The current PI Security material also identifies the newer PROFINET Design Guideline Security as the operational guidance for planning, commissioning, and operation of secure PROFINET installations.

## 3. The Evolution of PROFINET Security

PROFINET security has not remained a single fixed mechanism.

The earlier security model organized protection into three classes:

| Security Class | Security objective       | Historical scope                                                   |
| -------------- | ------------------------ | ------------------------------------------------------------------ |
| Class 1        | Robustness               | Hardened DCP/SNMP behavior and signed GSD files                    |
| Class 2        | Integrity + Authenticity | Cryptographic protection of assets and communication relationships |
| Class 3        | Confidentiality          | Class 2 protections plus confidentiality                           |

PI's 2019 security white paper describes Security Class 1a as a robustness-oriented extension, including configurable SNMP defaults, read-only DCP commands, and signatures protecting GSD files. Class 2 adds cryptographic integrity and authenticity for assets and communication relationships, while Class 3 extends the protection to confidentiality.

The model was subsequently incorporated into PROFINET and GSDML development. GSDML V2.45, for example, included explicit Security Class 2/3 dependencies on Security Class 1 and related cryptographic algorithm updates. The current architecture is different.

GSDML V2.50 introduces two ApplicationClasses:

```text
SecureAccess
SecureRealtime
```

and removes Security Classes 2 and 3 from the GSDML model.

At the protocol level, PI describes V2.5 as introducing secure-capable successors to protocols that previously lacked a secure variant, including SXP over Layer 3 and SXP over Layer 2. Secure provisioning using IDevID and certificates is also introduced, along with Secure SXP over TCP.

This evolution matters for the laboratory analysis because the older Security Class terminology should not be presented as the complete current PROFINET security architecture.

## 4. Phase 1 Contrast: DCP, LLDP and Discovery

Phase 1 demonstrated that a PROFINET device can expose meaningful information before conventional IP-layer communication becomes relevant.

The laboratory observed:

* DCP Identify traffic
* station name
* vendor and device identifiers
* IP configuration
* DCP Set behavior
* LLDP chassis and port information
* Layer 2 multicast communication

The DCP station name observed from the p-net device was:

```text
rt-labs-dev
```

The laboratory also attempted to change the station name. The target continued to report `rt-labs-dev`, and the update did not take effect.

### Security Class 1 Context

The historical Security Class 1 model directly addresses this type of configuration surface.

PI describes Security Class 1 as including the ability to place DCP commands into a read-only mode and to protect GSD files against unnoticed modification through signing. The same security model also includes hardening of SNMP defaults. This provides an important comparison.

The Phase 1 laboratory demonstrated that DCP is a meaningful configuration and discovery surface. The security specification subsequently identifies controls intended to reduce the ability of unauthorized actors to use that surface for configuration changes.

The laboratory's observation that the attempted station-name update did not take effect is therefore interesting, but it should not be retroactively labeled as Security Class 1 enforcement. The lab did not prove which internal mechanism prevented the change.

### LLDP Boundary

The Phase 1 capture also demonstrated LLDP information including chassis identity, port identity, system name, and TTL. The presence of LLDP information is important from an asset-discovery perspective. However, the Phase 1 experiment did not establish a cryptographic security property for LLDP.

This reinforces a broader architectural point:

```text
PROFINET security mechanisms
          │
          ├── Protect selected PROFINET assets
          │
          └── Do not automatically turn every
              Ethernet discovery mechanism into
              an authenticated channel
```

A security assessment therefore still has to account for Layer 2 discovery and topology information separately from authenticated application communication.

## 5. GSD and GSDX Integrity

GSD files are part of the engineering and device-description ecosystem around PROFINET. The historical Security Class 1 model introduced protection of GSD files against unnoticed modification through digital signatures. PI's Security Class 1 material identifies signed GSD files as one of the initial security extensions. This mechanism addresses a different asset from the cyclic process data examined in Phase 3.

The relevant security boundary is:

```text
Engineering artifact
       │
       ▼
GSD / GSDX
       │
       ▼
Engineering environment
       │
       ▼
Device configuration
```

The purpose is therefore asset integrity and authenticity rather than real-time packet confidentiality. This is important when interpreting the term "PROFINET security." A signed device description does not protect a cyclic RT packet. Likewise, cryptographic protection of communication does not automatically establish the integrity of an engineering artifact.

The security architecture therefore has to be evaluated by asset and communication boundary rather than by a single protocol-wide security switch.

## 6. Phase 2 Contrast: DCE/RPC and Application Relations

Phase 2 examined PROFINET acyclic communication using DCE/RPC over UDP/34964.

The laboratory observed:

* DCE/RPC version field
* request and response packet types
* interface UUID
* opnum `122`
* request/response association
* AR-related request blocks
* IOCR-related request blocks
* AlarmCR-related request blocks
* application-level progression through the p-net connection process

The capture demonstrated the mechanics of the exchange, but did not demonstrate cryptographic authentication.

## Historical Security Class Model

The historical Security Class 2 definition places integrity and authenticity around assets and communication relationships. PI's 2019 material specifically describes cryptographic protection of communication relationships as part of Class 2. That is directly relevant to Phase 2.

The Phase 2 AR handshake demonstrated that a communication relationship can be established through protocol identifiers and state transitions. Those identifiers are useful for protocol operation, but they are not equivalent to cryptographic proof of peer identity.

An ARUUID, interface UUID, or DCE/RPC opnum tells the protocol what relationship or operation is being referenced. It does not, by itself, establish that the remote endpoint is an authorized cryptographic principal.

The security architecture therefore introduces a second layer of trust:

```text
Protocol relationship
        │
        ├── ARUUID
        ├── IOCR parameters
        └── RPC operation
               
Security relationship
        │
        ├── Device identity
        ├── Credential
        ├── Trust anchor
        └── Cryptographic verification
```

The Phase 2 laboratory examined the first layer. This phase examines the second.

## 7. Device Identity and IDevID

Current PI security development places significant emphasis on device identity and secure provisioning. The V2.5 PROFINET specification identifies secure provisioning using IDevID and certificates as part of the new security architecture.

PI's Industrial Automation Security Harmonization Group also describes IDevID as an IEEE 802.1AR secure device identifier. The published profile describes an IDevID as a manufacturer-provided identity represented by an X.509 v3 certificate and intended to support secure device authentication and onboarding. This changes the meaning of device identity.

In Phase 1, the laboratory observed identifiers such as:

```text
Station Name
Vendor ID
Device ID
MAC address
```

These identifiers are useful for discovery and protocol operation. An IDevID introduces a cryptographically protected identity rooted in manufacturer-provisioned credentials.

Conceptually:

```text
Phase 1 identity

MAC ────────────────┐
Station Name ───────┤
Vendor / Device ID ─┘
        │
        ▼
Protocol identity


Secure provisioning identity

Manufacturer
     │
     ▼
 IDevID / X.509
     │
     ▼
 Device identity
     │
     ▼
 Cryptographic verification
```

The second model provides a substantially stronger basis for authentication because identity is tied to a credential and a trust model rather than merely to observable protocol fields.

## 8. Phase 3 Contrast: Cyclic PROFINET RT

Phase 3 was the most important empirical reference point for secure real-time analysis.

The laboratory captured 515 PROFINET RT frames using:

```text
EtherType:       0x8892
Frame ID:        0x8000
Cycle Counter:   0x0000
DataStatus:      0x35
TransferStatus:  0x00
```

The investigation also established that the sequential values previously interpreted as the PROFINET Cycle Counter were actually part of the 40-byte application/process-data region. The actual Cycle Counter remained `0x0000` throughout the analyzed capture. This correction is significant because it prevents application payload data from being mistaken for a protocol security mechanism.

## Freshness Is Not Authentication

The Phase 3 traffic demonstrated protocol-level state and timing information.

The DataStatus value `0x35` indicated:

* Primary state
* one primary AR present
* DataValid
* ProviderState Run
* StationProblemIndicator indicating OK
* Ignore bit clear

The TransferStatus value was `0x00`. These mechanisms help communicate the state and validity of cyclic data. They do not constitute cryptographic identity. A packet can contain internally consistent state indicators without proving who generated it.

That was one of the central security observations from Phase 3:

```text
Freshness / state
        ≠
Cryptographic authenticity
```

The current PROFINET security architecture addresses this broader problem through secure communication mechanisms rather than relying on application-state fields alone.

PI's V2.5 specification material specifically describes security integration and the introduction of secure-capable communication mechanisms, including SXP over Layer 2 and Layer 3. It also describes security-related changes affecting real-time communication and symmetric key updates in the V2.4 development path.

## 9. SecureRealtime and Cyclic Communication

GSDML V2.50 introduces the `SecureRealtime` ApplicationClass while removing Security Classes 2 and 3 from the GSDML security model.

This is important because the original Phase 5 plan assumed that the correct research question was simply:

> "How is AES encryption added to cyclic RT?"

The current specification architecture requires a more careful question:

> "How does the current SecureRealtime security model protect the real-time communication path, and what protocol and key-management mechanisms support that protection?"


A secure real-time communication system must establish an appropriate combination of:

* peer identity,
* integrity,
* authenticity,
* freshness,
* key establishment,
* key lifecycle,
* security state,
* and real-time compatibility.

The current PI specification explicitly identifies symmetric key updates and corresponding AR startup adaptations in its V2.4 security development, alongside security eventing and refined security state machines. Therefore, the correct Phase 5 conclusion is not that every `0x8892` frame observed in Phase 3 should contain an obvious encryption field.

The correct conclusion is that **the laboratory observed the baseline RT wire format, while current secure PROFINET introduces additional security architecture that cannot be validated using the unmodified p-net stack used in these experiments.**

## 10. Phase 4 Contrast: Layer 2 Injection

Phase 4 demonstrated that an external Layer 2 host could generate controlled traffic toward the PROFINET environment.

The capture contained:

* 500 high-rate EtherType `0x8892` frames
* 3 crafted DCP-like station-name frames
* 5 malformed `0x00FF` frames

The experiments did not establish successful endpoint compromise, but they established that Layer 2 packet injection is a practical capability when an attacker has access to the relevant segment. This provides the strongest bridge into the security architecture.

The historical security model was designed around the observation that network isolation alone is insufficient as industrial systems become increasingly connected. PI's Security Extensions white paper explicitly frames the need to supplement isolation with protection of components and communication.

The newer V2.5 architecture continues this direction by introducing secure-capable protocol successors and secure provisioning rather than relying exclusively on network isolation.

The resulting security model is therefore closer to:

```text
                 Defense in Depth

        Network segmentation
                 │
                 ▼
        Layer 2 access control
                 │
                 ▼
        Device identity
                 │
                 ▼
        Secure provisioning
                 │
                 ▼
        Secure communication
                 │
                 ▼
        Application authorization
```

Each layer addresses a different failure condition. Segmentation limits who can reach the network. Device identity establishes who a component is. Secure communication protects the communication relationship. Authorization limits what an authenticated entity is permitted to do. No single layer should be treated as a substitute for the others.

## 11. DCP Security and Configuration Control

The Phase 4 DCP experiment attempted to place station-name information onto the Layer 2 segment from a rogue MAC address. The capture demonstrated that such traffic could be generated. The historical Security Class 1 model directly addresses DCP configuration operations by allowing DCP commands to be configured as read-only.

This produces a useful security mapping:

| Laboratory observation                              | Security mechanism                                              |
| --------------------------------------------------- | --------------------------------------------------------------- |
| DCP Identify exposes station information            | Discovery remains observable                                    |
| DCP Set can represent configuration activity        | Read-only DCP can reduce configuration modification             |
| Rogue host can transmit DCP-like traffic            | Network controls restrict who can reach the segment             |
| Station identity is represented by protocol data    | Secure identity mechanisms provide stronger trust               |
| No cryptographic validation was observed in Phase 1 | Secure implementations introduce additional security mechanisms |

The laboratory did not establish whether the p-net stack supports or enforces the historical Security Class 1 controls. That question remains implementation-specific.

## 12. Secure Access

GSDML V2.50 introduces the `SecureAccess` ApplicationClass alongside `SecureRealtime`. This is significant because security is no longer represented simply as a single ascending class number. The application-class approach allows the security requirements of access-oriented functions and real-time functions to be modeled separately.

Conceptually:

```text
                  PROFINET Security

                         │
             ┌───────────┴───────────┐
             │                       │
       SecureAccess            SecureRealtime
             │                       │
      Access / services        Real-time path
             │                       │
       Authentication           Integrity
       Authorization            Authenticity
       Secure sessions          Freshness
       Secure management        Key handling
```

The exact mechanisms and requirements belong to the relevant V2.5 Security Profile and protocol definitions. The important point for this research is architectural: secure access and secure real-time communication are now represented as distinct security application areas rather than being reduced to the older Security Class 2/3 terminology.

---

## 13. SXP and Protocol Replacement

One of the largest changes introduced by the current PROFINET security architecture is the introduction of SXP. PI states that V2.5 replaces protocols without secure variants, including CLRPC and RSI, with secure-capable successors. The specification identifies SXP over Layer 3 and SXP over Layer 2 and introduces Secure SXP over TCP. This is directly relevant to Phase 2.

Phase 2 observed CLRPC traffic:

```text
UDP/34964
DCE/RPC
Interface UUID
opnum 122
Request / Response
```

The current security architecture does not simply add an authentication field to the old exchange. PI describes a broader protocol transition toward secure-capable successors. That means a future secure implementation should be analyzed as a **different protocol path**, not merely as the same packet format with a cryptographic trailer. This is one of the reasons a packet generator would have been a poor substitute for a genuine security-capable implementation.

## 14. Certificate Trust and Provisioning

Current PROFINET security places secure provisioning alongside communication protection. PI's V2.5 specification explicitly identifies secure provisioning using IDevID and certificates. The broader PI/industrial-automation IDevID work describes manufacturer-provided IDevIDs as X.509 v3 certificates used as secure device identifiers and emphasizes protection against modification and illegitimate use.

This introduces a lifecycle that did not exist in the Phase 1–4 laboratory:

```text
Manufacturing
     │
     ▼
Manufacturer identity
     │
     ▼
IDevID
     │
     ▼
Secure onboarding
     │
     ▼
Operational credentials
     │
     ▼
Secure communication
     │
     ▼
Credential lifecycle
```

The security assessment therefore moves beyond packet inspection.

A complete evaluation would eventually need to consider:

* credential provisioning,
* trust-anchor management,
* certificate validation,
* credential replacement,
* device reset behavior,
* credential protection,
* authorization,
* and security event handling.

The current PI specification material also identifies security eventing and ResetToFactory behavior as security-related specification work.

## 15. Historical Security Classes Versus Current V2.50

The evolution can be summarized as follows:

| Area                     | Earlier Security Class Model                 | Current V2.50 Direction                                |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------ |
| Security Class 1         | Robustness                                   | Security mechanisms integrated into newer architecture |
| Security Class 2         | Integrity + Authenticity                     | Reworked into current secure application mechanisms    |
| Security Class 3         | Confidentiality                              | Replaced in GSDML model                                |
| DCP                      | Read-only configuration                      | Security policy / secure architecture                  |
| GSD/GSDX                 | Digital signatures                           | Continued security-oriented asset protection           |
| Device identity          | Cryptographic identity under Class 2 concept | Secure provisioning / IDevID                           |
| Acyclic communication    | Cryptographic communication relationships    | SXP / secure-capable protocol successors               |
| Real-time communication  | Integrity/authenticity/confidentiality model | `SecureRealtime`                                       |
| Access/security services | Security class model                         | `SecureAccess`                                         |
| Protocol architecture    | Legacy + security extensions                 | Security Profile + secure-capable successors           |

GSDML V2.50 explicitly records the removal of Security Classes 2 and 3 and introduction of `SecureAccess` and `SecureRealtime`, while the current PROFINET specification identifies the Security Profile, SXP, secure provisioning, and Secure SXP as major V2.5 changes. The historical class model should therefore remain in this research as architectural history and as a useful description of the security objectives, but it should not be presented as the complete current terminology.

## 16. What the Laboratory Demonstrated

The laboratory provides direct evidence for the following:

### Discovery

DCP and LLDP expose Layer 2 information before conventional IP-layer application traffic becomes central to the communication model.

### Application relations

PROFINET uses DCE/RPC-based communication mechanisms for the acyclic AR establishment observed in the p-net environment.

### Real-time traffic

PROFINET RT cyclic communication uses a compact Layer 2 format with Frame ID, process data, Cycle Counter, DataStatus, and TransferStatus fields.

### Injection surface

A host with access to the Layer 2 segment can generate EtherType `0x8892` traffic and crafted DCP-like traffic.

### Availability surface

High-rate Layer 2 traffic can be generated against the relevant interface.

### Protocol robustness surface

Malformed Layer 2 inputs can be placed onto the network. These observations remain valid regardless of whether a future secure-capable implementation adds cryptographic protection.

## 17. What the Laboratory Did Not Demonstrate

The laboratory did not establish:

* PROFINET Security Class 1 enforcement,
* Security Class 2 enforcement,
* Security Class 3 enforcement,
* SXP operation,
* SecureAccess behavior,
* SecureRealtime behavior,
* certificate-based peer authentication,
* IDevID provisioning,
* cryptographic key establishment,
* secure key rotation,
* authenticated cyclic RT traffic,
* encrypted cyclic RT traffic,
* certificate revocation handling,
* secure downgrade prevention,
* security event generation.

These are implementation-level behaviors that require a corresponding security-capable PROFINET implementation. The absence of these features from the captures therefore does not constitute evidence that the current PROFINET specification lacks them. It only establishes that they were not present in the implementation and configuration examined during this research.

The complete research now supports a layered PROFINET security model:

```text
                    PROFINET Security Boundary

┌─────────────────────────────────────────────────────────────┐
│                    Industrial Network                       │
│                                                             │
│   Segmentation / Access Control / Defense in Depth          │
│                         │                                   │
│                         ▼                                   │
│                 Layer 2 Communication                       │
│              DCP / LLDP / PROFINET RT                       │
│                         │                                   │
│                         ▼                                   │
│                  Device Identity                            │
│                IDevID / Certificates                        │
│                         │                                   │
│                         ▼                                   │
│              Secure Application Access                      │
│                    SecureAccess                             │
│                         │                                   │
│                         ▼                                   │
│             Secure Real-Time Communication                  │
│                   SecureRealtime                            │
│                         │                                   │
│                         ▼                                   │

│                                                             │
└─────────────────────────────────────────────────────────────┘
```

The important observation is that no single mechanism covers the entire attack surface. A secure deployment still depends on network architecture, component security, identity management, protocol security, and operational controls. PI's current security guidance explicitly approaches PROFINET security from planning, commissioning, and operational perspectives rather than treating protocol cryptography as the only control.

## 19. Implications for ICS/OT Security Research

The Phase 1–4 laboratory work exposed the protocol surface. Phase 5 shows why that surface should not be evaluated solely through packet manipulation. A security researcher looking only at the legacy RT frame can identify fields that control state interpretation and timing. A researcher looking only at DCP can identify configuration operations. A researcher looking only at DCE/RPC can identify application-relation establishment.

The security architecture asks a different question:

> **What establishes trust around these operations?**

That question leads to credentials, secure provisioning, application authorization, cryptographic protection, key management, and security lifecycle controls. This is particularly important for OT environments because the operational requirement is not simply confidentiality. Availability and deterministic communication remain fundamental.

PI's security development therefore has to integrate security mechanisms without treating industrial real-time behavior as ordinary enterprise traffic. The V2.4 development notes explicitly identify secure communication, symmetric key updates, AR startup changes, security state machines, and security eventing as coordinated parts of the specification evolution.

## Key Takeaways

1. **Phase 5 does not add another artificial cryptographic experiment.** It compares the real protocol behavior observed in Phases 1–4 against the security architecture defined by PI.

2. **The historical Security Class model remains useful context.** Class 1 focused on robustness, Class 2 on integrity and authenticity, and Class 3 on confidentiality.

3. **Current PROFINET security has moved beyond that terminology.** V2.5 introduces a dedicated Security Profile, SXP, secure provisioning, IDevID/certificate mechanisms, and Secure SXP.

4. **GSDML V2.50 introduces `SecureAccess` and `SecureRealtime` while removing Security Classes 2 and 3 from the GSDML security model.**

5. **Phase 1 exposed the discovery and configuration surface.** Security Class 1 historically addressed part of this surface through DCP read-only operation and GSD/GSDX integrity protection.

6. **Phase 2 exposed the application-relation surface.** ARUUIDs, RPC identifiers, and protocol state establish communication semantics, but they are not equivalent to cryptographic peer identity.

7. **Phase 3 exposed the cyclic RT surface.** Cycle Counter, DataStatus, and TransferStatus provide protocol state and timing information, but they should not be treated as cryptographic authentication.

8. **Phase 4 demonstrated the practical Layer 2 injection surface.** A host with access to the segment can generate controlled EtherType `0x8892` and DCP-like traffic.

9. **Current PROFINET security introduces mechanisms above and around those protocol surfaces rather than simply modifying the fields already observed in the laboratory.**

10. **The biggest architectural change is the move from a simple security-class progression toward application-specific secure communication and secure provisioning.**

11. **The laboratory cannot claim these protections without a security-capable implementation.** Their presence in the specification is not evidence that the p-net stack used in this research implements them.

12. **The five-phase laboratory investigation therefore remains useful.** It establishes the baseline protocol surfaces that the security architecture is intended to protect.

13. **Phase 5 closes the research loop:** from Layer 2 discovery, through application relations, cyclic real-time communication, adversarial traffic generation, and finally the security architecture designed to place trust around those operations.
