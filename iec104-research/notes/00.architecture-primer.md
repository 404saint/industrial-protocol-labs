# IEC 60870-5-104 Architecture & Protocol Specification Primer

## Executive Summary

IEC 60870-5-104 is the TCP/IP network access profile of the IEC 60870-5 telecontrol protocol family. It adapts the telecontrol mechanisms defined for IEC 60870-5-101 to packet-switched IP networks, providing communication between control centers and field systems such as RTUs and substation automation equipment.

The protocol separates **transport connectivity**, **link-state management**, and **telecontrol application data** into distinct mechanisms. TCP provides the underlying connection, while the **Application Protocol Control Information (APCI)** layer provides frame delimitation, sequence numbering, acknowledgments, and link-state control. Application data is carried in **Application Service Data Units (ASDUs)** containing typed information objects addressed through a Common Address of ASDU (CA) and Information Object Address (IOA).

A simplified architectural model is:

```text
+------------------------------------------------------+
|                  Telecontrol ASDU                    |
| Type ID / COT / CA / IOA / Information Elements     |
+------------------------------------------------------+
|                       APCI                           |
| I / S / U Formats / N(S) / N(R) / Link State       |
+------------------------------------------------------+
|                        TCP                           |
|                    Port 2404                         |
+------------------------------------------------------+
|                         IP                           |
+------------------------------------------------------+
```

This architecture establishes the baseline for the research that follows. The investigation therefore focuses on five areas:

```text
TCP Connection
      ↓
APCI Link-State Activation
      ↓
ASDU / IOA Address Space
      ↓
State & Parser Enforcement
      ↓
Security Extensions
```

---

# 1. Telecontrol Architecture & Addressing Model

IEC 60870-5-104 retains the fundamental telecontrol data model of the IEC 60870-5 family while replacing the serial communication environment with TCP/IP transport.

The architectural model can be summarized as:

```text
IEC 60870-5-101
        │
        │ Telecontrol application model
        ▼
IEC 60870-5-104
        │
        │ TCP/IP network access
        ▼
      IP Network
```

IEC 104 therefore does not define a completely independent application model. Its application layer uses the **ASDU structure, information types, causes of transmission, and addressing concepts** associated with the IEC 60870-5 telecontrol family.

The principal addressing hierarchy is:

```text
             Common Address of ASDU
                       │
                       ▼
                 Station / RTU
                       │
                       ▼
          Information Object Address
                       │
                       ▼
            Process / Control Point
```

This distinction is important during reconnaissance. The network endpoint identifies the communicating station, while the ASDU addressing model identifies individual process points within that station.

---

## 1.1 Application Service Data Units

The **Application Service Data Unit (ASDU)** is the primary application-layer container for IEC 104 telemetry, events, commands, and system functions.

A simplified ASDU structure is:

```text
+------------------------------------------------+
| Type Identification                            |
+------------------------------------------------+
| Variable Structure Qualifier                   |
+------------------------------------------------+
| Cause of Transmission                          |
+------------------------------------------------+
| Common Address of ASDU                         |
+------------------------------------------------+
| Information Object(s)                          |
|                                                |
|   IOA + Type-Specific Information               |
+------------------------------------------------+
```

The ASDU therefore provides both **semantic identification** and **addressing** for application data.

The Type Identification determines how the information object should be interpreted. Examples include:

```text
Type 1   → Single Point Information
Type 11  → Measured Value, Scaled Value
Type 13  → Measured Value, Short Floating Point
Type 30  → Single Point with CP56Time2a
Type 45  → Single Command
Type 46  → Double Command
Type 48  → Setpoint Command, Short Floating Point
Type 100 → General Interrogation Command
Type 103 → Clock Synchronization Command
```

The research does not require a complete catalogue of Type IDs. The relevant distinction is between **monitoring information**, **control information**, and **system/service operations**.

---

## 1.2 Common Address & Information Object Address

IEC 104 uses two levels of application addressing.

The **Common Address of ASDU (CA)** identifies the station or logical telecontrol endpoint to which the ASDU belongs.

The **Information Object Address (IOA)** identifies the individual information object within that station.

Conceptually:

```text
CA = 1
 │
 ├── IOA 110  → Measurement
 ├── IOA 5000 → Control Point
 ├── IOA 5001 → Control Point
 └── ...
```

The CA is two bytes, while the IOA occupies three bytes. This produces a substantially different addressing model from protocols such as Modbus, where process data is primarily represented through register or coil addresses.

For the research, this hierarchy is particularly important because **enumerating IOAs can reveal the process schema exposed by an IEC 104 endpoint**.

# 2. IEC 104 Protocol Stack & Wire Architecture

IEC 104 uses standard TCP/IP transport rather than defining a proprietary network or transport mechanism.

The protocol stack examined in this research is:

```text
+------------------------------------------------------+
|                    ASDU                              |
| Type ID / VSQ / COT / CA / IOA / Data               |
+------------------------------------------------------+
|                    APCI                              |
| Framing / Sequence Numbers / Acknowledgment         |
| STARTDT / STOPDT / TESTFR                           |
+------------------------------------------------------+
|                     TCP                              |
|                    Port 2404                         |
+------------------------------------------------------+
|                      IP                              |
+------------------------------------------------------+
```

TCP provides a reliable byte stream, but TCP itself does not provide IEC 104 message boundaries or telecontrol session semantics. Those functions are provided by APCI.

---

## 2.1 TCP Transport

IEC 104 normally operates directly over TCP using port:

```text
TCP/2404
```

The TCP connection establishes network-level connectivity between the communicating systems.

However:

```text
TCP Connection
      ≠
IEC 104 Data Transfer
```

A successfully established TCP connection does not by itself place the IEC 104 link into an active data-transfer state. The APCI state machine must subsequently establish the appropriate link state. This distinction forms the basis for the first phase of the research.

---

# 3. APCI Framing & Link-State Architecture

The **Application Protocol Control Information (APCI)** provides the framing and link-management mechanisms required above TCP.

Every IEC 104 APDU begins with:

```text
+--------+--------+-------------------------------+
|  0x68  | Length |       Control Fields          |
+--------+--------+-------------------------------+
```

The first byte is the fixed start octet `0x68`. The second byte specifies the number of bytes following the length field. The remaining portion contains four control octets followed, where applicable, by an ASDU.

A simplified frame is:

```text
Byte 0       Byte 1       Bytes 2–5          Bytes 6+
+----------+------------+------------------+----------------+
|  0x68    | Length     | APCI Control     | ASDU           |
+----------+------------+------------------+----------------+
```

The four control octets determine the APCI frame format.

---

## 3.1 I-, S-, and U-Format Frames

IEC 104 defines three APCI frame formats.

```text
                    APCI Frame
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
      I-Format       S-Format      U-Format
          │             │             │
          ▼             ▼             ▼
      Data Transfer   ACK           Link Control
```

### I-Format

I-Format frames carry ASDUs and therefore represent normal application data transfer.

They contain:

* Send sequence number `N(S)`
* Receive sequence number `N(R)`
* ASDU payload

Conceptually:

```text
I-Frame
 ├── N(S)
 ├── N(R)
 └── ASDU
```

### S-Format

S-Format frames provide supervisory acknowledgment without carrying an ASDU.

```text
S-Frame
 └── N(R)
```

They are used when an endpoint must acknowledge received I-frames without simultaneously transmitting application data.

### U-Format

U-Format frames provide link-management functions.

The principal functions are:

```text
STARTDT ACT / CON
STOPDT  ACT / CON
TESTFR  ACT / CON
```

These mechanisms control data-transfer activation, deactivation, and link testing.

# 4. Sequence Control & Link-State Mechanics

IEC 104 uses numbered I-frames to provide ordered application-data transfer and acknowledgment.

Two sequence counters are maintained:

```text
N(S) → Send Sequence Number
N(R) → Receive Sequence Number
```

The relationship can be represented as:

```text
Master                                      RTU
  │                                          │
  │──── I-Frame N(S)=0 ────────────────────►│
  │                                          │
  │◄─── I-Frame N(S)=0 / N(R)=1 ────────────│
  │                                          │
  │──── I-Frame N(S)=1 / N(R)=1 ───────────►│
  │                                          │
```

`N(R)` acknowledges previously received I-frames, allowing the protocol to implement a sliding-window mechanism rather than requiring an acknowledgment for every individual application frame.

Two principal window parameters are:

```text
k → maximum number of outstanding I-frames
w → acknowledgment threshold
```

The protocol also defines timers governing acknowledgment, idle supervisory behavior, and link testing:

```text
t1 → acknowledgment / response timeout
t2 → delayed acknowledgment timeout
t3 → idle link-test timeout
```

The commonly used default parameter values are:

```text
k  = 12
w  = 8
t1 = 15 seconds
t2 = 10 seconds
t3 = 20 seconds
```

Actual deployments may configure different values.

These mechanisms are security-relevant because sequence validation and link-state enforcement determine whether malformed or unexpected frames remain within the established communication state.

---

## 4.1 Link-State Activation

The IEC 104 communication lifecycle separates TCP connectivity from active telecontrol exchange.

A simplified state model is:

```text
                 TCP Connection
                       │
                       ▼
                 +-----------+
                 |  STOPPED  |
                 +-----------+
                       │
                 STARTDT ACT
                       │
                 STARTDT CON
                       │
                       ▼
              +-------------------+
              | DATA TRANSFER     |
              |     ACTIVE        |
              +-------------------+
                       │
                 STOPDT ACT
                       │
                 STOPDT CON
                       │
                       ▼
                 +-----------+
                 |  STOPPED  |
                 +-----------+
```

The `STARTDT` exchange activates the transfer of numbered information frames. `STOPDT` suspends data transfer, while `TESTFR` provides link testing independently of application data exchange.

This separation creates an important security boundary:

```text
TCP Reachability
       ↓
APCI Link Activation
       ↓
ASDU Processing
       ↓
Process Interaction
```

The research therefore evaluates each boundary independently rather than treating an open TCP/2404 socket as equivalent to an active application session.

# 5. Application Data Delivery Model

IEC 104 supports both cyclic and event-driven communication patterns.

A field system may transmit information:

```text
Cyclic
  │
  └── Periodic measurements

Spontaneous
  │
  └── Event-driven changes

Interrogated
  │
  └── Response to General Interrogation
```

The **Cause of Transmission (COT)** identifies the operational context associated with an ASDU.

Relevant examples include:

```text
COT 1  → Periodic / Cyclic
COT 3  → Spontaneous
COT 6  → Activation
COT 7  → Activation Confirmation
COT 10 → Activation Termination
COT 20 → Interrogated by General Interrogation
```

The COT therefore provides context that is separate from the Type ID.

For example:

```text
Type ID 100
      +
COT 6
      ↓
General Interrogation Command

Type ID 11
      +
COT 20
      ↓
Measured-value response to interrogation
```

This distinction is relevant during address-space enumeration because the same Type ID can participate in different protocol operations depending on its COT.

---

# 6. Control Model & Security-Relevant Application Functions

IEC 104 supports application-layer control operations in addition to telemetry.

Examples include:

```text
Single Command
Double Command
Setpoint Command
General Interrogation
Clock Synchronization
```

Control operations can also be associated with **Select-Before-Operate (SBO)** mechanisms, depending on the information type and implementation configuration.

The architectural distinction is:

```text
Monitoring
    │
    └── Process information

Control
    │
    └── Process state modification

System Functions
    │
    └── Interrogation / synchronization / management
```

The protocol itself provides the structures necessary to represent these operations. Whether an implementation requires authentication, authorization, SBO sequencing, or additional application-layer security is a separate deployment and security question.

This distinction is central to the subsequent research into unauthenticated control execution.

# Security Characteristics

Native IEC 60870-5-104 establishes a **telecontrol communication architecture**, not a complete security architecture.

The baseline communication path is:

```text
TCP/2404
    ↓
APCI Framing
    ↓
Link-State Activation
    ↓
Sequence-Controlled I-Frames
    ↓
ASDU Processing
    ↓
CA / IOA Address Space
    ↓
Telemetry / Control
```

The protocol provides mechanisms for:

* Frame delimitation
* Sequence numbering
* Supervisory acknowledgment
* Link-state activation and deactivation
* Link testing
* Typed telemetry and control operations
* Station and information-object addressing

These mechanisms should not be interpreted as equivalent to cryptographic security controls.

The native protocol architecture does not inherently establish:

```text
Cryptographic Identity
        ↓
Message Authentication
        ↓
Authorization
        ↓
Confidentiality
```

Consequently, the security posture of a native IEC 104 deployment depends heavily on the surrounding network architecture, endpoint configuration, implementation behavior, and additional IEC 62351 security mechanisms.

For the research that follows, this architecture establishes five investigation areas:

```text
                 IEC 104 Research Baseline
                          │
          ┌───────────────┼────────────────┐
          │               │                │
          ▼               ▼                ▼
     Link State       ASDU / IOA       State / Parser
      Dynamics        Enumeration        Enforcement
          │               │                │
          └───────────────┼────────────────┘
                          ▼
                  Attack Surface
                          │
                          ▼
                 Security Extensions
                    / IEC 62351
```

These correspond to the subsequent analysis of **APCI state behavior, ASDU and IOA enumeration, sequence and state enforcement, malformed-input handling, and the security contrast provided by IEC 62351 mechanisms**.
