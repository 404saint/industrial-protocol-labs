# Phase 5: Secure Extension Contrast & Cryptographic Mitigation

* **File:** `notes/05.phase5-secure-extension-contrast.md`
* **Target Environment:** Python TLS-Wrapped mTLS / RBAC Lab (`19999`) vs. Cleartext IEC 104 Lab (`2404`)
* **Protocol Layer:** IEC 60870-5-104 with IEC 62351 security extensions
* **Objective:** Empirically contrast the unauthenticated attack surface observed in Phases 1–4 against standardized security mechanisms provided by IEC 62351, with emphasis on transport protection, application-layer authentication, and authorization.

---

## Executive Summary

Phase 5 evaluates the security boundary introduced when native IEC 60870-5-104 communication is deployed with additional IEC 62351 security mechanisms.

Phases 1–4 established that the native IEC 104 communication channel provides no cryptographic protection at the APCI or ASDU layers. The research demonstrated unauthenticated link activation, cleartext telemetry exposure, direct control execution, and protocol-state manipulation over TCP port `2404`.

A separate secured laboratory environment was therefore used to evaluate the effect of security controls applied above the native protocol.

Two primary controls were verified:

1. **IEC 62351-3 / TLS:** Mutual TLS prevented clients without an accepted X.509 certificate from establishing the secured communication channel and prevented passive observers from directly recovering IEC 104 application payloads.
2. **IEC 62351-8 / RBAC:** Authorization was evaluated after successful client authentication, preventing an authenticated but unauthorized identity from executing a protected control action against `IOA 5001`.

The secured environment therefore establishes an important distinction from the native protocol:

```text
Native IEC 104
     │
     ├── TCP connectivity
     ├── STARTDT activation
     ├── ASDU exchange
     └── Control execution
              │
              ▼
       No cryptographic
       identity boundary


IEC 104 + IEC 62351
     │
     ├── TLS / Application Authentication
     │
     ├── Protected IEC 104 Traffic
     │
     ├── Authenticated Identity
     │
     └── Authorization / RBAC
              │
              ▼
       Explicit security boundary
```

The experiments demonstrate that the security extensions introduce controls at boundaries that are absent from the native IEC 104 communication model.

# 1. Transport Security Contrast: TCP 2404 vs. IEC 62351-3

The native IEC 104 environment used throughout Phases 1–4 exposed the protocol directly over TCP port `2404`. The secured environment placed the IEC 104 communication inside a TLS-protected channel on port `19999`.

### 1.1 Cleartext Baseline

The Phase 1–4 environment permitted a client capable of reaching TCP `2404` to establish a connection and initiate the IEC 104 link state machine.

The communication sequence was effectively:

```text
Client                         RTU
  │                             │
  │──── TCP Connection ────────►│
  │                             │
  │──── STARTDT ACT ───────────►│
  │◄─── STARTDT CON ────────────│
  │                             │
  │──── I-Format / ASDU ───────►│
  │◄─── I-Format / ASDU ────────│
```

No certificate exchange, cryptographic authentication, or application identity validation was required before IEC 104 communication became active.

This permitted the attack conditions demonstrated in earlier phases:

* passive observation of APCI and ASDU traffic;
* extraction of Common Addresses and IOAs;
* unauthenticated General Interrogation;
* direct control command injection;
* APCI state manipulation;
* sequence-counter manipulation.

---

## 1.2 TLS-Protected Environment

The secured environment introduced TLS before IEC 104 application traffic was exchanged.

The laboratory configuration used:

```text
Transport:      TLS
TLS Version:    TLS 1.3
Cipher Suite:   TLS_AES_256_GCM_SHA384
Authentication: X.509 mutual authentication
Listener:       TCP 19999
```

With mandatory client certificate authentication enabled, an unauthenticated client attempting to establish the secured channel was rejected during the TLS handshake:

```text
[SSL: TLSV13_ALERT_CERTIFICATE_REQUIRED]
tlsv13 alert certificate required
```

The IEC 104 application layer was therefore not reached by the unauthenticated client.

The security boundary occurs before APCI state activation:

```text
Unauthenticated Client
        │
        ▼
   TCP 19999
        │
        ▼
    TLS Handshake
        │
        ├── Client Certificate Required
        │
        X
        │
   IEC 104 APCI
   never reached
```

This is materially different from the native `STARTDT` boundary observed in Phase 1, where link activation itself was unauthenticated.

---

## 1.3 Passive Traffic Visibility

The secured channel also changes the information available to passive network observers.

In the native environment, an observer could directly decode:

```text
APCI
  │
  ├── N(S)
  ├── N(R)
  └── Frame Type
       │
       ▼
ASDU
  │
  ├── Type ID
  ├── COT
  ├── CA
  ├── IOA
  └── Process Data
```

Under TLS protection, the observer sees the encrypted transport rather than the underlying IEC 104 fields.

The laboratory capture confirmed application payload protection using:

```text
TLS_AES_256_GCM_SHA384
```

Consequently, passive packet capture no longer directly exposes the ASDU contents or IOA mapping demonstrated in Phases 1 and 2.

# 2. Control Execution & IEC 62351-8 Authorization

Transport authentication alone does not establish whether an authenticated identity is authorized to perform a particular control operation. Phase 5 therefore evaluated authorization separately from transport authentication. The comparison was based on the direct Single Command execution demonstrated in Phase 3.

---

## 2.1 Native IEC 104 Control Boundary

Phase 3 demonstrated direct execution of:

```text
Type ID: 45
CA:      1
IOA:     5001
Command: OFF / TRIP
```

The native environment accepted the command without:

* cryptographic authentication;
* user identity validation;
* authorization checks;
* enforced Select-Before-Operate sequencing.

The effective control path was:

```text
Network Access
      │
      ▼
TCP 2404
      │
      ▼
STARTDT
      │
      ▼
Type 45 Command
      │
      ▼
IOA 5001
      │
      ▼
Actuator State Change
```

---

## 2.2 Authenticated but Unauthorized Control

The secured environment introduced authorization after successful TLS authentication.

The test client authenticated using:

```text
Client Identity:
CN = scada-master
```

The client then attempted to execute the same high-impact control operation against `IOA 5001`.

The laboratory instrumentation recorded:

```text
[+] Authenticated Session Established with CN: scada-master
  [rx] Secure Tunnel Bytes (16): 680b000000002d010600010089130001
  [i] Control Request Detected -> IOA: 5001
  [!] RBAC Violation: User 'scada-master' unauthorized for actuator IOA 5001.
  [rx] Raw Response Bytes: 680447000000
  [✔] RBAC Enforcement Verified: Server rejected command (Access Denied).
```

The important security property is that **successful authentication did not automatically imply authorization**.

The control path became:

```text
TLS Authentication
        │
        ▼
Authenticated Identity
        │
        ▼
Authorization Check
        │
        ├── Authorized ─────► Control Execution
        │
        └── Unauthorized
                  │
                  ▼
             Command Rejected
```

The attempted operation against `IOA 5001` therefore failed at the authorization boundary rather than reaching actuator execution.

# 3. Security Boundary Comparison

The experiments across the five phases establish three distinct security boundaries.

| Security Boundary          | Native IEC 104                     | Secured Environment                     | Observed Result                                          |
| -------------------------- | ---------------------------------- | --------------------------------------- | -------------------------------------------------------- |
| **Network Access**         | TCP `2404` reachable               | TLS listener on `19999`                 | Unauthenticated TLS client rejected                      |
| **Application Visibility** | APCI/ASDU transmitted in cleartext | IEC 104 payload transported through TLS | Passive observer cannot directly decode ASDU             |
| **Application Identity**   | No cryptographic identity          | X.509 client certificate                | Client identity established cryptographically            |
| **Control Authorization**  | Direct Type 45 execution           | RBAC authorization check                | Unauthorized `IOA 5001` command rejected                 |
| **SBO Enforcement**        | Not enforced by target             | Authorization added independently       | Transport security does not replace command interlocking |

The final row is particularly important.

TLS and RBAC address different security problems from Select-Before-Operate.

```text
TLS
 │
 └── Who is communicating?

Authentication
 │
 └── Which identity is communicating?

RBAC
 │
 └── What is that identity allowed to do?

SBO
 │
 └── Has the required control sequence been completed?
```

These controls should therefore be treated as complementary rather than interchangeable.

# 4. IEC 62351 Security Extension Coverage

The research considered three IEC 62351 security areas:

### IEC 62351-3 — Communication Network and System Security

Provides mechanisms for protecting communication at the transport/network layer, including TLS-based protection.

In the laboratory environment, this was represented by:

```text
IEC 104
   │
   ▼
TLS 1.3
   │
   ├── Confidentiality
   ├── Integrity
   └── Mutual Authentication
```

This directly addresses the cleartext exposure observed during Phases 1–4.

### IEC 62351-5 — Security for IEC 60870-5-101/104

Provides security mechanisms specifically associated with IEC 60870-5 telecontrol protocols and application-layer protection. Its relevance to this research is the additional security context available for IEC 104 beyond transport protection.

### IEC 62351-8 — Role-Based Access Control

Provides a framework for assigning permissions according to defined roles. In the laboratory implementation, RBAC was used to demonstrate that an authenticated identity could still be denied access to a protected control point. This addresses an attack class that encryption alone cannot solve.

# 6. Security Assessment

Phase 5 demonstrates that the principal weaknesses identified in the native IEC 104 environment are not inherent requirements for a secured deployment.

The native protocol's security boundary is primarily dependent on the surrounding network architecture:

```text
TCP Reachability
      │
      ▼
IEC 104 Link Activation
      │
      ▼
ASDU Access
      │
      ▼
Control Execution
```

The secured environment introduces explicit security decisions into that path:

```text
TCP Reachability
      │
      ▼
TLS Authentication
      │
      ▼
Encrypted Communication
      │
      ▼
Authenticated Identity
      │
      ▼
Authorization
      │
      ▼
IEC 104 Control
```

The practical difference is significant.

A network-adjacent attacker in the native environment can interact directly with the IEC 104 state machine. In the secured environment, an attacker must first satisfy the cryptographic authentication boundary before reaching the protected application channel. Likewise, possession of a valid authenticated identity does not necessarily grant unrestricted control access when RBAC is enforced.

## Security Characteristics

Phase 5 establishes the security contrast between **native IEC 104 operation** and an IEC 62351-protected deployment.

The laboratory results demonstrate three distinct protections:

```text
                 IEC 62351 Security Model

        ┌──────────────────────────────┐
        │       TLS / IEC 62351-3      │
        │                              │
        │ Confidentiality              │
        │ Integrity                    │
        │ Mutual Authentication        │
        └──────────────┬───────────────┘
                       │
                       ▼
        ┌──────────────────────────────┐
        │       IEC 62351-8            │
        │                              │
        │ Identity → Role → Permission │
        └──────────────┬───────────────┘
                       │
                       ▼
        ┌──────────────────────────────┐
        │       IEC 104 Application    │
        │                              │
        │ APCI / ASDU / Control        │
        └──────────────────────────────┘
```

The research therefore establishes the following baseline:

* **Native IEC 104:** no cryptographic identity or confidentiality at the APCI/ASDU layer.
* **IEC 62351-3:** establishes a protected communication channel and cryptographic peer authentication.
* **IEC 62351-5:** provides IEC 104-specific application-layer security mechanisms that complement transport protection.
* **IEC 62351-8:** establishes authorization boundaries between authenticated identities and permitted operations.
* **SBO:** remains a separate application control mechanism and should not be considered replaced by TLS or RBAC.

Taken together, the five phases establish a complete progression:

```text
Phase 1
Link State
    │
    ▼
Phase 2
ASDU / IOA Discovery
    │
    ▼
Phase 3
State & Control Abuse
    │
    ▼
Phase 4
Parser & Boundary Behavior
    │
    ▼
Phase 5
Security Extensions
    │
    ▼
Native Attack Surface
        vs.
Secured Architecture
```

This provides the final security baseline for the IEC 104 research: **the protocol's operational functionality and its security controls are separable architectural concerns.** Native IEC 104 provides the communication mechanisms; IEC 62351 introduces security boundaries around those mechanisms.
