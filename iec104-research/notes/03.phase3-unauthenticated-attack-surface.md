# Phase 3: APCI State Enforcement, Sequence Validation & Control Execution

* **Target Endpoint:** `127.0.0.1:2404` (`lib60870-C / cs104_server_no_threads`)
* **Layer:** IEC 60870-5-104 APCI State Machine and ASDU Application Layer
* **Objective:** Evaluate APCI state enforcement, I-format sequence-number handling, mid-session link disruption, and unauthorized control execution.

---

## Executive Summary

Phase 3 evaluated the target implementation's enforcement of IEC 104 communication state, handling of I-format sequence numbers, and command authorization boundaries.

The target demonstrated **strict APCI state enforcement**. I-format frames transmitted before `STARTDT` activation were rejected with connection termination, and I-format traffic transmitted after `STOPDT` was likewise rejected.

Sequence-number testing produced a different result. The server continued the session when presented with large forward `N(S)` values, including `5000` and `32767`, without an observed connection reset or protocol error. The test demonstrates **permissive sequence-number handling in the examined implementation**, although the observation alone does not establish that all out-of-window conditions are accepted or that the implementation completely disables sequence validation.

A direct `C_SC_NA_1` Single Command targeting `IOA 5001` was also executed without a preceding Select operation. The command caused the configured actuator state to change, confirming that the tested server did not enforce Select-Before-Operate for this control point.

The principal Phase 3 findings are therefore:

1. **APCI state transitions are enforced.**
2. **Large forward sequence-number jumps were tolerated by the tested implementation.**
3. **Direct command execution remained possible without an enforced Select operation or authentication boundary.**

---

# 1. APCI Link State Machine Enforcement

IEC 104 separates TCP connection establishment from activation of application data transfer.

The relevant communication states can be represented as:

```text
                    TCP Connection
                         │
                         ▼
                  +-------------+
                  |   STOPPED   |
                  +-------------+
                         │
                  STARTDT ACT
                         │
                  STARTDT CON
                         ▼
              +---------------------+
              |       STARTED       |
              | Data Transfer Active|
              +---------------------+
                    │          │
              STOPDT ACT       │
                    │          │
              STOPDT CON       │
                    ▼          │
              +-------------+  │
              |   STOPPED   |◄─┘
              +-------------+
```

The distinction is important because TCP connectivity alone does not place an IEC 104 endpoint into the data-transfer state.

---

## 1.1 Pre-STARTDT I-Format Injection

An I-format frame was transmitted immediately after TCP connection establishment without first completing the `STARTDT` activation sequence.

```text
[TEST 1]

──► TX | I-FRAME
         State: STOPPED

◄── RX | Connection closed by server
```

The server did not process the supplied ASDU.

The observed behavior establishes that the tested implementation does not permit normal I-format application traffic while the IEC 104 link remains in the `STOPPED` state.

---

## 1.2 Post-STOPDT I-Format Injection

A second test examined application traffic following an active `STOPDT` transition.

```text
[TEST 2]

──► TX | STOPDT ACT
◄── RX | STOPDT CON

──► TX | I-FRAME
         State: STOPPED

◄── Connection closed / I-FRAME rejected
```

The result was consistent with the pre-activation test: application-layer I-format traffic was not accepted after the link returned to the stopped state.

The observed state enforcement is therefore:

```text
STOPPED
   │
   ├── I-FRAME ──► Rejected
   │
   └── STARTDT ACT ──► STARTED

STARTED
   │
   ├── I-FRAME ──► Accepted
   │
   └── STOPDT ACT ──► STOPPED
```

### Security Characteristic

The target implementation provides a meaningful protocol-state boundary between TCP establishment and ASDU processing.

This is an important distinction from the authentication boundary examined in earlier phases:

```text
TCP Connectivity
       │
       ▼
IEC 104 State Machine
       │
       ▼
ASDU Processing
```

The state machine prevents application traffic from being processed outside the active communication state, but it does **not itself establish the identity or authorization of the peer**.

# 2. I-Format Sequence Number Handling

IEC 104 I-format frames contain two independent sequence values:

```text
N(S)
 │
 └── Send sequence number

N(R)
 │
 └── Receive sequence number
```

These values provide application-layer sequencing and acknowledgment independently of TCP sequence numbers. The test examined the target's response to large forward `N(S)` values.

---

## 2.1 Forward Sequence Jump: `N(S) = 5000`

The client transmitted:

```text
──► TX | I-FRAME
         N(S): 5000
         N(R): 0
         IOA: 5000
         State: ON
```

The target continued transmitting telemetry:

```text
◄── RX | I-FRAME
         N(S): 0
         N(R): 0
         Type: 11
```

No connection reset or explicit sequence error was observed.

---

## 2.2 Maximum Sequence Value: `N(S) = 32767`

The boundary value of the 15-bit sequence field was subsequently tested:

```text
──► TX | I-FRAME
         N(S): 32767
         N(R): 0
         IOA: 5000
         State: OFF
```

The target again continued normal telemetry transmission:

```text
◄── RX | I-FRAME
         N(S): 1
         N(R): 0
         Type: 11
```

No transport reset or explicit protocol error was observed during the test.

---

## 2.3 Analysis

The observed behavior demonstrates that the tested server did not terminate the connection when presented with the tested large forward sequence values.

The finding should be stated precisely:

> **The tested implementation tolerated large forward `N(S)` values without an observed session reset or sequence-error response.**

This does not, by itself, establish that sequence validation is completely absent. IEC 104 sequence handling depends on the relationship between the received sequence value and the endpoint's expected receive state, including the configured transmission and acknowledgment windows. The test therefore establishes **observed tolerance**, rather than proving universal acceptance of arbitrary sequence values.

A useful model for subsequent testing is:

```text
Received N(S)
      │
      ▼
Compare with expected receive state
      │
      ├── Expected / valid window
      │        │
      │        ▼
      │      Accept
      │
      └── Unexpected / outside window
               │
               ▼
          Implementation-specific
          handling
```

The Phase 3 observation concerns the second branch.

# 3. Direct Control Execution

A `C_SC_NA_1` Single Command (`Type ID 45`) was transmitted against the configured actuator:

```text
CA  = 1
IOA = 5001
```

The requested state was `OFF`.

```text
──► TX | I-FRAME
         Type: 45 (C_SC_NA_1)
         CA: 1
         IOA: 5001
         State: OFF
         Select: 0
```

The target processed the command:

```text
+----------------------+             +----------------------+
| Master / Test Client |             | RTU Server           |
|                      |             |                      |
| Type 45              |             |                      |
| CA 1                 |             |                      |
| IOA 5001             |------------>| Command Processing   |
| Select = Execute     |             |         │            |
+----------------------+             |         ▼            |
                                     | IOA 5001 = 0         |
                                     +----------------------+
```

The server-side output confirmed:

```text
IOA 5001 switch to 0
```

---

# 4. Select-Before-Operate Analysis

The command was transmitted directly with the Select/Execute indication set to **Execute**.

Conceptually:

```text
Single Command
      │
      ▼
     SCO
      │
      ├── Command State
      │
      └── Select / Execute
             │
             ├── Select
             └── Execute
```

The tested sequence was:

```text
Execute
   │
   ▼
Command accepted
   │
   ▼
IOA 5001 changed
```

No preceding Select transaction was required.

The appropriate finding is therefore:

> **The tested implementation did not enforce a Select-Before-Operate sequence for the configured control point.**

This distinction is important. SBO is not a separate IEC 104 Type ID. The command's Select/Execute semantics are represented within the command qualifier, while enforcement of a two-stage command procedure is an implementation and application-control decision. The evidence therefore demonstrates **SBO enforcement failure in the tested configuration**, rather than a protocol-wide absence of SBO capability.

# 5. Combined Attack Surface

The observations from the phase can be combined into a single attack path:

```text
Network Reachability
        │
        ▼
TCP / 2404
        │
        ▼
STARTDT ACT
        │
        ▼
STARTDT CON
        │
        ▼
Active IEC 104 Session
        │
        ├─────────────────────┐
        │                     │
        ▼                     ▼
I-Format Injection      Sequence Manipulation
        │                     │
        ▼                     ▼
ASDU Processing          Large N(S) tolerated
        │
        ▼
Type 45 Single Command
        │
        ▼
IOA 5001
        │
        ▼
Actuator State Change
```

The significant security boundary is therefore not the existence of the APCI state machine, but what happens **after successful state activation**.

The implementation enforces:

```text
STOPPED ──X──> I-FRAME
```

but the tested configuration permits:

```text
STARTED
   │
   ├── Type 45
   │      │
   │      ▼
   │   IOA 5001
   │
   └── No authentication
```

| Finding ID        | Severity     | Layer            | Finding                                                                                                                                                                                                                              |

# 7. Security Analysis

## 7.1 State Enforcement vs. Authentication

Phase 3 demonstrates that protocol-state enforcement and authentication are separate security properties.

The target correctly enforces:

```text
TCP
 │
 ▼
STOPPED
 │
 ├── STARTDT ──► STARTED
 │
 └── I-FRAME ──► Reject
```

However, once the link enters the active state:

```text
STARTED
   │
   ▼
ASDU Processing
   │
   └── Type 45 Command
```

No corresponding peer-authentication boundary was observed.

Therefore:

> **State validation determines whether a frame is valid for the current communication state; it does not establish whether the sender is authorized to perform the requested operation.**

This distinction is central to the IEC 104 threat model examined in this research.

---

## 7.2 Sequence State as a Security Boundary

IEC 104 sequence numbers provide communication-state integrity, but their effectiveness depends on implementation enforcement.

The tested server tolerated:

```text
Expected sequence
       ↓
     5000
       ↓
    32767
```

without terminating the session.

The observation warrants further testing of:

* backward sequence values;
* duplicate `N(S)` values;
* values outside the negotiated receive window;
* wraparound from `32767` to `0`;
* invalid `N(R)` values;
* repeated malformed sequence combinations.

These tests can establish whether the observed behavior represents a narrow implementation quirk or a broader weakness in APCI sequence validation.

---

# 8. Recommendations

### 1. Enforce Receive-Sequence Validation

The implementation should validate received `N(S)` values against the endpoint's current receive state and configured transmission window. Unexpected sequence values should trigger the protocol-defined error-handling behavior rather than being silently tolerated.

Testing should include:

```text
Expected N(S)
      │
      ├── +1       → valid
      ├── duplicate → test
      ├── forward gap → test
      ├── backward → test
      └── wraparound → test
```

### 2. Enforce Command Authorization

Control commands should not be authorized solely because the sender has reached the IEC 104 `STARTED` state.

The authorization model should establish:

```text
Authenticated Peer
        │
        ▼
Authorized Role
        │
        ▼
Authorized Control Point
        │
        ▼
Command Execution
```

### 3. Enforce SBO Where Operationally Required

Where Select-Before-Operate is required by the control-system design, the RTU should maintain selection state and reject Execute operations without a valid preceding Select.

The implementation should validate both:

* selected control point;
* valid selection state / timing.

### 4. Apply IEC 62351 Security Controls

Appropriate IEC 62351 mechanisms should be evaluated for providing cryptographic protection, peer authentication, and application-layer security.

### 5. Maintain Network-Level Isolation

TCP/2404 should be restricted to authorized control-system communication paths through OT firewalls, ACLs, and network segmentation. Network isolation should supplement, rather than replace, application-layer authorization.

# Security Characteristics

Phase 3 establishes three distinct security characteristics in the tested IEC 104 implementation.

### 1. APCI State Enforcement

The server enforces the distinction between stopped and active communication states:

```text
STOPPED
   │
   └── I-FRAME → Rejected

STARTED
   │
   └── I-FRAME → Processed
```

This demonstrates functioning protocol-state validation.

### 2. Permissive Sequence Handling

Large forward `N(S)` values were tolerated during testing:

```text
N(S) = 5000
N(S) = 32767
```

without an observed session reset.

This is recorded as an **implementation-specific sequence-validation weakness**, pending broader boundary testing.

### 3. Unauthenticated Control Execution

The most significant observation is the complete attack path demonstrated after link activation:

```text
TCP Reachability
      │
      ▼
STARTDT
      │
      ▼
Active Session
      │
      ▼
Type 45
      │
      ▼
IOA 5001
      │
      ▼
Actuator State Change
```

The tested implementation therefore maintains a strong **protocol-state boundary** while exposing a weak **authorization boundary**.
