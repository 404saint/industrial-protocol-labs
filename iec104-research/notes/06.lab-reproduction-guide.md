# Lab Reproduction & Automation Guide

* **File:** `notes/06.lab-reproduction-guide.md`
* **Target Environment:** IEC 60870-5-104 Cleartext & TLS Security Extension Laboratory
* **Objective:** Provide a reproducible procedure for building the IEC 104 target, generating the laboratory PKI, launching the cleartext and secured environments, executing the research scripts, and capturing the resulting network traffic.

---

## Executive Summary

This document defines the laboratory procedure used to reproduce the IEC 60870-5-104 research environment and validate observations documented across Phases 1–5.

The laboratory consists of two communication environments:

1. **Cleartext IEC 104 Environment**

   * `lib60870-C`
   * `cs104_server_no_threads`
   * TCP port `2404`
   * Native IEC 60870-5-104 communication without transport encryption

2. **Secured IEC 104 Environment**

   * Python-based TLS wrapper / security extension laboratory
   * Mutual TLS authentication
   * TCP port `19999`
   * X.509 certificates generated locally for the research environment
   * RBAC enforcement for protected control operations

Network traffic is captured from the loopback interface using Wireshark. The same capture methodology is applied to both environments to provide a direct comparison between cleartext IEC 104 traffic and TLS-protected communication.

# 2. Cleartext IEC 104 Environment

The baseline environment uses the `lib60870-C` implementation and its `cs104_server_no_threads` example server.

The server listens on TCP port `2404`.

## 2.1 Clone `lib60870`

```bash
git clone https://github.com/mz-automation/lib60870.git
cd lib60870/c
```

Build the library and included examples:

```bash
mkdir build
cd build
cmake ..
make
```

The resulting build contains the IEC 104 example server.

---

## 2.2 Launch the IEC 104 Server

From the completed build directory:

```bash
./bin/cs104_server_no_threads
```

The research environment also used a separate CMake build from the laboratory workspace:

```bash
cd ~/Desktop/iec104-lab/build
cmake ../lib60870/lib60870-C
make
```

The server can then be launched with:

```bash
./examples/cs104_server_no_threads/cs104_server_no_threads
```

The resulting target is:

```text
127.0.0.1:2404
```

This cleartext server provides the baseline implementation against which the protocol behavior documented in Phases 1–4 was evaluated.

# 4. Laboratory PKI Generation

The secured environment uses a locally generated Certificate Authority and X.509 certificates.

These certificates are included/generated for the laboratory so that a researcher cloning the repository can reproduce the mTLS environment without obtaining certificates from an external CA.

## 4.1 Create the Certificate Authority

```bash
openssl req -x509 -newkey rsa:2048 -days 365 -nodes \
  -keyout ca-key.pem \
  -out ca-cert.pem \
  -subj "/CN=Lab-Root-CA"
```

This creates the local root CA:

```text
ca-key.pem
ca-cert.pem
```

---

## 4.2 Generate the Server Certificate

Create the server private key and CSR:

```bash
openssl req -newkey rsa:2048 -nodes \
  -keyout server-key.pem \
  -out server-csr.pem \
  -subj "/CN=localhost"
```

Sign the server certificate using the laboratory CA:

```bash
openssl x509 -req -days 365 \
  -in server-csr.pem \
  -CA ca-cert.pem \
  -CAkey ca-key.pem \
  -CAcreateserial \
  -out server-cert.pem
```

The resulting certificate identifies the TLS server as:

```text
CN=localhost
```

---

## 4.3 Generate the Client Certificate

Create the client private key and CSR:

```bash
openssl req -newkey rsa:2048 -nodes \
  -keyout client-key.pem \
  -out client-csr.pem \
  -subj "/CN=scada-master"
```

Sign the client certificate:

```bash
openssl x509 -req -days 365 \
  -in client-csr.pem \
  -CA ca-cert.pem \
  -CAkey ca-key.pem \
  -CAcreateserial \
  -out client-cert.pem
```

The resulting certificate identifies the laboratory master station as:

```text
CN=scada-master
```

This identity is subsequently used by the secure laboratory when evaluating authorization decisions.

> **Note:** The commands above reproduce the certificate-generation procedure used during the research. For production deployments, certificate extensions such as Subject Alternative Name, appropriate Key Usage, and Extended Key Usage should be explicitly configured rather than relying on a minimal laboratory certificate profile.

# 5. Secure IEC 104 Environment

The secured environment operates separately from the cleartext listener.

The laboratory secure endpoint is:

```text
127.0.0.1:19999
```

The secure environment provides:

```text
IEC 104 Application Data
        │
        ▼
   TLS 1.3 / mTLS
        │
        ▼
   TCP port 19999
```

Unlike the cleartext environment, the secured laboratory requires X.509 client authentication before application communication is accepted.

---

## 5.1 Launch the Secure Server

From the research repository:

```bash
python3 scripts/05_secure_lab_server.py
```

The secure server loads the laboratory CA and server certificate and listens on port `19999`.

---

## 5.2 Execute Secure Client Tests

In a separate terminal:

```bash
python3 scripts/05_secure_lab_client.py
```

The client performs the secure-environment validation.

The expected successful configuration establishes a TLS 1.3 session using:

```text
TLS_AES_256_GCM_SHA384
```

The client certificate identifies the laboratory master as:

```text
CN=scada-master
```

The negative authentication test intentionally omits the client certificate.

The expected result is a TLS handshake failure similar to:

```text
[SSL: TLSV13_ALERT_CERTIFICATE_REQUIRED]
tlsv13 alert certificate required
```

This reproduces the transport-level authentication boundary documented in Phase 5.

# 6. Network Traffic Capture

All protocol traffic generated during the research was captured on the loopback interface.

The capture filter was restricted to the active IEC 104 laboratory port.

## 6.1 Cleartext Capture

Start Wireshark with:

```bash
wireshark -k -i lo -f "tcp port 2404"
```

---

## 6.2 Secure Environment Capture

For the TLS environment:

```bash
wireshark -k -i lo -f "tcp port 19999"
```

---

## 6.3 Capture Methodology

The capture sequence is:

```text
Start Wireshark
      │
      ▼
Launch Target Server
      │
      ▼
Execute Research Script
      │
      ▼
Observe / Record Traffic
      │
      ▼
Terminate Test
      │
      ▼
Stop Capture
      │
      ▼
Analyze PCAP
```

The same methodology is used for both ports:

```text
Cleartext:
lo → tcp port 2404

Secure:
lo → tcp port 19999
```

This provides a controlled comparison between visible APCI/ASDU traffic and encrypted TLS application traffic.

# 9. Research Scope & Safety

The laboratory is designed for isolated protocol research and defensive security validation.

The target addresses used throughout the study are loopback addresses:

```text
127.0.0.1:2404
127.0.0.1:19999
```

The protocol manipulation, malformed-frame testing, and control execution procedures described in the research should be performed only against systems explicitly controlled by the researcher. The cleartext environment is intentionally vulnerable and exists to establish the protocol-security baseline. The secured environment demonstrates the effect of authentication, encryption, and authorization controls against that baseline.

---

## Security Characteristics

The reproduction environment separates **protocol behavior** from **security-extension behavior**.

The cleartext `lib60870-C` server provides the baseline required to reproduce the APCI, ASDU, state-machine, sequence-counter, and control-execution observations from Phases 1–4.

The secure laboratory provides the corresponding security boundary:

```text
Cleartext IEC 104
        │
        ├── No transport authentication
        ├── No encryption
        └── Direct protocol visibility
                    │
                    ▼
             Security Extensions
                    │
        ├── X.509 Authentication
        ├── TLS Encryption
        └── Authorization / RBAC
                    │
                    ▼
              Secure IEC 104
```

The laboratory therefore provides a reproducible path from **native IEC 104 protocol behavior** through **wire-level observation** to **cryptographic and authorization controls**, without treating the reproduction guide itself as an additional research phase.
