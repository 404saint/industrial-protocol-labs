# Phase 1: Link State Dynamics & APCI Control Framing

* **Target Server:** `127.0.0.1:2404` (`lib60870-C / cs104_server_no_threads`)
* **Protocol Layer:** IEC 60870-5-104 APCI over TCP
* **Objective:** Examine native link-state activation, APCI control-frame behavior, state transitions, keep-alive mechanisms, and sequence-control behavior prior to ASDU processing.

---

## Executive Summary

Phase 1 examined the IEC 104 communication state established between an unauthenticated master client and the target RTU implementation.

A TCP connection to port `2404` established the transport connection, after which raw APCI U-format frames were transmitted to exercise the IEC 104 link-state machine. The target accepted `STARTDT ACT` and returned `STARTDT CON`, demonstrating successful transition from the initial `STOPPED` state into active data transfer without an authentication exchange.

Additional testing examined `TESTFR` keep-alive behavior, `STOPDT` state transitions, and the interaction between U-format control frames and supervisory S-format acknowledgments.

Two implementation-specific behaviors were also observed in `lib60870-C / cs104_server_no_threads`: S-format acknowledgments could appear between expected U-format responses during rapid frame transmission, and `STOPDT ACT` could result in connection teardown before the expected `STOPDT CON` was observed by the client.

The primary security observation is that **native APCI state activation does not establish cryptographic peer authentication**. Reachability to the IEC 104 endpoint is therefore sufficient to participate in the protocol's link-state negotiation.

---

# 1. Protocol Architecture & APCI Structure

IEC 104 places its communication-control mechanism in the **Application Protocol Control Information (APCI)** structure. Application information is carried separately within the **Application Service Data Unit (ASDU)**.

The basic APDU structure is:

```text
Byte:   0      1      2      3      4      5
     +------+------+------+------+------+------+
     | 0x68 | Len  | Ctrl1| Ctrl2| Ctrl3| Ctrl4|
     +------+------+------+------+------+------+
                                  |
                                  +---- Optional ASDU
```

The first six bytes constitute the APCI framing structure.

The first control octet determines the APDU format:

```text
                    Control Byte 1
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
          Bit 0 = 0     Bits 1:0 = 01  Bits 1:0 = 11
              │            │            │
              ▼            ▼            ▼
          I-Format      S-Format      U-Format
              │            │            │
              ▼            ▼            ▼
         ASDU Data      ACK State    Link Control
```

The three formats provide separate protocol functions:

| Format       | Primary Function              | ASDU |
| ------------ | ----------------------------- | ---- |
| **I-format** | Numbered information transfer | Yes  |
| **S-format** | Supervisory acknowledgment    | No   |
| **U-format** | Link-state and test functions | No   |

This distinction is fundamental to packet-level analysis because an IEC 104 TCP stream cannot be interpreted as a sequence of application messages alone. APCI state and control frames must be processed before ASDU semantics can be evaluated.

# 2. Unauthenticated Link-State Negotiation

Establishing a TCP connection to port `2404` provides transport connectivity but does not, by itself, place the IEC 104 connection into the active data-transfer state. The target initially operated in the `STOPPED` state.

The following exchange was captured:

```text
[*] Target Server: 127.0.0.1:2404
[*] Establishing Layer 4 TCP Socket...
[+] TCP Connected. IEC 104 State: STOPPED

[>] STARTDT ACT
    68 04 07 00 00 00

[<] STARTDT CON
    68 04 0B 00 00 00

[+] IEC 104 data transfer activated
```

The exchange demonstrates that the target accepted the activation request without an authentication mechanism at the APCI layer.

The resulting state transition is:

```text
TCP Connection Established
            │
            ▼
         STOPPED
            │
       STARTDT ACT
            │
       STARTDT CON
            │
            ▼
         STARTED
```

This establishes the baseline required for subsequent ASDU testing.

# 3. APCI Link-Control Frames

The U-format control functions exercised during Phase 1 are:

| Control Action          | Frame         | Bytes               | Control Byte |
| ----------------------- | ------------- | ------------------- | ------------ |
| Start data transfer     | `STARTDT ACT` | `68 04 07 00 00 00` | `0x07`       |
| Confirm data transfer   | `STARTDT CON` | `68 04 0B 00 00 00` | `0x0B`       |
| Stop data transfer      | `STOPDT ACT`  | `68 04 13 00 00 00` | `0x13`       |
| Confirm stop transfer   | `STOPDT CON`  | `68 04 23 00 00 00` | `0x23`       |
| Test-frame activation   | `TESTFR ACT`  | `68 04 43 00 00 00` | `0x43`       |
| Test-frame confirmation | `TESTFR CON`  | `68 04 83 00 00 00` | `0x83`       |

These frames contain APCI control information only and therefore do not carry an ASDU.

The U-format functions provide the control primitives used to activate, deactivate, and supervise the IEC 104 communication channel.

# 4. Link-State Dynamics

The observed state machine can be represented as:

```text
                  TCP Connection
                        │
                        ▼
                +---------------+
                |    STOPPED    |
                +---------------+
                        │
                 STARTDT ACT
                        │
                 STARTDT CON
                        │
                        ▼
             +---------------------+
             | DATA TRANSFER ACTIVE|
             +---------------------+
                  │            │
             TESTFR ACT    STOPDT ACT
                  │            │
             TESTFR CON    STOPDT CON
                  │            │
                  │            ▼
                  │      +---------------+
                  └─────>|    STOPPED    |
                         +---------------+
```

The important observation is that **TCP establishment and IEC 104 data-transfer activation are separate protocol states**. A client can therefore establish the TCP connection without immediately having an active IEC 104 data-transfer state. Once `STARTDT ACT` / `STARTDT CON` succeeds, I-format communication becomes available.

# 5. Wire-Level Behavior

Manual APCI generation was used to examine how the target implementation handled control frames and frame ordering.

Two implementation-specific behaviors were identified.

## 5.1 S-Format Frame Interleaving

During rapid transmission of control frames, the target generated an S-format acknowledgment between the expected U-format exchange:

```text
──► TX | TESTFR ACT
        68 04 43 00 00 00

◄── RX | S-FRAME
        68 04 01 00 02 00

◄── RX | TESTFR CON
        68 04 83 00 00 00
```

The S-format frame contains supervisory receive-state information rather than U-format control information.

This demonstrates an important property of TCP stream processing:

> **A client must parse IEC 104 frames according to APCI format rather than assuming that one transmitted control frame produces one immediately following response frame.**

A simplistic request/response parser could incorrectly interpret the S-frame as a malformed response to `TESTFR ACT`.

This is an **implementation-observed framing behavior**, not an assertion that IEC 104 requires S-frames to precede U-frame responses.

---

## 5.2 `STOPDT` Connection Teardown

The following behavior was observed when `STOPDT ACT` was transmitted to the non-threaded server:

```text
──► TX | STOPDT ACT
        68 04 13 00 00 00

◄── Socket Read Timeout / Connection Closed
```

The expected `STOPDT CON` was not captured before the connection was terminated. The observed behavior indicates that the `cs104_server_no_threads` implementation may terminate its communication context while processing the stop-data-transfer transition. This behavior should be treated as an **implementation-specific finding**. It does not establish that IEC 104 itself requires a TCP connection to terminate following `STOPDT ACT`.

# 6. Security Assessment

## 6.1 Lack of Native APCI Authentication

The tested IEC 104 APCI exchange does not contain an authentication step preceding `STARTDT ACT`.

The observed sequence is therefore:

```text
TCP Connect
     │
     ▼
STARTDT ACT
     │
     ▼
STARTDT CON
     │
     ▼
Data Transfer
```

No cryptographic identity exchange occurs within this native APCI sequence. Consequently, **network reachability to the IEC 104 endpoint is sufficient to participate in link-state negotiation** unless an external security mechanism or network control prevents access. This observation forms the security baseline for subsequent phases.

---

## 6.2 Control-Frame Exposure

The APCI U-format control functions are transmitted as clear protocol fields.

An observer capable of inspecting the connection can distinguish:

```text
STARTDT
STOPDT
TESTFR
```

without requiring ASDU decoding.

Likewise, an endpoint capable of injecting traffic into the communication path can attempt to introduce APCI control frames. The security significance of this behavior depends on the surrounding network architecture and whether additional protection mechanisms are deployed.

---

## 6.3 Keep-Alive Exposure

`TESTFR ACT` / `TESTFR CON` provides link supervision but does not itself establish peer identity.

The mechanism therefore provides:

```text
Link Liveness
      ≠
Peer Authentication
```

The exchange can confirm that an endpoint is responding, but the native U-format mechanism does not cryptographically establish who is generating or receiving the frame.

---

# 7. Hardening Considerations

The appropriate security control depends on the deployment architecture.

### Network Access Control

TCP/2404 should not be exposed beyond the network paths required for legitimate IEC 104 communication.

Recommended controls include:

* Firewall ACLs
* Strict source/destination filtering
* OT network segmentation
* Controlled routing between control centers and substations
* Monitoring of unexpected TCP/2404 connections

### IEC 62351 Protection

Where supported by the deployment and equipment, IEC 62351 mechanisms should be evaluated rather than treating native IEC 104 as the complete security architecture.

In particular:

* **IEC 62351-3** addresses security mechanisms for TCP/IP-based protocols.
* **IEC 62351-5** addresses security mechanisms for IEC 60870-5-based application profiles.
* **IEC TS 60870-5-7** defines security extensions for IEC 60870-5-101 and IEC 60870-5-104.

The security architecture should therefore be evaluated as:

```text
IEC 104
   │
   ▼
Network Protection
   │
   ▼
IEC 62351 Security Mechanisms
```

rather than assuming that APCI itself provides cryptographic security.

# Security Characteristics

Phase 1 establishes the baseline behavior of the IEC 104 communication channel before ASDU processing.

The research confirmed:

```text
TCP/2404
    │
    ▼
STOPPED
    │
    │ STARTDT ACT / CON
    ▼
DATA TRANSFER ACTIVE
    │
    ├── I-Format
    ├── S-Format
    └── U-Format
```

The primary security characteristic is the absence of native authentication in the APCI state-activation exchange.

The phase also demonstrated that **APCI parsing must be stateful and format-aware**. S-format acknowledgments and U-format control responses cannot safely be interpreted through a simplistic one-request/one-response model.

The `STOPDT` teardown behavior and S-frame interleaving observed during testing are retained as **implementation-specific observations against `lib60870-C / cs104_server_no_threads`**, rather than generalized protocol properties.

With the link-state and APCI baseline established, the next research phase can move into **ASDU processing, General Interrogation, and IOA enumeration**.
