# Phase 4: Security Boundaries & Implementation Edge Cases

* **Target Endpoint:** `127.0.0.1:2404` (`lib60870-C / cs104_server_no_threads`)
* **Layer:** IEC 60870-5-104 APCI Framing and ASDU Error Handling
* **Objective:** Evaluate handling of malformed APCI framing, payload-length inconsistencies, invalid U-format directives, unsupported ASDU Type IDs, and truncated application payloads.

---

## Executive Summary

Phase 4 evaluated the robustness of the target implementation when presented with malformed, incomplete, and semantically invalid IEC 104 frames.

The tested stack maintained **process stability throughout the malformed-input tests**. No unhandled exception, process crash, or observable memory-corruption condition was encountered.

APCI start-byte validation was enforced: frames beginning with an invalid start octet were rejected and the TCP connection was closed. An exaggerated APCI length caused the server to wait for the remaining bytes required to satisfy the declared frame length rather than processing the incomplete frame.

At the ASDU layer, unsupported Type IDs and truncated application payloads were discarded without disrupting the established communication session. Normal cyclic telemetry continued after these malformed-input tests.

The principal observation from Phase 4 is therefore not a demonstrated memory-safety vulnerability, but a set of **implementation-specific parser and error-handling characteristics**:

* strict APCI framing validation;
* blocking behavior when declared frame lengths exceed received data;
* silent rejection of unsupported or incomplete ASDUs;
* rejection of invalid U-format direction/state combinations;
* continued operation of the communication process after malformed input.

These behaviors establish the parser's current security boundaries.

---

# 1. APCI Framing & Length Handling

IEC 104 APDUs begin with the fixed start octet `0x68`, followed by a length field describing the number of bytes following the length octet.

A simplified frame structure is:

```text
+──────────────┬──────────────┬───────────────────────────────+
| Start (0x68) | Length (1B)  | Control Fields & ASDU         |
+──────────────┴──────────────┴───────────────────────────────+
       1B             1B              L bytes
```

For a minimum U-format or S-format APDU:

```text
68 04 [4-byte Control Field]
```

An I-format frame additionally contains the ASDU following the four control octets.

---

## 1.1 Invalid Start Octet

The first test replaced the mandatory `0x68` start octet with `0x99`:

```text
[TEST 1A]

──► TX
    99 04 07 00 00 00

◄── Connection closed by server
```

The target did not attempt to interpret the remaining bytes as an IEC 104 APDU.

### Analysis

The parser performs start-octet validation before proceeding to APDU interpretation.

The observed processing path is therefore:

```text
Receive Byte
     │
     ▼
Start == 0x68 ?
     │
     ├── YES ──► Continue APDU parsing
     │
     └── NO  ──► Reject / Close Connection
```

This prevents an invalid byte sequence from entering the subsequent frame-decoding stages.

---

## 1.2 Exaggerated APCI Length

A second test declared a frame length larger than the bytes actually transmitted:

```text
[TEST 1B]

──► TX
    68 FF 07 00 00 00

    Declared length: 255
    Bytes following length: 4

◄── Socket read timeout / connection remains pending
```

The parser did not process the four available control bytes as a complete APDU. Instead, it waited for additional stream data required to satisfy the declared length.

### Analysis

The observed behavior demonstrates that the implementation treats the APCI length field as a frame-boundary requirement.

```text
68
 │
 ▼
Length = 255
 │
 ▼
Wait for declared number of bytes
 │
 ├── Complete → Parse
 │
 └── Incomplete → Continue waiting / timeout
```

This prevents premature interpretation of a truncated frame.

However, the behavior also establishes a potential **resource-consumption consideration**: an attacker able to maintain multiple connections while supplying incomplete frames could potentially cause parser/socket resources to remain occupied until timeout. The current test demonstrates the condition, but does not establish a denial-of-service vulnerability by itself.

---

# 2. ASDU Type Identification Validation

The next test moved from APCI framing into ASDU semantic validation.

An unsupported Type Identification was transmitted:

```text
──► TX | I-FRAME
         Type ID: 255 (0xFF)
         VSQ: 1
         COT: 6
         CA: 1
```

The target did not return an explicit application-layer error during the test.

Normal telemetry subsequently continued:

```text
◄── RX | I-FRAME
         Type ID: 11
         M_ME_NB_1
```

---

## 2.1 Unsupported Type Handling

The observed behavior can be represented as:

```text
I-FRAME
   │
   ▼
ASDU Type ID = 255
   │
   ▼
Unsupported / Unrecognized
   │
   └──► Discarded
            │
            ▼
      Session remains active
            │
            ▼
      Telemetry continues
```

No process crash or transport reset was observed.

### Analysis

The important distinction is between **error response behavior** and **parser safety**.

The target did not produce the explicit negative response expected by the test methodology for an unsupported ASDU. Instead, the malformed/unsupported ASDU was silently discarded.

This represents an **error-reporting and observability characteristic**, rather than evidence of memory corruption or parser instability.

It also should not be described as "missing COT 44" without first establishing that the specific negative response being expected is defined for this exact condition by the relevant IEC 104 application semantics.

For the research record:

> **Unsupported Type ID `255` was silently discarded by the tested implementation while the IEC 104 session remained operational.**

---

# 3. Directional U-Format Control Enforcement

U-format frames contain control functions used for link activation, deactivation, and testing.

The test deliberately transmitted a confirmation message from the client side where an activation request would normally originate:

```text
──► TX | U-FRAME
         STARTDT CON
         68 04 0B 00 00 00

◄── No state transition / connection timeout
```

The server did not treat the inbound confirmation as a valid request to activate the data-transfer state.

---

## 3.1 Directional State Validation

The observed behavior can be represented as:

```text
Client / Master                     RTU / Server

STARTDT ACT ───────────────────────►
           ◄──────────────── STARTDT CON

STARTDT CON ────────────────────────►
              Invalid inbound state/direction
```

The implementation therefore distinguishes between:

* a valid activation request;
* a confirmation generated in response to an activation request.

The server did not transition the link into the active state merely because it received a `STARTDT CON`.

### Security Characteristic

This prevents an unauthenticated peer from arbitrarily constructing a confirmation frame and using it as a substitute for the expected state-transition sequence. The behavior demonstrates **state-machine validation**, not authentication.

---

# 4. ASDU Payload Truncation

The final parser test supplied an incomplete ASDU while declaring a longer APCI payload:

```text
──► TX | I-FRAME
         Declared APCI Length: 10
         Actual ASDU data: 2 bytes

◄── No malformed ASDU processing
```

The target continued transmitting valid telemetry:

```text
◄── RX | I-FRAME
         Type ID: 11
         Telemetry continues
```

---

## 4.1 Truncated Payload Handling

The observed processing path is:

```text
APCI Header
    │
    ▼
Declared Length
    │
    ▼
Insufficient Bytes
    │
    ▼
Incomplete APDU
    │
    └──► Not processed as valid ASDU
```

No process crash or observable memory-access failure occurred.

### Analysis

The implementation therefore does not appear to pass the incomplete payload directly into normal ASDU processing.

This provides evidence of a basic framing boundary between:

```text
APCI Stream Parser
        │
        ▼
Complete APDU
        │
        ▼
ASDU Decoder
```

The test does not establish complete protection against all malformed length combinations. It establishes only that the tested truncation condition did not result in an observed process failure.

# 6. Security Analysis

## 6.1 Parser Stability

The most significant positive result from Phase 4 is process stability.

Across the malformed-input tests:

```text
Invalid Start
      │
Invalid Length
      │
Invalid Type
      │
Invalid Direction
      │
Truncated Payload
      │
      ▼
No observed process crash
```

No unhandled exception or termination of the server process was observed during testing. This establishes a baseline of robustness for the tested parser implementation. It should not, however, be interpreted as proof of complete parser security. The test set covers selected malformed conditions rather than exhaustive fuzzing.

---

## 6.2 Silent Error Handling

Unsupported and incomplete application data were discarded without an explicit application-layer error response. This has two consequences.

First, it contributes to process stability:

```text
Malformed ASDU
      │
      ▼
Discard
      │
      ▼
Session continues
```

Second, it reduces protocol-level visibility into malformed traffic.

Without additional instrumentation, an operator may not be able to distinguish between:

```text
No application traffic
        ≠
Malformed application traffic
```

This becomes relevant for protocol-aware monitoring and intrusion detection.

---

## 6.3 Incomplete-Length Resource Consumption

The exaggerated-length test produced a different behavior:

```text
Declared Length = 255
        │
        ▼
Parser expects additional bytes
        │
        ▼
Socket remains pending
        │
        ▼
Timeout
```

This is not yet a demonstrated denial-of-service condition.

However, it identifies a potentially useful attack surface for subsequent testing:

* multiple simultaneous incomplete frames;
* multiple partially established TCP sessions;
* repeated large declared lengths;
* slow byte-by-byte delivery;
* interaction with connection limits and worker threads;
* timeout behavior under concurrent incomplete streams.

The implementation's resource behavior under these conditions should be measured before assigning a security severity.

# 7. Recommendations

### 1. Instrument Parser Rejection Paths

Malformed frames should generate structured internal security events identifying conditions such as:

```text
INVALID_START
INVALID_LENGTH
UNSUPPORTED_TYPE
TRUNCATED_APDU
INVALID_U_STATE
```

This provides visibility without necessarily requiring a protocol-level response to every malformed packet.

### 2. Apply Bounded Read Timeouts

APCI stream parsing should enforce appropriate read and connection timeouts for incomplete frames.

Resource limits should also be applied to:

* concurrent connections;
* incomplete APDUs;
* connection buffers;
* parser state;
* repeated malformed requests.

### 3. Preserve Strict Frame Validation

The existing rejection of invalid start octets and incomplete APDUs should remain enforced before ASDU decoding.

The parser should maintain the boundary:

```text
TCP Stream
    │
    ▼
APCI Validation
    │
    ▼
Complete APDU
    │
    ▼
ASDU Validation
    │
    ▼
Application Processing
```

### 4. Validate U-Format State Transitions

U-format commands should continue to be validated against the current communication state and expected direction. Confirmation frames should not independently create state transitions.

### 5. Expand Fuzzing Coverage

The Phase 4 results provide a starting point for systematic parser fuzzing.

Future cases should include:

```text
Length = 0
Length = 1
Length = 3
Length = 4
Length = 253
Length = 254
Length = 255

Reserved U-format combinations
Invalid I/S/U bit patterns
Malformed VSQ values
Invalid COT combinations
Invalid CA values
Boundary IOAs
Duplicate / conflicting sequence values
Truncated type-specific payloads
```

The objective should be to determine whether the observed parser stability persists across the complete APCI and ASDU boundary space.

# Security Characteristics

Phase 4 establishes that the tested `lib60870-C / cs104_server_no_threads` implementation maintains several important parser and state-machine boundaries.

```text
                    IEC 104 Input
                         │
                         ▼
                +------------------+
                | APCI Framing     |
                | Validation       |
                +------------------+
                  │       │
             Valid │       │ Invalid
                  ▼       ▼
              Continue   Reject
                  │
                  ▼
             Complete APDU
                  │
                  ▼
            ASDU Validation
                  │
          ┌───────┼────────┐
          │       │        │
       Valid    Invalid   Truncated
          │       │        │
          ▼       └────┬───┘
       Process          ▼
                    Discard
```

The tested implementation demonstrated:

* **strict start-byte validation;**
* **length-aware stream parsing;**
* **stable handling of unsupported Type IDs;**
* **stable handling of truncated application payloads;**
* **U-format state/direction validation;**
* **no observed process crash during the tested malformed-input cases.**

The principal security consideration identified in this phase is the **resource behavior associated with incomplete APDUs**. An exaggerated length causes the parser to wait for additional stream data, making connection and timeout management relevant to denial-of-service resistance.

The silent rejection of malformed ASDUs also establishes an important monitoring limitation: **protocol-invalid traffic may not produce an explicit IEC 104 error response even though the input was rejected internally.**
