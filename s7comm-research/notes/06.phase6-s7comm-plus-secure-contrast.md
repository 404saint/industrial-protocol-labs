# Phase 6: S7CommPlus & Modern Protection Contrast

* **Target Reference:** Siemens S7-1200 / S7-1500 security architecture and S7CommPlus research
* **Protocol Layer:** S7comm / S7CommPlus application communication
* **Lab Dependency:** No additional PLC lab required
* **Objective:** Contrast the classic S7comm behavior observed in Phases 1–5 with the security mechanisms introduced through S7CommPlus and modern Siemens CPU protection.

---

## Executive Summary

The first five phases examined the classic S7comm communication model from the wire up.

The laboratory target accepted ISO-on-TCP connections on TCP/102, negotiated communication parameters through Setup Communication, exposed variable services through `ReadVar` and `WriteVar`, returned diagnostic information through UserData/SZL services, and demonstrated incomplete session-state enforcement when a `ReadVar` request was processed before Setup Communication.

Those observations describe the behavior of the **Snap7 implementation used throughout this research**. They do not represent the security properties of every Siemens PLC generation.

Modern Siemens controllers introduced a substantially different security model around S7CommPlus and related protection mechanisms. Public technical research describes session establishment involving challenge and key material, session identifiers, and cryptographic integrity protection. Newer S7-1500 communication documentation also describes TLS-based secure PG/PC and HMI communication, while Siemens CPU documentation defines configurable access-protection levels controlling operations such as reading, writing, and changing CPU operating state.

The resulting contrast is therefore broader than a simple protocol replacement.

Classic S7comm places considerable trust in the network path and the communicating endpoint. Modern Siemens architectures add authentication, access-control decisions, cryptographic protection, and, for supported secure communication paths, TLS.

This phase documents those architectural differences and maps them against the behaviors observed during the laboratory research.

# 1. From Classic S7comm to S7CommPlus

The classic communication model examined in this research can be represented as:

```text 
TCP / 102
    │
    ▼
TPKT
    │
    ▼
COTP
    │
    ▼
S7comm
    │
    ├── Setup Communication
    ├── ReadVar
    ├── WriteVar
    └── UserData / SZL
```

This model was visible throughout the laboratory work.

⟶ Phase 1 established the TCP/102, TPKT and COTP session.

⟶ Phase 2 established the S7comm communication parameters and `ReadVar` operation.

⟶ Phase 3 exercised `WriteVar` and constructed a CPU-control UserData request.

⟶ Phase 4 queried SZL diagnostic information.

⟶ Phase 5 tested whether the target enforced expected communication-state ordering.

S7CommPlus retains the underlying network transport context, but introduces a different application-layer communication model and security architecture. Public research identifies a distinct S7CommPlus protocol layer following the TCP/COTP connection and documents session establishment, session identifiers, challenge material and cryptographic integrity mechanisms.

The comparison is therefore:

| Area                 | Classic S7comm                                | S7CommPlus / modern communication                                  |
| -------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
| Network endpoint     | TCP/102                                       | TCP/102                                                            |
| Lower transport      | TPKT / COTP                                   | TPKT / COTP remains relevant to connection establishment           |
| Application protocol | S7comm                                        | S7CommPlus                                                         |
| Session model        | S7comm communication setup                    | Security-aware session establishment                               |
| Session identity     | COTP/S7comm references                        | Session identifiers are incorporated into the security model       |
| Message protection   | No cryptographic integrity in classic traffic | Cryptographic integrity mechanisms are used by S7CommPlus variants |
| Confidentiality      | None in classic S7comm                        | Available through supported secure/TLS communication paths         |
| Access control       | Implementation/configuration dependent        | CPU protection levels and secure communication controls            |
| Research visibility  | Largely readable directly from the wire       | Security-sensitive portions require session/protocol context       |

# 2. Session Establishment & Key Material

The most significant conceptual difference is the treatment of the communication session.

The classic S7comm sessions observed during this research followed:

```text 
TCP
 │
 ▼
COTP CR / CC
 │
 ▼
Setup Communication
 │
 ▼
S7comm services
```

No cryptographic session establishment was observed.

The S7CommPlus model introduces additional session-security mechanisms. Public research describes a sequence in which the PLC provides session-related challenge material, after which the client derives or constructs security/session-key material and presents it to the PLC for verification. Later protocol generations introduced stronger challenge-response mechanisms involving public-key cryptography.

A simplified representation is:

```text 
TCP / COTP
    │
    ▼
S7CommPlus Session Initialization
    │
    ▼
PLC Challenge / Session Information
    │
    ▼
Key / Security Material
    │
    ▼
Verification
    │
    ▼
Protected Session
```

The important architectural change is that application operations are associated with an authenticated or integrity-protected communication context rather than being treated as ordinary plaintext S7comm requests immediately following session establishment.

The exact handshake varies across S7CommPlus generations and firmware families. Public research distinguishes earlier and later mechanisms, including older key-synchronization approaches and newer challenge-response mechanisms using elliptic-curve public-key cryptography. This is one reason the phase does not attempt to reproduce a single universal S7CommPlus handshake.

# 3. Session Integrity

Phase 3 demonstrated that classic S7comm application requests can be constructed directly and transmitted as ordinary S7comm PDUs.

For example:

```text 
S7comm Job
    │
    ├── ROSCTR
    ├── Function
    ├── Variable specification
    └── Data
```

The target processes the PDU according to its protocol fields.

S7CommPlus adds cryptographic integrity to the protected communication context. Research into the protocol describes integrity material associated with subsequent function requests and responses, allowing the PLC to verify that protected messages belong to the established session and have not been modified outside the expected security mechanism. This changes the security meaning of packet manipulation.

In the classic S7comm model examined in the lab:

```text 
Construct valid S7comm PDU
          │
          ▼
Transmit to target
          │
          ▼
Target parses request
```

In an integrity-protected S7CommPlus session:

```text 
Construct protected request
          │
          ▼
Session security context
          │
          ▼
Integrity verification
          │
          ├── Valid ───► Process request
          │
          └── Invalid ─► Reject
```

This is the architectural boundary that the classic S7comm experiments do not provide.

# 4. Access Protection

Cryptographic session protection and CPU access control address different problems.

Siemens documentation for S7-1200 describes four CPU access levels:

| Protection level                | Documented behavior                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Full access / no protection     | Full access without password protection                                                                                       |
| Read access                     | Reading remains available without a password while modification and CPU mode changes require authentication                   |
| HMI access                      | HMI and PLC-to-PLC communication remain available while CPU reading, modification and RUN/STOP changes require authentication |
| No access / complete protection | CPU access requires the configured password                                                                                   |

The precise behavior depends on the CPU family and configuration. Siemens security documentation similarly describes multiple access levels across S7 CPU families and notes that the newer S7-1200/S7-1500 generations provide additional protection levels. This provides an important contrast with the Snap7 laboratory configuration.

During Phase 3, the target accepted:

```text 
S7comm session
      │
      ▼
WriteVar DB3
      │
      ▼
0xFF Success
```

No authentication step was required in that lab configuration.

The appropriate comparison is therefore:

```text
Snap7 laboratory configuration
    │
    └── WriteVar accepted without an authentication step

Modern protected Siemens CPU
    │
    └── Access level determines which operations require authorization
```

The Snap7 observation should not be interpreted as evidence that every modern Siemens CPU accepts equivalent write operations without protection.

# 5. Protection of CPU State Changes

Phase 3 also explored CPU control through S7comm UserData.

The packet was constructed and transmitted, but the Snap7 implementation did not implement the requested CPU-control function. No real PLC state transition was demonstrated. Modern Siemens CPU protection explicitly treats operating-state changes as an access-controlled operation under relevant protection configurations.

For example, Siemens documentation states that under the S7-1200 **Read access** level, changing the CPU mode between RUN and STOP requires the corresponding password. Under stronger protection levels, additional CPU operations are restricted.

The contrast is therefore conceptual rather than experimental:

```text 
Phase 3 laboratory result
    │
    ├── CPU-control request constructed
    └── Snap7 implementation did not execute it

Modern CPU protection model
    │
    └── CPU operating-state changes can be subject to
        configured access protection
```

This is another case where the research must distinguish protocol construction from target behavior.

---

# 6. Confidentiality & TLS

Classic S7comm traffic observed throughout Phases 1–5 was directly inspectable at the application layer. The PDU fields, variable specifications, diagnostic requests and returned values could be decoded from the capture.

Modern Siemens communication adds TLS-based secure communication for supported S7-1500 configurations. Siemens documentation identifies TLS 1.2 and TLS 1.3 support for relevant S7-1500 firmware generations and describes certificate management for secure PG/PC and HMI communication.

Siemens ProductCERT also documents the transition toward TLS-protected PG/PC and HMI communication and recommends enabling secure communication configurations on supported devices.

This creates a clear difference:

```text 
Classic S7comm
    │
    └── Application data visible on the wire

Modern secure communication
    │
    └── TLS / cryptographic protection
             │
             ├── Confidentiality
             └── Integrity
```

The presence of TLS should not be treated as synonymous with all S7CommPlus implementations. Siemens communication capabilities vary by CPU generation, firmware version, service and configuration.

## S7CommPlus

```text id="4xq7pn"
Ethernet
   │
   ▼
IP
   │
   ▼
TCP / 102
   │
   ▼
TPKT / COTP
   │
```

Public protocol research identifies S7CommPlus-specific message structures and application-layer opcodes. The protocol has also evolved through multiple generations, so individual field layouts and security mechanisms should be treated as version-specific rather than universal.

This is important when analyzing modern captures. A classic S7comm dissector and a S7CommPlus dissector are describing different application-layer protocols even though both can operate through the same TCP/102 endpoint.

# 9. What the Snap7 Laboratory Represents

Snap7 was deliberately useful throughout this research because it provided a controllable implementation of the classic S7 communication model.

It allowed the investigation to reach the wire quickly:

```text id="z8h3rx"
COTP
  ↓
S7comm
  ↓
PDU negotiation
  ↓
Variable access
  ↓
Diagnostics
  ↓
State anomalies
```

That makes the resulting observations valuable for understanding classic S7comm mechanics, but it also creates a clear boundary. The Snap7 target is **not a substitute for a Siemens S7-1200 or S7-1500 firmware implementation**. Its accepted services, access-control behavior, diagnostic surface and state-machine enforcement reflect the implementation being tested.

Consequently:

* The successful Phase 3 write is a Snap7 laboratory observation.
* The Phase 4 SZL responses are Snap7 implementation observations.
* The Phase 5 pre-Setup ReadVar behavior is a Snap7 state-machine observation.
* The Phase 5 resource-handling result is a Snap7 resilience observation.
* The S7CommPlus security mechanisms described in this phase come from Siemens documentation and independent protocol research rather than a live S7CommPlus experiment.

Keeping those boundaries explicit makes the comparison more useful rather than less.

# 10. Security Evolution

The overall progression can be represented as:

```text id="p5w1zk"
Classic S7comm
     │
     ├── TCP/102
     ├── COTP
     ├── S7comm PDUs
     ├── Variable services
     └── UserData diagnostics
             │
             ▼
   Trust largely placed on
   network and endpoint controls
             │
             ▼
      S7CommPlus evolution
             │
             ├── Session identity
             ├── Authentication / authorization
             ├── Session key mechanisms
             ├── Message integrity
             └── Secure communication / TLS
                     │
                     ▼
          Modern protected deployment
```

The evolution is therefore not simply a change in packet format. It represents a change in where security decisions are made. The classic S7comm experiments demonstrated that once an endpoint accepts a communication session, application services can become directly accessible. Modern Siemens architectures add security controls between session establishment and sensitive operations, with the exact mechanism depending on CPU generation, firmware and configuration.

# 11. Security Characteristics

## 11.1 Session Security

Classic S7comm sessions observed during the research did not establish a cryptographic session key. S7CommPlus research documents session identifiers, challenge material and cryptographic key establishment mechanisms that bind subsequent communication to a security-aware session.

## 11.2 Message Integrity

The classic S7comm PDUs tested in this laboratory were directly constructed and transmitted without a cryptographic integrity layer. S7CommPlus research documents integrity protection for protected function messages, providing a mechanism for the PLC to verify the integrity and session association of received operations.

## 11.3 Access Control

Modern S7-1200 and S7-1500 families provide configurable CPU protection levels that determine which functions can be performed without the appropriate authorization.

## 11.4 Confidentiality

Classic S7comm traffic observed in this research was readable at the application layer. Supported modern Siemens secure communication configurations can use TLS, with Siemens documentation listing TLS 1.2 and TLS 1.3 support for applicable S7-1500 firmware generations.

## 11.5 Protocol Evolution

S7CommPlus exists in multiple generations and configurations. Earlier and later implementations differ in their session-security mechanisms, and newer deployments can combine S7CommPlus with TLS-based secure communication. Therefore, “S7CommPlus” should not be treated as one immutable wire format or one universal security configuration.

---

# 12. Defensive Considerations

The comparison produces several practical defensive considerations for environments containing Siemens PLCs.

* Determine the exact PLC family and firmware version before assessing S7 communication security.
* Identify whether classic or modern communication paths are enabled.
* Configure CPU access protection appropriate to the required engineering, HMI and PLC-to-PLC functions.
* Prefer supported secure PG/PC and HMI communication where the device and engineering environment support it.
* Maintain current CPU firmware and TIA Portal versions.
* Restrict TCP/102 exposure at the network boundary even when cryptographic protections are enabled.
* Treat legacy communication compatibility as a security consideration rather than assuming that a modern CPU automatically means every communication path is protected.
* Monitor both classic S7comm and S7CommPlus traffic according to the protocol generations actually deployed.

Siemens has explicitly documented cases where legacy PG/PC and HMI communication provides a weaker security posture than TLS-based communication and recommends updating affected products and configuring secure communication where supported.

Phase 6 closes the S7comm research by putting the laboratory observations into their proper historical and architectural context.

The classic S7comm model made it possible to directly observe session establishment, variable access, diagnostics and state-machine behavior at the wire level. The Snap7 target reproduced enough of that model to investigate those mechanics in detail.

Modern Siemens controllers introduce additional security layers around that communication model. S7CommPlus adds session-aware security and cryptographic integrity mechanisms, while newer Siemens platforms provide configurable access protection and supported TLS-based communication paths.

The result is not that the older protocol suddenly becomes irrelevant. The opposite is true. Understanding classic S7comm provides the vocabulary needed to recognize what modern Siemens communication is attempting to protect: session establishment, authorization, command integrity, diagnostic exposure, and control operations.

That completes the S7comm protocol research sequence from transport establishment through application services, diagnostics, state anomalies, and modern security contrast.
