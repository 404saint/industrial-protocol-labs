# Phase 1: Transport & Session Layer Initialization (TPKT/COTP)

* **Target Server:** `127.0.0.1:102` (`Snap7 1.4.2 / Native C++ Server`)
* **Protocol Layer:** ISO-on-TCP / TPKT / COTP
* **Objective:** Examine TPKT framing, COTP connection establishment, reference handling, TSAP parameter encoding, and session behavior prior to S7comm PDU negotiation.

---

## Executive Summary

Phase 1 examined the transport and session establishment sequence required before S7comm application services can execute.

A TCP connection to port `102` established the underlying transport connection, after which a manually crafted TPKT/COTP Connection Request (`CR`) was transmitted to the Snap7-based target. The server returned a COTP Connection Confirm (`CC`), establishing the ISO-on-TCP session required for subsequent S7comm communication. The baseline exchange confirmed the expected TPKT version and packet-length fields, COTP `CR` / `CC` types, connection references, Siemens-specific TSAP parameters, and COTP TPDU size negotiation.

Additional testing modified the Destination TSAP to examine how the target handled unusual rack/slot and connection-type values. Both tested values received successful `CC` responses from the Snap7 implementation, demonstrating permissive TSAP handling at the tested transport endpoint. These results are scoped to the Snap7 1.4.2 target used in the laboratory. They do not establish equivalent behavior on physical Siemens PLCs.

---

# 1. Protocol Architecture & Encapsulation

Classic S7comm communication is carried over ISO-on-TCP. TCP provides the underlying byte-stream transport, while TPKT and COTP establish the framing and transport session used before S7comm messages are exchanged.

The observed encapsulation is:

```text
+------------------------------------------------------+
| TCP / Port 102                                       |
+------------------------------------------------------+
| TPKT Header                                          |
| Version | Reserved | Packet Length                   |
+------------------------------------------------------+
| COTP TPDU                                            |
| CR / CC + Connection Parameters                      |
+------------------------------------------------------+
| S7comm PDU                                           |
| Negotiated and processed after session establishment |
+------------------------------------------------------+
```

Phase 1 is concerned only with the layers preceding the S7comm PDU. The transition into the S7comm layer occurs after successful COTP connection establishment.

---

# 2. TPKT Framing

TPKT provides packet boundaries above the TCP byte stream.

The four-byte TPKT header observed during the baseline exchange was:

```text
03 00 00 16
```

The fields are:

| Field         | Value    | Meaning                   |
| ------------- | -------- | ------------------------- |
| Version       | `0x03`   | TPKT version              |
| Reserved      | `0x00`   | Reserved field            |
| Packet Length | `0x0016` | 22-byte total TPKT packet |

The packet length includes the four-byte TPKT header.

The baseline CR therefore begins: `03 00 00 16` and the returned CC uses the same framing: `03 00 00 16`. TPKT does not interpret the S7comm application data. Its role at this layer is to provide explicit packet boundaries over TCP.

---

# 3. COTP Connection Establishment

The COTP layer provides the connection-oriented transport session used by the S7comm communication path.

The baseline exchange consisted of:

```text
Client                              Server
  │                                   │
  │──── COTP CR (0xE0) ──────────────►│
  │                                   │
  │◄─── COTP CC (0xD0) ───────────────│
  │                                   │
  │──── ISO-on-TCP session ───────────│
  │                                   │
```

The client transmitted:

```text
03 00 00 16
11 E0
00 00
00 01
00
C2 02 01 02
C1 02 01 00
C0 01 09
```

The server returned:

```text
03 00 00 16
11 D0
00 01
00 01
00
C2 02 01 02
C1 02 01 00
C0 01 09
```

The COTP TPDU codes identify the connection operation:

```text
0xE0 → Connection Request (CR)
0xD0 → Connection Confirm (CC)
```

Successful receipt of the `CC` established the transport session required for the next S7comm layer.

---

# 4. COTP Reference Handling

The client CR contained:

```text
Destination Reference: 0x0000
Source Reference:      0x0001
```

The target returned:

```text
Destination Reference: 0x0001
Source Reference:      0x0001
```

The destination reference was therefore changed from `0x0000` in the request to `0x0001` in the response. The exchange demonstrates the use of COTP connection references as part of the transport-session state. These references belong to the COTP layer and should be distinguished from identifiers used later by S7comm itself.

---

# 5. TSAP Parameter Encoding

The baseline connection contained two TSAP parameters:

```text
C2 02 01 02
C1 02 01 00
```

The parameter identifiers are:

```text
C2 → Destination TSAP
C1 → Source TSAP
```

For this laboratory exchange, the Destination TSAP was: `01 02` and the research harness represented this as:

```text
Connection Type: 1
Rack:            0
Slot:            2
```

The Source TSAP was: `01 00`.  These values demonstrate an important distinction when analyzing S7 traffic. The parameters are transported as COTP connection information, while their interpretation as Siemens-specific connection type and rack/slot values comes from the S7 communication convention rather than from generic COTP semantics alone.

The baseline target accepted: `Destination TSAP: 0x0102` and returned the same value in the CC.

---

# 6. COTP TPDU Size

The CR and CC both contained:

```text
C0 01 09
```

This represents the COTP TPDU Size parameter. The value `0x09` corresponds to a 512-byte TPDU size. This value should not be confused with the S7comm PDU size negotiated later during S7 communication setup.

The difference is:

```text
COTP TPDU Size
       │
       ▼
Transport-layer characteristic

S7comm PDU Size
       │
       ▼
Application-layer communication parameter
```

Phase 1 therefore establishes the transport-level value without drawing conclusions about the S7comm PDU negotiation that follows.

---

# 7. Baseline Wire-Level Exchange

The complete baseline client transmission was:

```text
03 00 00 16 11 E0 00 00 00 01 00
C2 02 01 02
C1 02 01 00
C0 01 09
```

The corresponding server response was:

```text
03 00 00 16 11 D0 00 01 00 01 00
C2 02 01 02
C1 02 01 00
C0 01 09
```

The measured handshake RTT was approximately:

```text
1.75 ms
```

The captured PCAP independently confirmed the CR/CC sequence:

```text
127.0.0.1 → 127.0.0.1    COTP  CR TPDU
127.0.0.1 → 127.0.0.1    COTP  CC TPDU
```

The resulting state can therefore be represented as:

```text
TCP Connection
      │
      ▼
TPKT Framing
      │
      ▼
COTP CR
      │
      ▼
COTP CC
      │
      ▼
ISO-on-TCP Session Established
      │
      ▼
S7comm Communication Setup
```

The final step belongs to Phase 2.

# 8. TSAP Boundary Testing

After establishing the baseline exchange, the research harness modified the Destination TSAP to examine the target's handling of unusual routing parameters.

Two test cases were performed.

## 8.1 Out-of-Range Rack/Slot

The tested Destination TSAP was:

```text
0x01FF
```

The research harness interpreted this as:

```text
Connection Type: 1
Rack:            7
Slot:            31
```

The target returned: `COTP CC`, rather than rejecting the connection during COTP establishment. This demonstrates that the tested Snap7 implementation accepted the supplied TSAP value at the transport/session layer. It does not establish that the same value would be accepted by a physical Siemens CPU, nor does it demonstrate where such a value would ultimately be validated if subsequent S7 communication were attempted.

---

## 8.2 Unusual Connection Type

The second test used: `0x0F02` instead of the connection type used by the baseline request. The target again returned: `COTP CC` . The tested Snap7 implementation therefore did not reject the unusual connection-type value during COTP session establishment. As with the rack/slot test, this is an implementation-specific observation.

The result can be summarized as:

```text
                    Snap7 Target
                         │
             ┌───────────┴───────────┐
             │                       │
      0x01FF TSAP              0x0F02 TSAP
             │                       │
             ▼                       ▼
          COTP CC                 COTP CC
             │                       │
             └───────────┬───────────┘
                         ▼
                 Accepted at COTP
```

The significance of this observation is therefore the target's validation behavior, rather than a claim about S7 TSAP processing in general.

---

# 9. Session Handling

The server recorded three client connections during the test sequence:

```text
[127.0.0.1] Client added
[127.0.0.1] Client disconnected by peer
```

The sequence repeated for the tested connections. These logs corroborate that the target accepted the TCP connections and subsequently observed peer-initiated termination. The PCAP remains the primary protocol evidence because it exposes the actual TPKT and COTP fields exchanged during each connection. No connection timeout or channel-saturation behavior was established during this phase. Those conditions require dedicated testing and are therefore left outside the current findings.

---

# 10. Detection & PCAP Analysis

The captured traffic can be isolated in Wireshark using:

```text
cotp.type == 0x0e || cotp.type == 0x0d || tpkt
```

The captured tshark output included:

```text
COTP  CR TPDU src-ref: 0x0001 dst-ref: 0x0000
COTP  CC TPDU src-ref: 0x0001 dst-ref: 0x0001
```

The transport exchange can therefore be identified before decoding higher-level S7comm services.

A monitoring implementation observing TCP/102 can use the TPKT/COTP layer to identify:

```text
TCP connection
      │
      ▼
TPKT packet
      │
      ▼
COTP CR / CC
      │
      ▼
S7comm traffic
```

This provides a useful protocol boundary for subsequent detection work.

# 11. Security Characteristics

## 11.1 Transport Reachability

The tested endpoint accepted TCP connections on port `102` and proceeded directly into COTP session establishment. No authentication mechanism was observed during the TPKT/COTP exchange. Transport reachability therefore establishes the ability to participate in the initial session negotiation of the tested implementation.

---

## 11.2 TSAP Validation

The Snap7 target accepted both tested non-standard Destination TSAP values:

```text
0x01FF
0x0F02
```

The observation indicates permissive TSAP handling at the tested COTP endpoint. The result should remain scoped to the Snap7 implementation rather than being generalized to Siemens PLCs.

---

## 11.3 Clear Transport Metadata

The transport exchange exposes:

```text
TPKT version
Packet length
COTP PDU type
Connection references
Source TSAP
Destination TSAP
TPDU size
```

These fields are directly observable from the captured traffic and provide useful metadata for passive protocol identification.

# Hardening Considerations

The security controls applied around TCP/102 should account for the fact that transport/session establishment occurs before any higher-level S7comm access-control behavior.

Relevant controls include:

* Restricting TCP/102 to authorized engineering, HMI, and supervisory hosts.
* Applying network segmentation between control systems and general-purpose networks.
* Filtering unexpected sources attempting to establish S7 communication sessions.
* Monitoring repeated COTP `CR` attempts and unusual TSAP values.
* Applying controller-level access protection where supported.
* Evaluating modern Siemens secure communication mechanisms rather than assuming that classic S7comm transport provides cryptographic protection.

For passive monitoring, TSAP values can provide additional context when identifying the intended Siemens communication relationship, while repeated unusual values can serve as an investigation signal.
