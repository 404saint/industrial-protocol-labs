# S7comm Architecture & Protocol Research Primer

## Executive Summary

S7comm is a Siemens communication protocol used by engineering systems, HMIs, supervisory applications, and other clients to communicate with compatible SIMATIC controllers.

Classic S7comm is carried over an ISO-on-TCP communication stack. A connection to a PLC therefore passes through several protocol layers before an S7-specific request is interpreted by the CPU:

```text
Application
    │
    ▼
  S7comm
    │
    ▼
   COTP
    │
    ▼
   TPKT
    │
    ▼
 TCP / 102
    │
    ▼
 IP / Ethernet
```

The S7comm layer provides services for establishing communication parameters, accessing PLC variables, retrieving system information, and interacting with controller functions. These services operate against the PLC's logical memory and system model rather than against an arbitrary byte stream.

Understanding S7comm therefore requires three related perspectives:

* the **transport path** that carries the communication;
* the **S7comm message model** used to represent requests and responses;
* the **PLC model** that gives those requests meaning.

This primer establishes those concepts without attempting to reproduce the complete S7comm specification. The objective is to provide the architectural vocabulary required to understand the protocol traffic examined throughout the research.

---

# 1. S7comm in the Siemens Communication Architecture

S7comm exists within a broader Siemens automation environment. A typical communication relationship may involve an engineering workstation, HMI, SCADA system, or another industrial application communicating with a PLC CPU.

```text
Engineering / HMI / Supervisory System
                  │
                  ▼
               S7comm
                  │
                  ▼
              SIMATIC CPU
```

The client and PLC do not communicate through S7comm alone. S7comm provides the application-level protocol while the lower layers establish and carry the communication channel. This is important because a packet capture may contain information belonging to several different layers at once. A TCP segment establishes the network transport, TPKT frames the ISO-on-TCP data, COTP manages the connection-oriented transport exchange, and the S7comm payload carries the PLC-specific request. S7comm is therefore best understood as the application protocol sitting above the ISO-on-TCP transport path.

---

# 2. The ISO-on-TCP Communication Stack

Classic S7comm traffic is commonly encountered on TCP port 102, the port associated with RFC 1006 ISO-on-TCP communication in Siemens systems. Siemens documentation identifies TCP/102 as the RFC 1006 service port for relevant S7 communication environments.

The protocol stack can be represented as:

```text
+---------------------------+
|          S7comm           |
+---------------------------+
|           COTP            |
+---------------------------+
|           TPKT            |
+---------------------------+
|            TCP            |
+---------------------------+
|             IP            |
+---------------------------+
|          Ethernet         |
+---------------------------+
```

Each layer has a different responsibility.

⟶ **Ethernet** provides the local network frame.

⟶ **IP** provides network-layer addressing.

⟶ **TCP** provides the reliable byte-stream transport.

⟶ **TPKT** provides packet framing for ISO transport protocols carried over TCP.

⟶ **COTP** provides the connection-oriented transport protocol used by the ISO-on-TCP communication model.

⟶ **S7comm** provides the Siemens-specific application messages exchanged after the underlying communication path has been established.

This layered structure is fundamental to packet analysis because an S7comm request cannot be interpreted correctly until the surrounding TPKT and COTP structure has been identified.

---

# 3. TPKT

The **Transport Packet** mechanism defined by RFC 1006 allows ISO transport protocol data to be carried over a TCP byte stream. A TPKT header provides the framing information required to determine where an ISO transport packet begins and ends.

Its basic structure is:

```text
TPKT
+-----------------------------+
| Version                     |
+-----------------------------+
| Reserved                    |
+-----------------------------+
| Packet Length               |
+-----------------------------+
| TPKT Payload                |
+-----------------------------+
```

The version field identifies the TPKT format, while the packet length describes the complete TPKT packet. TPKT therefore provides a boundary between TCP's continuous byte stream and the packet-oriented structure expected by the ISO transport layer above it. The S7comm application does not replace this mechanism. It is carried inside it.

---

# 4. COTP

The **Connection-Oriented Transport Protocol (COTP)** provides the transport connection semantics used by ISO-on-TCP communication.

COTP messages appear between TPKT and S7comm:

```text
TPKT
  │
  └── COTP
        │
        └── S7comm
```

Connection establishment uses COTP connection request and connection confirmation PDUs. In a simplified exchange:

```text
Client                         PLC
  │                             │
  │──── COTP Connection ──────► │
  │       Request (CR)          │
  │                             │
  │◄─── COTP Connection ─────── │
  │       Confirm (CC)          │
  │                             │
  │──── S7 communication ─────► │
  │                             │
```

COTP therefore establishes the transport context in which the S7-specific communication can occur.

The COTP layer also carries addressing information used by the communication endpoints. In Siemens environments, connection parameters such as TSAP values are associated with the PLC communication endpoint and can encode information relevant to the selected communication access point. The exact values and behavior depend on the controller and configuration under examination and should therefore be treated as implementation data rather than as universal constants.

---

# 5. The S7comm PDU Model

Once the underlying transport connection has been established, communication moves into the S7comm layer.

An S7comm PDU can be viewed conceptually as three major components:

```text
+--------------------------------+
|            Header              |
+--------------------------------+
|           Parameter            |
+--------------------------------+
|             Data               |
+--------------------------------+
```

⟶ The **header** identifies the S7comm PDU and provides fields used to describe the message.

⟶ The **parameter section** identifies the requested service and contains the parameters required to interpret that service.

⟶ The **data section** carries service-specific data when required.

This distinction is useful when reading packet captures. The meaning of an S7comm packet is not contained in one field. The header establishes the message context, the parameter section identifies what the client is asking the PLC to do, and the data section carries the associated payload where applicable.

S7comm also distinguishes between different PDU types, including requests represented as **Jobs** and responses represented as **Ack** or **Ack-Data** PDUs. The result is a request/response model in which the same transport connection can carry multiple classes of S7 communication.

---

# 6. Communication Establishment

A TCP connection to port 102 does not by itself represent a complete S7 communication session.

The communication path progresses through several layers:

```text
TCP connection
      ↓
TPKT framing
      ↓
COTP connection
      ↓
S7 communication setup
      ↓
S7 services
```

After the COTP connection is established, S7comm can exchange communication setup information before ordinary application services are used. One important part of this process is **PDU negotiation**. The communicating endpoints establish parameters describing the S7 communication channel, including the maximum PDU size that can be used for subsequent exchanges. This matters because the size of an S7comm request or response is not simply determined by the underlying TCP connection. The S7 communication context establishes constraints that the application messages must respect.

---

# 7. S7comm Communication Services

S7comm provides several classes of services rather than one generic request format.

At a high level, the protocol can be viewed as exposing services for:

```text
S7comm
   │
   ├── Communication setup
   │
   ├── Variable access
   │      ├── Read
   │      └── Write
   │
   ├── UserData
   │      └── System / diagnostic services
   │
   └── Control / management services
```

The variable services provide access to data represented by the PLC memory model.

⟶ UserData provides a separate mechanism for services such as system information and diagnostics.

⟶ Control and management functions operate at a different level because they can affect the behavior or state of the controller rather than simply retrieving application data.

The same S7comm transport connection can therefore carry requests with very different consequences.

---

# 8. The PLC Memory Model

S7comm addresses data according to the logical memory model of the PLC.

A simplified representation is:

```text
PLC Memory
   │
   ├── Inputs
   ├── Outputs
   ├── Merkers / Flags
   └── Data Blocks
```

The exact memory organization varies between Siemens controller families, but these areas provide the basic vocabulary required to understand traditional S7 variable access.

A variable reference generally identifies an area together with an offset into that area. Data Blocks introduce an additional DB number because the target is not simply a global byte address.

The important difference is between, **PLC memory**:  the logical location where the process or application data exists, and **S7comm addressing**: the representation used by the protocol to identify that location.

S7comm therefore does not simply request "byte 100." It describes what memory area is being accessed and where within that area the requested data resides.

---

# 9. Variable Addressing

S7 variable access can target different data areas and data types.

A simplified address can be understood as:

```text
Memory Area
     │
     ├── DB Number
     │      │
     │      └── where applicable
     │
     └── Address
            │
            ├── Byte offset
            └── Bit position
```

This structure allows S7comm to represent both byte-oriented and bit-level access.

For example, a Data Block reference conceptually identifies:

```text
DB
 │
 └── Offset
       │
       └── Bit
```

The protocol also carries information describing the requested transport or data size.

This becomes important when interpreting a `ReadVar` or `WriteVar` request because the address alone does not completely describe the operation. The request also needs to describe how the referenced data should be interpreted and transferred.

---

# 10. Read and Write Variable Services

The traditional S7comm variable-access model includes services for reading and writing PLC variables.

A simplified interaction is:

```text
Client                         PLC
  │                             │
  │──── ReadVar ───────────────►│
  │                             │
  │◄─── Read response ───────── │
  │                             │
```

For a write:

```text
Client                         PLC
  │                             │
  │──── WriteVar ──────────────►│
  │                             │
  │◄─── Write response ──────── │
  │                             │
```

A variable request contains enough information for the PLC to identify the target and process the requested operation. A response then provides a return status together with the requested data or the result of the operation. This model is one of the central characteristics of classic S7comm because it connects the network protocol directly to the PLC's internal data model.

---

# 11. UserData and System Information

Not every S7comm operation is a direct memory read or write. S7comm also provides **UserData** services for functions that require additional protocol-specific structures.

One important category is **System Status List (SZL)** access.

SZL information provides structured information about the controller and its modules. Depending on the controller and requested SZL, this can include identification, hardware, firmware, and diagnostic information.

Conceptually:

```text
S7comm
   │
   └── UserData
          │
          └── SZL
               │
               ├── Identification
               ├── Hardware information
               ├── Firmware information
               └── Diagnostics
```

SZL should therefore be understood as part of the PLC's system-information model rather than as another form of ordinary process-memory access. The information returned is also highly dependent on the controller family and the specific SZL being requested. The protocol provides the mechanism; the actual information exposed belongs to the target implementation.

---

# 12. CPU Operational State

A PLC is more than a collection of memory locations. The CPU also has an operational state that determines how the controller executes its application program.

At a simplified level:

```text
CPU
 │
 ├── RUN
 │
 └── STOP
```

Memory services and CPU control services therefore represent different classes of interaction.

A `ReadVar` request may retrieve application data without changing the execution state of the controller. A control operation affecting CPU state is fundamentally different because it can alter whether the PLC is executing its program. This is important when considering the security consequences of S7comm services. Access to data and access to controller operations are separate capabilities even when they are carried through the same protocol.

---

# 13. Communication Context and Access Control

The ability to establish an S7comm connection does not necessarily imply unrestricted access to every PLC function.

Actual behavior depends on factors including:

* controller generation;
* firmware version;
* configured protection settings;
* enabled communication functions;
* connection type;
* engineering configuration;
* and the capabilities implemented by the particular device.

This is particularly important when comparing classic S7 controllers with newer Siemens platforms. The protocol defines communication mechanisms, while the controller determines which mechanisms are available and under what conditions. Consequently, an S7comm packet should not automatically be interpreted as proof that the corresponding operation will succeed on every Siemens PLC.

---

# 14. Classic S7comm Security Model

Classic S7comm emerged from an industrial communication environment in which protection was often provided primarily by the surrounding automation network and controller configuration rather than by modern end-to-end cryptographic communication.

This creates an important security boundary:

```text
Network Access
      │
      ▼
 S7 Communication
      │
      ▼
 PLC Services
```

The security significance of that boundary depends heavily on the controller generation and configuration.

Siemens documentation for newer controllers describes additional protection mechanisms including access protection, restrictions on communication functions, certificate-based security, and TLS-based secure communication. Siemens also documents the ability to disable or restrict functions such as PUT/GET on supported newer controllers.

Classic S7comm should therefore not be treated as representative of every modern Siemens communication configuration. The relevant security question is always tied to the specific controller, firmware, enabled services, and protection configuration under examination.

The research consequently treats the legacy protocol as a distinct communication model rather than generalizing its characteristics across the entire SIMATIC product line.

---

# 15. S7comm and Modern Siemens Communication

Siemens' newer controller families introduced additional security mechanisms over time.

For S7-1200 and S7-1500 platforms, Siemens documents secure communication capabilities involving confidentiality, integrity, and endpoint authentication, with TLS used for several modern communication paths. Secure PG/HMI communication was subsequently introduced using standardized security mechanisms and TLS.

This creates an important architectural difference:

```text
Classic S7 communication
        │
        ▼
Legacy S7comm model
        │
        ▼
ISO-on-TCP / traditional services


Modern protected communication
        │
        ▼
Additional authentication /
integrity / confidentiality
        │
        ▼
Controller-dependent mechanisms
```

The term **S7comm-Plus** is commonly used in tooling and research to describe communication associated with newer S7-1200 and S7-1500 controllers, but the modern Siemens security architecture is broader than simply assigning a new name to classic S7comm.

For that reason, the modern comparison should be treated as a separate communication and security context rather than as a direct extension of every classic S7comm behavior.

---

# Security Characteristics

S7comm is a PLC-oriented application protocol operating within the Siemens automation ecosystem.

The architectural characteristics established here are:

* **Classic S7comm operates above ISO-on-TCP**, with TPKT and COTP providing the transport layers between S7comm and TCP.
* **TCP/102 is the conventional RFC 1006 communication endpoint** used by Siemens systems for this communication path.
* **S7comm uses structured PDUs** consisting of a protocol header, parameters, and, where required, a data section.
* **Communication establishment precedes normal application services**, including S7-specific communication setup and PDU parameter negotiation.
* **Variable services provide access to the PLC's logical memory model**, including areas such as Inputs, Outputs, Merkers, and Data Blocks.
* **Variable addressing combines memory-area information with an address and data representation**, allowing byte- and bit-level access.
* **UserData provides a separate service family for functions such as system information and diagnostics**, including SZL access.
* **CPU state represents a separate control dimension from ordinary memory access**, making controller operations distinct from reading or writing process data.
* **Protocol behavior is controller-dependent.** PLC generation, firmware, configuration, protection settings, and enabled services all affect what a particular endpoint will accept.
* **Modern Siemens controllers provide additional security mechanisms** that are not representative of the classic S7comm model, including access protection and, on supported platforms and configurations, certificate- and TLS-based secure communication.

This primer establishes the architectural vocabulary for the S7comm research. The following investigation examines how these concepts are represented on the wire and how an actual implementation responds to them.
