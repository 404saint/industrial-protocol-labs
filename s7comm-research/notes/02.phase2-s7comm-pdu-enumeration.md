# Phase 2: S7comm PDU Negotiation & Memory Read Enumeration

* **Target Server:** `127.0.0.1:102` (`Snap7 1.4.2 / Native C++ Server`)
* **Protocol Layer:** S7comm over ISO-on-TCP
* **Objective:** Establish the S7comm communication state, identify PDU negotiation parameters, and enumerate PLC memory through passive `ReadVar` requests without modifying process data.

---

## Executive Summary

Phase 2 moved from the transport/session layer into the S7comm application protocol.

Following successful TCP and COTP establishment, the client exchanged a S7comm communication-setup PDU with the target and negotiated a maximum S7 PDU size of `480` bytes. Both calling and called parallel-job limits were reported as `1`.

The research harness then issued a `ReadVar` request targeting 16 bytes beginning at byte offset `0` of `DB3`. The request used the S7-Any variable specification and explicitly encoded the target data block, memory area, byte offset, and requested length.

The target returned an `Ack-Data` response with return code `0xFF`, indicating successful execution, and returned the requested 16 bytes. The response represented the payload using the bit-counted transport-size encoding, reporting `128` bits on the wire for the 16-byte result.

The exchange establishes the basic S7comm application workflow used by subsequent phases:

```text
COTP Session
     │
     ▼
Setup Communication
     │
     ▼
PDU Size Negotiated
     │
     ▼
ReadVar Request
     │
     ▼
Variable Specification
     │
     ▼
PLC Memory Read
     │
     ▼
Ack-Data Response
```

No process data was modified during this phase.

---

# 1. S7comm PDU Structure

Once the COTP session from Phase 1 is established, S7comm messages are carried inside the resulting ISO-on-TCP connection.

The S7comm PDU can be viewed conceptually as:

```text
+------------------------------------------------+
| S7comm Header                                  |
| ROSCTR | PDU Reference | Parameter/Data Length |
+------------------------------------------------+
| Parameter                                      |
| Service-specific request or response fields    |
+------------------------------------------------+
| Data                                           |
| Optional service payload                       |
+------------------------------------------------+
```

The header identifies the S7comm communication direction and provides the lengths and reference information required to interpret the remainder of the PDU.

For this phase, the primary ROSCTR value observed was:

```text
0x03 → Ack-Data
```

Ack-Data PDUs are used when a response contains application-level information in addition to acknowledging a request. The exact contents of the Parameter and Data sections depend on the S7comm service being executed.

---

# 2. Communication Setup & PDU Negotiation

The first S7comm exchange after COTP establishment was the communication-setup sequence.

The target reported:

| Parameter                 | Observed Value         |
| ------------------------- | ---------------------- |
| PDU Type (ROSCTR)         | `0x03` — Ack-Data      |
| Max Calling Parallel Jobs | `1`                    |
| Max Called Parallel Jobs  | `1`                    |
| Negotiated PDU Size       | `480` bytes (`0x01E0`) |

The negotiated PDU size establishes the maximum S7comm PDU length used by the communication relationship. This value is different from the COTP TPDU size observed during Phase 1.

The resulting protocol state is:

```text
TCP
 │
 ▼
TPKT
 │
 ▼
COTP Session
 │
 ▼
S7comm Setup Communication
 │
 ├── Parallel Jobs: 1 / 1
 │
 └── PDU Size: 480 bytes
 │
 ▼
S7comm Services Available
```

The setup exchange therefore establishes the application-level communication parameters required before variable services are issued.

---

# 3. Parallel Job Limits

The target reported:

```text
Max Calling Parallel Jobs: 1
Max Called Parallel Jobs:  1
```

These parameters describe the number of outstanding S7comm jobs supported in the negotiated communication relationship.

For the laboratory target, the resulting baseline is effectively:

```text
Client ── Job ──► Server
Client ◄─ Response ─ Server
```

rather than a session designed around multiple simultaneously outstanding requests. This provides an important baseline for later session-state and concurrency testing. No saturation behavior was tested during Phase 2.

---

# 4. ReadVar Service

After communication setup completed, the research harness issued S7comm `ReadVar` using function: `0x04`

The request targeted:

```text
DB3
Offset: 0
Length: 16 bytes
```

The operation was read-only and did not modify the target's process data.

The service can be represented as:

```text
Client
  │
  │ ReadVar
  │ DB3 / Offset 0 / 16 bytes
  ▼
Snap7 Target
  │
  │ Memory Lookup
  ▼
DB3
  │
  │ 16-byte result
  ▼
Ack-Data Response
```

This provides the first application-level demonstration of direct PLC memory access in the research.

---

# 5. S7-Any Variable Specification

The ReadVar request used the S7-Any addressing format.

The decoded item structure was:

| Field                        | Raw        | Meaning                     |
| ---------------------------- | ---------- | --------------------------- |
| Variable Specification       | `0x12`     | S7 addressing item follows  |
| Address Specification Length | `0x0A`     | 10 bytes of addressing data |
| Syntax ID                    | `0x10`     | S7-Any                      |
| Transport Size               | `0x02`     | Byte-oriented request       |
| Requested Count              | `16`       | 16 bytes                    |
| DB Number                    | `3`        | Target DB3                  |
| Area ID                      | `0x84`     | Data Block                  |
| Byte/Bit Address             | `0x000000` | Byte 0, bit 0               |

The S7-Any pointer therefore identifies the target using several independent fields:

```text
+--------------------------------------------------+
| Syntax ID                                        |
+--------------------------------------------------+
| Transport Size                                   |
+--------------------------------------------------+
| Element Count                                    |
+--------------------------------------------------+
| DB Number                                        |
+--------------------------------------------------+
| Area ID                                          |
+--------------------------------------------------+
| Byte / Bit Address                               |
+--------------------------------------------------+
```

This structure is important because S7 memory access is not represented by a single flat address. The request identifies both the memory area and the location within that area.

---

# 6. PLC Memory Addressing

The Phase 2 request targeted the Data Block area:

```text
Area ID: 0x84
DB Number: 3
```

The requested address was:

```text
DB3
Byte: 0
Bit: 0
Length: 16 bytes
```

The resulting logical range was therefore:

```text
DB3
├── Byte 0
├── Byte 1
├── Byte 2
├── ...
└── Byte 15
```

The target returned:

```text
01 01 01 01 01 01 01 01
01 01 01 01 01 01 01 01
```

All sixteen requested bytes contained the value `0x01`.

The result confirms that the research harness successfully translated the logical DB address into an S7-Any request and that the Snap7 target returned the corresponding data.

---

# 7. ReadVar Response

The target returned an S7comm Ack-Data response containing:

| Field             | Value                   |
| ----------------- | ----------------------- |
| PDU Type (ROSCTR) | `0x03` — Ack-Data       |
| Return Code       | `0xFF` — Success        |
| Transport Size    | `0x04` — Bit-counted    |
| Data Length       | `16` bytes / `128` bits |
| Source            | DB3, offset 0           |

The return code: `0xFF` indicates that the requested item was successfully processed by the target. The response's transport-size representation reported the returned data length in bits:

```text
128 bits
     │
     ▼
16 bytes
```

The returned length therefore corresponds exactly to the 16-byte ReadVar request.

# 9. Protocol State & Service Separation

Phase 2 establishes an important separation between communication setup and application services.

The target first negotiated the communication parameters:

```text
Setup Communication
        │
        ▼
PDU Size / Parallel Jobs
```

Only after that exchange did the client issue: `ReadVar`.

The resulting sequence is:

```text
COTP CC
   │
   ▼
Setup Communication
   │
   ▼
Negotiated S7 PDU Parameters
   │
   ▼
ReadVar
   │
   ▼
Ack-Data
```

This separation will become important when later phases examine write operations and CPU control. A successful COTP connection alone does not represent a completed S7comm application exchange.

# 10. Detection & Traffic Analysis

The Phase 2 PCAP and `tcpdump` capture were cross-validated against the terminal execution.

The packet-level evidence consistently mapped to the decoded application behavior:

* The communication-setup exchange reported a negotiated PDU size of `480` bytes (`0x01E0`).
* The ReadVar request contained an S7-Any specification targeting `DB3`.
* The requested element count was `16`.
* The area identifier was `0x84`, identifying the Data Block area.
* The starting address was byte offset `0`.
* The response returned `0xFF`, indicating successful processing.
* The response reported `0x0080` bits, corresponding to the requested 16-byte result.

The PCAP therefore independently confirms the same protocol state and addressing semantics exposed by the research harness. The packet capture is retained as the primary wire-level artifact, while the decoded fields above provide the concise research record.

# 11. Security Characteristics

## 11.1 Direct Memory Read Capability

The tested S7comm session permitted the client to issue a `ReadVar` request against a Data Block and retrieve its contents.

The observed sequence was:

```text
COTP Session
     │
     ▼
S7 Communication Setup
     │
     ▼
ReadVar DB3
     │
     ▼
0xFF Success
     │
     ▼
16 Bytes Returned
```

The exchange demonstrates that an established S7comm communication relationship can expose controller memory through explicit variable addressing. The security significance depends on controller configuration, protection settings, connection type, and implementation.

---

## 11.2 Structured Memory Addressing

S7-Any addressing exposes several pieces of information directly within the request:

```text
Memory Area
DB Number
Offset
Transport Size
Element Count
```

This makes ReadVar traffic suitable for passive protocol analysis and memory-access profiling. A monitoring system can distinguish different classes of S7 memory access without interpreting the returned application values.

---

## 11.3 PDU Negotiation as Session Metadata

The communication-setup exchange exposes:

```text
Parallel Job Limits
Negotiated PDU Size
```

These values provide useful session-level characteristics that can be associated with a particular S7 communication relationship. Unexpected changes in negotiated parameters may therefore provide useful context during traffic analysis, although this phase does not establish detection thresholds for legitimate versus anomalous values.

---

# Hardening Considerations

The ability to retrieve PLC memory through S7comm should be evaluated against the controller's intended communication model.

Relevant controls include:

* Restricting TCP/102 access to authorized engineering, HMI, and supervisory systems.
* Applying controller access-protection settings appropriate to the deployment.
* Restricting unnecessary S7 communication paths through network segmentation and firewall policy.
* Monitoring ReadVar activity from unexpected hosts.
* Profiling normal memory areas accessed by legitimate engineering and supervisory applications.
* Reviewing whether exposed Data Blocks contain configuration, process, or other operationally sensitive information.
* Evaluating modern Siemens communication protections where supported instead of treating legacy S7comm access controls as the complete security boundary.

Read-only access should also be treated as an information-exposure concern. The absence of a write operation does not make unrestricted controller memory enumeration benign.
