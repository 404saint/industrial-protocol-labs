# Phase 4: System Status List (SZL) & CPU Diagnostics Enumeration

* **Target Server:** Snap7 1.4.2 Native C++ Server
* **Protocol Layer:** S7comm UserData / SZL Diagnostic Services
* **Target Endpoint:** `127.0.0.1:102`
* **Objective:** Enumerate diagnostic and hardware-identification data exposed through S7comm System Status List (SZL) requests and determine the response boundary of the target implementation.

---

## Executive Summary

Phase 4 moves from process-data interaction into the diagnostic surface of S7comm.

Where Phase 3 demonstrated active memory modification through `WriteVar`, this phase examines the information exposed through S7comm UserData services. System Status Lists (SZLs) provide structured diagnostic information associated with the PLC, including identification and system-level metadata.

Two SZL identifiers were queried against the Snap7 target.

The first request targeted **SZL ID `0x0011`**, which the lab implementation exposes as module identification data. The request completed successfully and returned structured metadata including the identifier `6ES7 315-2EH14-0AB0` and the string `Boot Loader`.

The second request targeted **SZL ID `0x0111`**, selected to test CPU hardware and firmware-version information. The target returned `0x0A`, reported as **Object Does Not Exist**, and the server classified the requested SZL as unavailable.

Both exchanges were independently verified against the packet captures. The results demonstrate that diagnostic UserData services can expose meaningful device metadata without an authentication step in this lab configuration, while also showing that the available SZL surface depends on the target implementation.

---

# 1. Diagnostic Surface & UserData

S7comm provides more than variable access to PLC process data. Diagnostic operations are carried through the **UserData** service class, identified in the protocol by ROSCTR `0x07`. These requests use a different service path from the `ReadVar` and `WriteVar` operations examined in the previous phases.

The general relationship is:

```text
TCP / 102
    │
    └── ISO-on-TCP
          │
          └── COTP
                │
                └── S7comm PDU
                      │
                      └── UserData
                            │
                            └── SZL Request
                                  │
                                  ├── SZL ID
                                  └── Index
```

For this phase, each diagnostic query was executed in a fresh S7comm session. This keeps the individual observations isolated and makes the packet sequence easier to correlate with the corresponding server-side result.

---

# 2. System Status Lists

System Status Lists provide structured diagnostic information that can be requested from an S7 system. An SZL request identifies the information being requested through an **SZL ID** and an associated **index**.

For the lab, the request structure can be represented as:

| Field         | Function                                                 |
| ------------- | -------------------------------------------------------- |
| ROSCTR        | Identifies the PDU as UserData                           |
| SZL ID        | Selects the requested diagnostic information             |
| Index         | Selects the requested portion of the SZL                 |
| Response Code | Indicates whether the request was processed successfully |
| SZL Data      | Returned diagnostic or identification records            |

This makes SZL enumeration useful from a security-research perspective because the operation is primarily informational. Unlike `WriteVar`, the objective is not to alter process state, but to determine what information the communication endpoint is willing to disclose.

---

# 3. SZL `0x0011` Module Identification

The first request targeted:

```text
SZL ID: 0x0011
Index:  0x0000
ROSCTR: 0x07 UserData
Target: 127.0.0.1:102
```

The Snap7 server accepted the request:

```text
Read SZL request, ID:0x0011 INDEX:0x0000 --> OK
```

The client received:

```text
PDU Type: 0x07 -- UserData
Return Code: 0xFF -- Success
```

The returned SZL payload contained several identifiable strings. The client extracted:

```text
6ES7 315-2EH14-0AB0
6ES7 315-2EH14-0AB0
Boot Loader
```

The first two values represent the same device-identification string appearing in separate returned records.

The important observation is that the diagnostic request produced structured identification information rather than simply acknowledging that the SZL existed.

### Returned Identification Data

| Observed value        | Interpretation in lab                             |
| --------------------- | ------------------------------------------------- |
| `6ES7 315-2EH14-0AB0` | Module identification / order-number-style string |
| `6ES7 315-2EH14-0AB0` | Repeated identification record                    |
| `Boot Loader`         | Returned system/module string                     |

The values above describe the contents exposed by the Snap7 target. They should not be interpreted as evidence that a physical Siemens PLC with this exact hardware configuration was queried. The result establishes the diagnostic information available from this specific implementation.

---

# 4. Diagnostic Metadata as an Enumeration Surface

The information returned by an identification-oriented SZL can be useful before any process-data interaction takes place. A diagnostic query can potentially provide information that helps characterize a target:

```text
S7comm Endpoint
       │
       ▼
   UserData
       │
       ▼
    SZL Query
       │
       ▼
Module Identification
       │
       ├── Order-number-style identifier
       ├── Module/system strings
       └── Additional implementation-defined records
```

This creates a different reconnaissance surface from the memory enumeration performed in Phase 2. Phase 2 established what could be addressed and read from the PLC memory model. Phase 4 establishes that the protocol also exposes a diagnostic namespace capable of describing the target itself.

In an operational environment, such metadata could contribute to asset identification and fingerprinting. The security significance depends on the information exposed, the accessibility of the S7comm endpoint, and the controls surrounding engineering and diagnostic access.

# 5. SZL `0x0111` Boundary Test

The second query targeted:

```text
SZL ID: 0x0111
Index:  0x0000
ROSCTR: 0x07 UserData
```

The client identified this request as a CPU hardware / firmware-version query. Unlike the previous request, the Snap7 target did not provide a successful SZL response.

The server reported:

```text
Read SZL request, ID:0x0111 INDEX:0x0000 --> NOT AVAILABLE
```

The client received:

```text
Return Code: 0x0A -- Object Does Not Exist
```

The corresponding packet capture showed an S7comm UserData response containing the error information. The capture therefore confirms that the request reached the target and that the negative result was generated as part of the S7comm exchange rather than being caused by a transport failure.

This establishes an implementation boundary:

```text
SZL 0x0011
      │
      ▼
Supported
      │
      └── Structured identification returned

SZL 0x0111
      │
      ▼
Unavailable in target implementation
      │
      └── Return code 0x0A
```

The result should be scoped specifically to the Snap7 target used in this research. It does not establish that the corresponding diagnostic information is unavailable from real Siemens PLCs.

---

# 6. Response-Code Handling

The two requests also provide a useful example of how S7comm communicates service-level outcomes.

The successful request returned:

```text
0xFF -- Success
```

The unsupported/unavailable request returned:

```text
0x0A -- Object Does Not Exist
```

The difference is important when building protocol-analysis tooling.

A connection that completes successfully does not imply that the requested S7 service succeeded. The transport and S7comm session can remain functional while an individual UserData operation is rejected.

For passive analysis, the relevant sequence is therefore:

```text
TCP Session
    │
    ▼
COTP Session
    │
    ▼
S7comm Communication Setup
    │
    ▼
UserData Request
    │
    ├── Success ───────► Diagnostic Data
    │
    └── Error ─────────► S7comm Return Code
```

Detection logic that only tracks TCP/102 connectivity would miss this difference.

---

# 7. Session Isolation

Each SZL query was executed through a separate client session.

The resulting test structure was:

```text
Session 1
   │
   ├── TCP / COTP establishment
   ├── Setup Communication
   ├── SZL 0x0011
   └── Disconnect

Session 2
   │
   ├── TCP / COTP establishment
   ├── Setup Communication
   ├── SZL 0x0111
   └── Disconnect
```

This prevents the outcome of one diagnostic query from influencing the state of the following test. It also provides a clean packet-level correlation between each request and its corresponding response.

# 8. Wire-Level Validation

The results were independently checked against the captured traffic.


## 1. SZL `0x0011`


The first sequence consisted of frames 8–11.

The exchange contained:

1. A fresh connection establishment.
2. S7comm communication setup and PDU negotiation.
3. A UserData request for SZL `0x0011`, index `0x0000`.
4. A successful UserData response.

The successful response corresponds to the server-side observation:

```text
Read SZL request, ID:0x0011 INDEX:0x0000 --> OK
```

The returned payload was then decoded by the client to extract the module-identification strings.

## 2. SZL `0x0111`

The second sequence consisted of frames 22–25.

The exchange contained:

1. A new connection establishment.
2. S7comm communication setup and PDU negotiation.
3. A UserData request for SZL `0x0111`, index `0x0000`.
4. A UserData error response.

The response contained error information corresponding to the server-side result:

```text
Read SZL request, ID:0x0111 INDEX:0x0000 --> NOT AVAILABLE
```

The packet capture therefore validates both the successful and unsuccessful diagnostic paths. The PCAPs remain the wire-level evidence for the experiment; the research note records the decoded observations rather than reproducing raw packet payloads.

# 9. Security Characteristics

The phase demonstrates three relevant characteristics of the diagnostic surface.

## 9.1 Diagnostic Information Exposure

The Snap7 target returned structured module-identification information through an S7comm UserData request.

The successful `0x0011` query exposed:

```text
6ES7 315-2EH14-0AB0
Boot Loader
```

This demonstrates that diagnostic services can provide useful asset-identification information beyond normal process-data access.

## 9.2 Diagnostic Access Boundary

The `0x0111` request was accepted at the protocol level but rejected at the service level.

The target returned:

```text
0x0A -- Object Does Not Exist
```

This demonstrates that the diagnostic namespace is implementation-dependent. An S7comm client cannot assume that every SZL identifier is available simply because the UserData service itself is supported.

## 9.3 Authentication Boundary


Both queries were performed without an authentication step in the laboratory configuration. The successful result therefore demonstrates **unauthenticated diagnostic information access in this Snap7 lab configuration**.

This should remain scoped to the tested implementation. It is not sufficient evidence to characterize authentication behavior across Siemens PLC families or firmware versions.

---

# 10. Defensive Considerations

The primary defensive concern is controlling who can reach the S7comm diagnostic surface. Where S7comm endpoints are exposed beyond the required engineering or control environment, diagnostic enumeration can provide useful information to an unauthorized client even when no process-data modification occurs.

Relevant defensive controls include:

* Restrict TCP/102 access to authorized engineering and control hosts.
* Segment PLC networks from general-purpose user and enterprise networks.
* Monitor unexpected S7comm UserData traffic.
* Baseline normal diagnostic-query behavior for engineering workstations.
* Alert on repeated or broad SZL enumeration from hosts that do not normally perform PLC diagnostics.
* Treat returned module and firmware metadata as sensitive asset information.
* Use vendor-supported access-control and protection mechanisms appropriate to the PLC family and deployment.

For monitoring, an IDS or protocol-analysis tool should distinguish between ordinary S7comm session establishment and diagnostic UserData operations. A TCP connection to port 102 alone does not identify the actual operation being performed.
