# Phase 5: State Manipulation & Protocol Anomaly Testing

* **Target Server:** Snap7 1.4.2 Native C++ Server
* **Protocol Layer:** S7comm Session State / Variable Services / TPKT
* **Target Endpoint:** `127.0.0.1:102`
* **Objective:** Test whether the target enforces expected S7comm session initialization before processing variable services, determine whether state-dependent operations can be executed before communication setup, and evaluate basic resilience against incomplete oversized TPKT frames.

---

## Executive Summary

Phase 5 examines the relationship between S7comm session state and service execution.

Earlier phases established the normal communication sequence: TCP/102 establishment, COTP session negotiation, S7comm Setup Communication, and subsequent application services. This phase deliberately breaks that sequence.

The first test established a COTP session and immediately issued a `ReadVar` request without performing Setup Communication. The Snap7 target processed the request and returned live DB3 data with a successful S7comm response.

Packet capture confirmed the ordering. The `ReadVar` transaction occurred before the first Setup Communication exchange in the tested session. This demonstrates that the Snap7 implementation does not enforce the expected communication-setup state before processing this read operation.

A second test repeated the same approach with `WriteVar`. The unsolicited write reached the S7comm service, but the target returned `0x05` for the write item and a subsequent negotiated read confirmed that DB3 remained unchanged. The experiment therefore does **not** establish a pre-handshake write primitive. Instead, it demonstrates that reaching the WriteVar service before Setup Communication is possible while the attempted operation itself was rejected.

The final test opened 50 fully negotiated sessions and sent intentionally incomplete oversized TPKT frames, holding each socket open for 15 seconds without transmitting the bytes promised by the TPKT length field. All 50 sockets remained open during the test window, and the server remained responsive after release. The test therefore demonstrated sustained resource consumption but did not produce a server crash or persistent denial of service under the tested conditions.

---

# 1. Expected Communication State

The normal S7comm session established during the previous phases follows a predictable progression:

```text
TCP Connection
      │
      ▼
COTP CR / CC
      │
      ▼
Setup Communication
      │
      ├── PDU negotiation
      ├── Parallel job parameters
      └── S7 communication context
      │
      ▼
Application Services
      │
      ├── ReadVar
      ├── WriteVar
      ├── UserData
      └── Other S7 services
```

The Setup Communication exchange establishes the S7comm communication parameters used by subsequent services. Phase 5 intentionally removes that step.

The objective is not simply to send malformed bytes. The test asks:

> Does the target require the S7comm communication setup to occur before accepting application-level variable services?

This is important because a parser can accept a syntactically valid S7comm PDU while still failing to enforce the protocol state in which that PDU is expected.

---

# 2. Pre-Setup ReadVar

The first test established a COTP session and immediately transmitted a `ReadVar` request.

The client explicitly skipped Setup Communication:

```text
COTP session established.
Skipping Setup Communication.
Reading DB3.0
```

The target returned a valid S7comm response.

The decoded response contained:

```text
ROSCTR: 0x03
Item return code: 0xFF -- Success
```

The client therefore received live data from DB3 without performing the normal Setup Communication exchange first.

The target-side logs independently recorded the read operation:

```text
Read request, Area : DB3, Start : 0, Size : 1 --> OK
```

This establishes that the request was processed as a real variable operation rather than merely being accepted at the transport layer.

---

# 3. State-Machine Bypass

The important observation is the ordering of the S7comm transactions.

The packet capture shows:

```text
Frames 8–9
    │
    └── ReadVar request / response
          │
          ▼
      No Setup Communication

Frames 32–33
    │
    └── Setup Communication
```

The first Setup Communication exchange therefore appears only after the earlier ReadVar operation has already completed.

The tested sequence becomes:

```text
COTP CR / CC
      │
      ▼
ReadVar
      │
      ▼
Successful response
      │
      ▼
Setup Communication
```

rather than:

```text
COTP CR / CC
      │
      ▼
Setup Communication
      │
      ▼
ReadVar
```

Within the Snap7 target, this demonstrates incomplete enforcement of the expected S7comm application state before servicing `ReadVar`. The result is particularly significant because the request was not rejected as an invalid state transition. It was processed normally and returned the requested DB3 value.

---

# 4. Why the Read Result Matters

The successful read distinguishes this behavior from a transport-level anomaly. The server did not merely keep the TCP connection open or acknowledge the incoming bytes.

It:

1. Parsed the S7comm request.
2. Identified the requested DB area.
3. Performed the variable read.
4. Returned an S7comm Ack-Data response.
5. Reported a successful item return code.

The operation therefore crossed from session establishment into application-level data access despite the absence of Setup Communication. This makes the observation a **state-enforcement issue in the tested implementation**, rather than simply a permissive TCP parser.

---

# 5. Pre-Setup WriteVar

The second test applied the same state-machine bypass to a write operation.

The client established COTP and immediately sent:

```text
WriteVar
Target: DB3.0
Payload: 0x41
Setup Communication: skipped
```

The target responded with an S7comm Ack-Data PDU, but the write item returned:

```text
0x05 -- Invalid address
```

A separate, fully negotiated session then read DB3.0.

The value returned was:

```text
0x02
```

This was different from the attempted write value `0x41`. The server-side logs also did not record a successful write for this test.

## Result

The pre-Setup WriteVar test therefore **did not demonstrate a successful process-data modification**.

What it demonstrated was narrower:

```text
COTP CR / CC
      │
      ▼
Unsolicited WriteVar
      │
      ▼
S7comm service reached
      │
      ▼
Return code 0x05
      │
      ▼
Write not applied
```

The Snap7 implementation permits the WriteVar request to reach the application service before Setup Communication, but the particular write was rejected. The successful pre-Setup ReadVar and failed pre-Setup WriteVar therefore provide two separate observations rather than one generalized bypass claim.

---

# 6. Read vs. Write State Enforcement

The paired tests reveal an important asymmetry.

| Operation            | Setup Communication performed? | Result                      |
| -------------------- | -----------------------------: | --------------------------- |
| ReadVar              |                             No | `0xFF` Success              |
| WriteVar             |                             No | `0x05` Invalid address      |
| Verification ReadVar |                            Yes | Existing DB3 value returned |

The implementation therefore cannot be described simply as “accepting all S7comm services before Setup Communication.”

The accurate finding is:

> The tested Snap7 implementation processed a ReadVar operation before Setup Communication, while the corresponding pre-Setup WriteVar attempt did not modify the target and returned an invalid-address error.

This is the behavior that should be reproduced and evaluated.

---

# 7. Wire-Level Validation

The packet capture independently validates the state-machine behavior. The relevant sequence contains the application operation before the first Setup Communication block.

## ReadVar

Frames 8–9 show:

```text
COTP session
      │
      ▼
ReadVar request
      │
      ▼
Ack-Data response
```

No Setup Communication exchange occurs before this transaction.

## WriteVar

Frames 20–21 show:

```text
COTP session
      │
      ▼
WriteVar request
      │
      ▼
Ack-Data response
```

The returned item code was `0x05`, and the subsequent verification read confirmed that the attempted value was not written.

## Later Setup Communication

Frames 32–33 contain the Setup Communication exchange. This provides direct packet-level evidence that communication setup occurred later than the earlier application operations in the tested sequence.

---

# 8. Held-Open Oversized TPKT Frames

The second class of anomaly examined resource handling rather than S7comm service state. The client opened **50 fully negotiated sessions** and transmitted a ReadVar request whose TPKT length field claimed more data than was actually supplied. Each connection was then held open without sending the missing bytes or closing the socket.

The test parameters were:

```text
Connections attempted:                    50
Successfully held open:                   50
Failed before hold:                        0
Hold duration:                           15 s
```

The target therefore maintained all 50 partial-frame connections throughout the test window. This creates a deliberate mismatch between the advertised TPKT message length and the bytes currently available to the receiver:

```text
TPKT Length Field
        │
        ▼
"More bytes are coming"
        │
        ▼
Actual TCP stream
        │
        └── Missing promised bytes
```

The server must retain enough connection state to wait for completion or termination.

---

# 9. Resource-Handling Result

The server remained responsive after all 50 held-open connections were released.

The client reported:

```text
Server liveness immediately after all sockets released: UP
```

The server logs show the corresponding burst of client creation followed by peer disconnect events approximately 15 seconds later. This result does **not** demonstrate a denial of service. It demonstrates that the target accepted and maintained a relatively large number of incomplete TPKT exchanges for the duration of the test without crashing or becoming permanently unavailable.

The observation is therefore better characterized as a **resource-consumption and timeout-handling test**.

A production assessment would require additional measurements such as:

* Maximum sustainable incomplete connections.
* Thread and file-descriptor consumption.
* Memory growth.
* CPU utilization.
* Behavior at progressively larger connection counts.
* Behavior with different hold durations.
* Recovery time after connection release.
* Interaction with legitimate S7comm clients during resource pressure.

Those measurements were outside the scope of this phase.

---

# 10. Implementation Boundaries

The combined tests demonstrate why protocol anomaly research should distinguish between parser acceptance, service execution, and actual state modification.

The three relevant outcomes were:

```text
Pre-Setup ReadVar
        │
        └── Parsed + executed + successful data response

Pre-Setup WriteVar
        │
        └── Parsed + service reached + rejected
                         │
                         └── No data modification demonstrated

Oversized TPKT
        │
        └── Connection retained + incomplete frame held
                         │
                         └── Server remained available
```

Each represents a different implementation behavior. Treating all three as a generic “S7comm bypass” would be overstating the evidence.

---

# 11. Security Characteristics

## 11.1 Incomplete State Enforcement

The Snap7 target processed a `ReadVar` operation before Setup Communication. This demonstrates that the tested implementation does not consistently enforce the expected session progression before application-level reads.

## 11.2 Write Protection Boundary

The corresponding pre-Setup WriteVar request did not result in a write. The target returned `0x05` and subsequent verification showed that DB3.0 remained unchanged. The experiment therefore provides no evidence of a successful pre-handshake write primitive.

## 11.3 Incomplete-Frame Resource Consumption

The target maintained 50 connections carrying incomplete oversized TPKT messages for 15 seconds. The server remained available after the test. This establishes resource retention under the tested conditions, but not a denial-of-service condition.

## 11.4 Protocol-State Visibility

The state-machine behavior is observable at the packet level. A network monitor capable of reconstructing S7comm session state can identify application requests occurring before Setup Communication and distinguish them from normal negotiated sessions.

---

# 12. Defensive Considerations

The strongest defensive control for this class of behavior is protocol-aware monitoring combined with network access restriction.

Recommended controls include:

* Restrict TCP/102 to authorized engineering and control hosts.
* Track S7comm session state rather than treating every TCP/102 connection as equivalent.
* Flag `ReadVar` or other application services appearing before Setup Communication.
* Monitor abnormal TPKT length declarations and incomplete sessions.
* Apply connection and session timeouts appropriate for the environment.
* Monitor concurrent TCP/102 session counts and unexpected connection bursts.
* Correlate incomplete-frame behavior with source hosts and existing engineering activity.
* Validate that deployed PLC implementations enforce expected communication state transitions.

For an IDS, a useful detection model is:

```text
TCP/102
  │
  ▼
COTP CR / CC
  │
  ├── Setup Communication
  │       │
  │       └── Normal application services
  │
  └── Application service before Setup
          │
          └── State anomaly
```

| Pre-Setup WriteVar       | Request reached service but returned `0x05`                      | Snap7 1.4.2 lab         |
| Write modification       | Not demonstrated                                                 | DB3 remained unchanged  |
| Setup ordering           | Setup Communication appeared after earlier application traffic   | Tested session          |

| Confirmed DoS            | Not demonstrated                                                 | Outside tested evidence |
| Wire validation          | PCAP confirmed application traffic preceding Setup Communication | Lab PCAP                |

Phase 5 demonstrates that protocol-state enforcement can be as important as individual S7comm service validation. The Snap7 target processed a live `ReadVar` request before communication setup, establishing a concrete state-machine weakness in the tested implementation. The paired WriteVar experiment showed that this behavior does not automatically extend to successful process-data modification.

The held-open oversized-TPKT test further showed that the target can maintain multiple incomplete sessions without losing liveness under the tested 50-connection, 15-second workload.

The next phase moves toward the final layer of the S7comm study: contrasting the legacy communication model with modern Siemens secure communication mechanisms and examining where cryptographic protection, access control, and protocol evolution change the security boundary.
