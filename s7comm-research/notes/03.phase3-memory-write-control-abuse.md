# Phase 3: Memory Write & CPU Control Abuse

* **Target Server:** `127.0.0.1:102` (`Snap7 1.4.2 / Native C++ Server`)
* **Protocol Layer:** S7comm Variable Services / UserData
* **Objective:** Examine direct memory modification through `WriteVar`, validate address-boundary enforcement, and construct a CPU control UserData request against the laboratory target without relying on high-level S7 libraries.

---

## Executive Summary

Phase 3 moved from read-only memory enumeration into active S7comm operations.

Using the same communication setup established in Phase 2, the research harness issued a `WriteVar` request targeting the first 16 bytes of `DB3`. The Snap7 target returned `0xFF`, indicating successful processing, and its server-side log confirmed that the requested 16-byte write was committed to memory.

No authentication exchange occurred before the write in the tested laboratory configuration. The result therefore demonstrates that the configured Snap7 communication path permitted direct memory modification from the established S7comm session.

A second `WriteVar` request targeted byte offset `65000`, well beyond the registered `1024`-byte size of `DB3`. The target rejected the operation with return code `0x05`, and the server logged the request as out of range. The daemon remained stable, demonstrating effective bounds enforcement for this test case.

The final test constructed a S7comm UserData request associated with CPU control and attempted to exercise the CPU STOP function. The Snap7 demonstration server does not implement the corresponding CPU-control functionality and provided no response before the client timeout. The packet was nevertheless successfully constructed and transmitted, establishing the wire-level foundation for later analysis against an implementation that supports the service.

The phase therefore demonstrates three distinct properties:

```text id="f3x6r1"
WriteVar
   │
   ├── Valid address ───────► Write accepted
   │
   └── Invalid address ─────► Write rejected

UserData CPU Control
   │
   └── Unsupported by target ─► No state transition observed
```

# 1. WriteVar Service

S7comm provides variable access through the `ReadVar` and `WriteVar` services.

Phase 2 established the read operation:

```text id="7cy8q2"
ReadVar = 0x04
```

Phase 3 examines the corresponding write operation:

```text id="3o4k1p"
WriteVar = 0x05
```

The basic operation is:

```text id="o8r6k3"
Client
   │
   │ WriteVar
   │ DB3 / Offset / Length / Data
   ▼
S7comm Target
   │
   ├── Address validation
   │
   ├── Memory access
   │
   └── Return Code
```

Unlike the Phase 2 ReadVar operation, the WriteVar service changes the contents of the addressed memory area when accepted. For this reason, every write test was performed against a dedicated laboratory Data Block.

---

# 2. Unauthenticated Memory Write

The first test targeted:

```text id="b5t7m9"
Area:        DB3
Byte Offset: 0
Length:      16 bytes
Payload:     16 × 0xFF
```

The client established a fresh S7comm session and negotiated:

```text id="0k9n4p"
ROSCTR: 0x03
PDU Size: 480 bytes
```

The WriteVar request then specified:

```text id="e6y4s2"
Function:     0x05
Area:         DB3
Offset:       0
Payload Size: 16 bytes
```

The target returned: `Return Code: 0xFF` indicating successful processing of the write.

The server independently recorded:

```text id="v2r8c6"
Write request, Area : DB3, Start : 0, Size : 16 --> OK
```

The resulting memory operation was:

```text id="q7m2x5"
DB3[0..15]
     │
     ▼
FF FF FF FF FF FF FF FF
FF FF FF FF FF FF FF FF
```

The PCAP analysis independently confirmed the sequence:

```text id="s9h4w1"
WriteVar Job
     │
     ▼
DB3 / Offset 0 / 16 bytes
     │
     ▼
Ack-Data
     │
     ▼
Return Code 0xFF
```

The write was therefore verified at both the protocol and target-implementation levels.

---

# 3. Write Authorization Boundary

The successful write is significant because no authentication exchange was performed between session establishment and the WriteVar operation.

The observed sequence was:

```text id="m4q8s6"
TCP/102
    │
    ▼
COTP Session
    │
    ▼
S7comm Setup Communication
    │
    ▼
WriteVar
    │
    ▼
0xFF Success
```

Within this laboratory configuration, the established S7comm session was sufficient to submit a valid memory-write request. This should be interpreted as an **implementation and configuration observation**. It does not establish that all Siemens controllers expose the same write behavior, since access protection, firmware, controller generation, connection configuration, and communication settings can affect which services are permitted.

The security boundary demonstrated here is therefore the one actually present in the tested Snap7 environment.

---

# 4. Out-of-Bounds Write

The second test examined the target's handling of an invalid memory address.

The registered size of DB3 was:

```text id="x8w3k5"
1024 bytes
```

The client attempted to write:

```text id="a6n2q9"
Offset: 65000
Length: 4 bytes
Payload: 42 42 42 42
```

The requested offset was therefore far beyond the valid DB3 range.

The server returned:

```text id="r5v7c1"
Return Code: 0x05
```

The Snap7 server independently recorded:

```text id="j3q9m2"
Write request, Area : DB3, Start : 65000, Size : 4 --> Out of range
```

The daemon remained operational after the rejected request.

The resulting behavior can be summarized as:

```text id="w6p4z8"
WriteVar
   │
   ▼
DB3 / Offset 65000 / Length 4
   │
   ▼
Address Validation
   │
   ├── Valid? ── No
   │
   ▼
Return Code 0x05
   │
   ▼
Memory unchanged
```

The test therefore confirms an effective bounds check for the specific Data Block and address examined.

---

# 5. Address Validation

The contrast between the two write operations provides a useful implementation baseline.

| Test               | Target               | Result                 |
| ------------------ | -------------------- | ---------------------- |
| Valid write        | `DB3:0`, 16 bytes    | `0xFF` Success         |
| Out-of-range write | `DB3:65000`, 4 bytes | `0x05` Invalid address |

The target therefore distinguishes between a valid memory range and an address outside the registered Data Block. This is important for later anomaly testing because malformed or deliberately invalid addresses do not necessarily imply memory corruption. A robust implementation can reject the request before performing the underlying memory operation.

The current experiment demonstrates that behavior for Snap7's DB memory model.

# 6. CPU Control Through UserData

The final test moved beyond variable services and constructed an S7comm UserData request associated with CPU control.

The request used:

```text id="c8y5r2"
ROSCTR: 0x07
Sub-function: 0x47
```

The client transmitted the request after successfully establishing the normal S7comm communication session.

The observed sequence was:

```text id="n7w4k2"
COTP Session
     │
     ▼
S7comm Setup Communication
     │
     ▼
UserData
ROSCTR 0x07
Sub-function 0x47
     │
     ▼
Snap7 Target
     │
     ▼
No Response
```

The research harness timed out waiting for a response. The target's behavior is consistent with the known limitation of the Snap7 demonstration server used in this laboratory: the relevant CPU-control functionality is not implemented.

Consequently, **no CPU STOP state transition was demonstrated during this experiment**.

---

# 7. Control-Plane Request Construction

Although the CPU state transition was not available on the target, the test established that the research harness can construct and transmit an S7comm UserData control request independently of a high-level S7 client library.

This is useful for the research methodology:

```text id="p2k7v9"
High-Level Client
      │
      │ Validate behavior
      ▼
Snap7 Exchange
      │
      ▼
Protocol Understanding
      │
      ▼
Hand-Crafted UserData
      │
      ▼
Wire-Level Verification
```

The final request was therefore treated as a **protocol-construction result**, rather than a demonstrated CPU-control result. Testing the actual operational effect requires an implementation that exposes the corresponding CPU-control service.

# 8. Session Isolation

Each Phase 3 test opened a fresh S7comm session.

The test structure was:

```text id="t9x4c3"
Test 1
  │
  └── Fresh session
          │
          ▼
      Write DB3

Test 2
  │
  └── Fresh session
          │
          ▼

  │
```

This prevented the successful memory modification in Test 1 from influencing the subsequent address-boundary and CPU-control tests. Session isolation also makes the PCAP streams easier to correlate with individual test cases.

# 10. Security Characteristics

## 10.1 Direct Memory Modification

The Snap7 target accepted a valid `WriteVar` request and modified the contents of DB3.

The observed operation was:

```text id="d2f6k8"
WriteVar 0x05
      │
      ▼
DB3 / Offset 0
      │
      ▼
16-byte payload
      │
      ▼
Return Code 0xFF
```

This demonstrates that the tested S7comm session permitted direct PLC memory modification without an authentication exchange. The finding remains scoped to the laboratory implementation and its configuration.

---

## 10.2 Memory Boundary Enforcement

The target rejected an attempted write beyond the registered DB3 boundary.

```text id="q3v8m1"
DB3 Size: 1024 bytes
Requested Offset: 65000
Requested Length: 4
          │
          ▼
      Rejected
          │
          ▼
Return Code: 0x05
```

The server remained stable after processing the invalid request. This provides a positive implementation-security observation: the tested memory boundary was enforced rather than allowing the request to proceed into an invalid memory region.

---

## 10.3 CPU Control Surface

The UserData test demonstrated that CPU-control functionality exists as a distinct S7comm control-plane concept and can be represented at the protocol level. The Snap7 target did not implement the tested function, so no CPU state transition was observed. The security significance of CPU-control services therefore remains an area for implementation-specific validation against a target that supports them.

---

# Hardening Considerations

S7comm memory-write capability should be treated as a privileged control-plane function.

Relevant controls include:

* Restricting TCP/102 access to authorized engineering and control hosts.
* Applying controller access-protection mechanisms appropriate to the target generation and deployment.
* Separating engineering workstations from general-purpose network segments.
* Monitoring unexpected `WriteVar` operations and unusual write destinations.
* Establishing an allowlist or baseline of legitimate memory areas modified by engineering or supervisory applications.
* Alerting on writes outside expected Data Block ranges.
* Protecting CPU-management functions through controller-level access controls and network restrictions.
* Testing security controls against the actual Siemens controller and firmware rather than relying exclusively on behavior observed in protocol emulators.

For detection purposes, the combination of:

```text id="v9x5c7"
WriteVar
   +
Unexpected Source
   +
Unexpected Memory Area
   +
Unexpected Address / Length
```

provides a useful basis for identifying potentially unauthorized modification activity.

# Security Characteristics

Phase 3 crossed the boundary from observation into active modification.

The tested Snap7 implementation demonstrated:

```text id="c6m8q2"
                    S7comm Session
                         │
              ┌──────────┴──────────┐
              │                     │
           WriteVar              UserData
              │                     │
        ┌─────┴─────┐               │
        │           │               ▼
      Valid       Invalid       CPU Control
        │           │               │
        ▼           ▼               ▼
    0xFF OK      0x05 Error      Unsupported
        │
        ▼
   DB3 Modified
```

The primary finding is that the laboratory Snap7 configuration accepted a direct `WriteVar` operation without an authentication exchange and committed the supplied data to DB3. The same implementation correctly rejected an out-of-range write with return code `0x05` and remained stable, demonstrating effective boundary enforcement for the tested memory region.

The CPU-control experiment successfully constructed and transmitted a UserData request, but the Snap7 demonstration server does not implement the corresponding functionality. No CPU state transition was therefore claimed or observed. Phase 3 establishes the S7comm write and control surfaces required for the next stage of research.

Phase 4 moves into **SZL and CPU diagnostic services**, shifting the investigation back toward information disclosure and controller identification before returning to protocol-state manipulation in Phase 5.
